# 持久化 模块总览

> 本目录是 aladdin **数据落库**的功能行为唯一信源。实现细节变更只改代码；**后端选择、迁移语义、失败处理**的变更必须先改本目录。

## 背景与目标

aladdin 的权限数据（角色、主体、绑定）原先只活在服务端进程的内存里：进程一重启，所有角色变更与授权关系全部消失。这让"授予一个角色"实际上变成"下一次重启前有效"，也让权限体系无法成为一个可以被运营的系统。

本模块把 `rbac.Store` 这个既有抽象落到真实数据库上，同时保证两件事：

1. **零配置可跑**：默认后端是 sqlite，`make dev` 不做任何配置就能把数据存下来；
2. **后端可替换**：方言从第一天就按"不止一个"设计，MySQL 的接入代价是加一个 DSN，而不是重写一遍持久化。

成功的衡量标准：

1. 服务端重启后，重启前写入的角色与绑定仍然存在，且判定结果不变。
2. 库结构由**版本化的迁移**演进，而不是由模型定义隐式决定；升到最新版本这件事是幂等的，重复执行不产生副作用。
3. 迁移失败时进程拒绝启动，而不是带着半套结构对外服务。
4. 存储层的所有实现（内存、SQL）对同一个输入给出**同一套可观察语义**，包括错误类别。
5. 数据在哪、结构是什么，可以从启动日志与一次查询中确定，不需要读代码。

### 非目标

- 本模块不决定"谁能做什么"。持久化只负责把事实存下来与读回来，判定仍然只有一处实现（见 [../rbac/README.md](../rbac/README.md)）。
- 本模块不是 ORM 使用手册。用哪个 ORM、怎么写查询属于实现细节，不写进 spec。

## 支持的后端

| 后端 | 状态 | 定位 |
|------|------|------|
| sqlite | 默认、已启用 | 本地开发、单机部署、小规模自托管 |
| MySQL | 预留 | 多副本、需要独立数据库服务的部署 |

sqlite 作为默认后端，取的是"零配置即可开始"：它不需要一个独立进程、一个账号、一条网络路径，因此"第一次跑起来"这件事没有前置条件。代价是它不适合多写入方的场景——这正是保留 MySQL 的原因。

### 为什么不用需要 cgo 的 sqlite 驱动

Go 生态里最常用的 sqlite 驱动绑定 C 库，需要开启 cgo 并在构建机上装 C 工具链。aladdin 是一个三端一体的仓库，构建产物要能交叉编译、要能在精简镜像里构建，为一个**本地开发用**的数据库引入 cgo 会把这些能力一起牺牲掉。因此选纯 Go 实现。

这条取舍只影响驱动选型，不影响本模块的任何行为约定。

## 功能行为

### 配置与连接

数据库由两个配置项描述：**后端类型**与**连接串**。它们与其它服务端配置项走同一套来源分层与合并语义（见 [../config/README.md](../config/README.md)），默认值保证零配置可启动。

后端类型的取值集合是封闭的：写了一个不认识的值必须拒绝启动。理由与配置模块同源——静默回落到默认后端会让"我明明配了 MySQL"变成一个需要猜的问题，而它的表现形式是"数据写到了另一个地方"。

连接串的形状随后端而异：

| 后端 | 连接串 |
|------|--------|
| sqlite | 一个文件路径。也可以写成完整的连接串以自行控制底层参数 |
| MySQL | 完整的连接串 |

**连接串里可能含有口令，因此它不得进入日志、错误信息与 `--debug` 输出。** 这是 [../config/README.md](../config/README.md) 中"凭证值不得出现在日志中"的直接推论：连接串在本模块的地位与凭证文件在 CLI 端的地位相同。启动日志中可以出现的是**脱敏后的摘要**——后端类型，以及不带口令的定位信息（文件路径，或用户名@地址/库名）。这样"我改的连接串到底有没有被读到"仍然可答，而口令不外泄。

### 连接失败与不可用

连不上库、结构版本落后、迁移执行失败，都属于**启动期的致命错误**：进程以非零退出码终止，错误信息里包含后端类型与脱敏后的定位信息。

**运行期**数据库不可用时不得降级。存储层遇到无法归类的数据库错误，必须让判定路径快速失败，由上层决定是否重试；**绝不允许**退化为"允许全部"或"拒绝全部"——后者会把一次数据库抖动放大成全站权限拒绝，前者更糟。这条与 [../rbac/enforcement.md](../rbac/enforcement.md) 的取向一致，不得因为"库暂时连不上"而放宽。

"没找到"与"库出错"是两类结果，必须可区分：前者是正常的业务结论（角色不存在），后者是设施故障。把它们混成同一个错误会让一次数据库故障被当成"权限配置缺失"来处理。

### 迁移

库结构由一组**有序、带版本标识**的迁移推进到最新版本。约定：

- **迁移在服务端启动时自动执行**，先于监听端口打开。失败即拒绝启动。
- **迁移是幂等的**：已经应用过的版本不再重复执行。重复启动服务端不产生任何额外副作用。
- **迁移按顺序整体应用**：不存在"跳到中间某个版本"的常规路径。
- **已发布的迁移不可修改**。它已经在别的库上执行过，改动它不会改变那些库，只会让新库与旧库的结构不一致。需要变更结构就追加一条新迁移。
- **库里存在代码中不存在的版本时拒绝启动**。这通常意味着二进制被回滚而库没有，带着未知结构继续服务比停机更危险。
- **单个迁移在事务中执行**：失败则整体回滚，不留下半成品结构。

**迁移的结构定义与"表应该长什么样"是同一件事，只有一个信源。** 当结构定义被改动而迁移没有相应追加时，必须能被自动化检查发现，而不是等到某个库上出现结构差异才暴露。检查手段见下文的可验证性表。

### 内置角色的初始化

内置角色的**存在**是权限模型的一部分（见 [../rbac/role-model.md](../rbac/role-model.md)），因此库首次可用时必须把它们补进去。但它与迁移不是一回事：迁移管结构，它管数据。

初始化遵循一条规则：**只补缺失的，不覆盖已存在的。** 模型明确允许内置角色的权限绑定在部署时被调整，每次启动都按代码里的定义覆盖一遍，等于把这种调整静默撤销。

### 边界与约束

本模块**明确不处理**：

- **结构回滚命令**。回滚一次已经上线的结构变更需要人工判断数据怎么办，把它做成一条命令是在鼓励无脑回滚。需要时由运维人员手写 SQL。
- **数据迁移之外的在线结构变更**。迁移发生在启动时，此时还没有请求在途。
- **多副本并发迁移的加锁**。sqlite 是单文件、单进程写入，不存在这个问题；MySQL 上多副本同时启动时的迁移互斥留到真正接入 MySQL 时处理。
- **数据备份与恢复**。这是部署形态的事，不由本模块承诺。
- **缓存层的失效**。判定路径目前不走缓存；引入缓存时按其自身的设计处理。

约束：

- 全仓库只有一处代码建立数据库连接、只有一处代码执行迁移。其他模块不得自行 `gorm.Open` 或执行 DDL。
- 表结构只有一处定义。任何"在别处再建一张表"或"在业务代码里顺手 `AutoMigrate`"的做法都不允许。
- 存储实现不得绕过 `rbac.Store` / `rbac.MutableStore` 被业务代码直接使用：判定路径只依赖只读接口这一约束不因换了后端而放宽。

## 可验证性与长程执行

**部分属于长程任务。** 连接与迁移是启动期的一次性动作，但"库结构与代码定义一致"这件事需要在每次结构变更后重新成立——它是长期约束，不是一次性检查。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 零配置可启动 | 无数据库配置时服务端以 sqlite 启动并在工作目录建库（启动冒烟） |
| 后端类型封闭 | 未登记的后端取值被拒绝，且错误信息指出取值与合法集合（`internal/config` / `internal/database` 测试） |
| 连接串不入日志 | 口令不出现在启动日志与错误信息中（`internal/database` 测试 + 启动冒烟） |
| 迁移幂等 | 同一库上连续执行两次，第二次不改变任何结构、不报错（`internal/database/migrate` 测试） |
| 未知版本拒绝启动 | 库中存在代码里没有的版本时返回错误（`internal/database/migrate` 测试） |
| 迁移清单自洽 | 版本标识唯一、非空、顺序稳定（`internal/database/migrate` 测试） |
| 结构与定义一致 | 迁移后的表、列与主键约束与**冻结的快照**一致；改了结构定义而没追加迁移时该测试失败（`internal/database/migrate` 测试） |
| 持久化确实生效 | 用同一个库文件构造两次存储，第二次能读到第一次写入的数据（`internal/rbac/gormstore` 测试） |
| 实现语义一致 | 内存实现与 SQL 实现跑**同一套**契约用例，对同一输入给出相同的返回值与**相同的错误类别**（`internal/rbac/gormstore` 测试） |
| 内置角色只补不覆盖 | 已被调整过的内置角色在再次初始化后保持调整后的值（`internal/rbac` 测试） |

> 结构与定义一致性是唯一需要长期守护的一条。**当它失败时不要改快照了事**：先回答"这次结构变更本应有一个配套迁移吗"，是则补迁移，不是则确认快照的更新是本次变更的一部分。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 配置模块 | 消费已解析完成的数据库后端类型与连接串，不自行读取来源（见 [../config/server-config.md](../config/server-config.md)） |
| RBAC 模块 | 实现其 `Store` / `MutableStore` 抽象；判定语义不因后端改变（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 可观测性 | 迁移与连接作为"涉及外部依赖调用"的关键路径留痕：调用前记目标（脱敏）、调用后记结果与耗时（见 [../../observability.md](../../observability.md)） |
| ORM 与迁移库 | 提供方言适配与版本表；本模块只消费，不自行实现 SQL 方言分支 |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| MySQL 多副本启动时的迁移互斥 | 接入 MySQL 时实现（**未定**） | 只影响迁移运行器；sqlite 侧不受影响 |
| 是否提供独立的迁移命令 | 不提供，只随启动执行（**已定**，见"迁移"） | 影响部署流程与命令入口 |
| sqlite 的连接数上限 | 单连接（**已定**） | 只影响连接池取值；换后端不影响 |
