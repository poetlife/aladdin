# 持久化 — 表结构与连接串

## 背景与目标

本文件回答两个问题：**库里存了什么、它们之间有什么不变式**，以及**连接串怎么填**。

它不描述用什么类型、什么列名之外的技术细节——那些跟着实现走。它描述的是：数据的形状、哪些事实必须成立、以及当同一份事实有两个来源时以谁为准。

## 功能行为

### 表

#### 角色表

存放角色的定义。一个角色一条记录，标识唯一。

| 内容 | 说明 |
|------|------|
| 角色标识 | 主键。一旦发布不可更改——标识变更在模型上是"删除旧角色 + 新建角色"（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 显示名 | 可改。标识不可改而名称可改，是这个模型刻意的区分 |
| 内置标记 | 该角色是否由权限目录派生。内置角色不可删除 |
| 权限码集合 | 该角色直接持有的权限码 |
| 被继承的角色标识 | 该角色继承的父角色 |
| 静态互斥的角色标识 | 不可与它同时授予同一主体的角色 |

后三项是**有序无关的集合**：读出来的顺序不影响判定（判定会排序，见 `internal/rbac/sort.go`）。

#### 主体表

存放发起操作的一方。一个主体一条记录，标识唯一。**主体是规范实体**：RBAC 的角色绑定挂在它身上，与"这个人用哪个渠道登进来"无关。

| 内容 | 说明 |
|------|------|
| 主体标识 | 主键。首次见到一个未知身份时由 aladdin 分配，此后不再改变 |
| 主体类型 | 人类用户 / 服务账号 / 机器凭证 |
| 默认作用域 | 未显式指定作用域时使用的值 |

**主体标识不由渠道标识派生，也不含任何渠道取值。** 它是一条只在 aladdin 内部有意义的规范标识：分配即冻结，永不复用，不随渠道、邮箱或显示名的变化而变化。因此"用什么渠道登进来"这件事不出现在这张表上——一个主体可以有多个渠道，把它写成主体的一列等于替它选定唯一一个，与多渠道登录直接冲突。

**未登记的主体在判定时视为不存在**，而不是"存在但没有权限"。这两者的区别会反映到错误类别上：前者是"主体不存在"，后者是"权限不足"，客户端的处理方式不同（见 [../rbac/enforcement.md](../rbac/enforcement.md)）。

主体的**登记**属于认证流程，不属于授权面：授权面对一个未登记的主体授权，不代替认证模块把它创建出来。

#### 身份别名表（认证模块）

存放"某个渠道上的某个身份属于哪个主体"这一事实。一个身份一条记录，身份本身唯一。

| 内容 | 说明 |
|------|------|
| 身份来源 | 这个身份由谁签发（如 Google） |
| 身份标识 | 该来源签发的不可变标识 |
| 主体标识 | 这个身份属于谁 |
| 展示信息 | 该渠道给出的可读标识（如邮箱），仅供展示与排障 |

前两项构成主键：**同一个来源的同一个身份只能属于一个主体**，由库保证。这条唯一性不是防重复写入的优化，而是归并语义的地基——它同时给出了"登录时用哪个主体"和"这个身份不能再被别人认领"两个结论。

**一个主体可以有多个身份，一个身份只能属于一个主体。** 这就是多渠道登录同一个用户的全部机制：登录时先按（来源，身份标识）查这张表，命中即用其指向的主体，未命中才分配一个新主体并写入一条。因此"同一个人两次登录不会变成两个主体"由这张表保证，而不是由主体标识的构造方式保证。

**展示信息落在身份这一层，不落在主体上。** 同一个人在两个渠道上可能有两个不同的邮箱；把它记在主体上，等于要求回答"哪个邮箱才是这个人的"，而这个问题没有正确答案。它**不参与任何判定**，也不参与身份归属的确定——按邮箱归并意味着邮箱在渠道侧被回收的那天，另一个人接管了这个主体已有的全部绑定（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。

**与主体表之间不建外键**，理由与绑定表相同：主体是否存在是领域约束，唯一入口是认证流程的登记动作，不复制成库约束。

按主体标识建索引：列出"这个人已经绑了哪些渠道"是绑定与解绑界面的常规读取路径（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。这与"不为想象中的查询先付写入代价"不冲突——这是一个确定存在的查询，与绑定表刻意不加的索引不同类。

#### 绑定表

存放"主体在某个作用域上持有某个角色"这一事实。一条事实一条记录。

| 内容 | 说明 |
|------|------|
| 主体标识 | 该事实的主体方 |
| 角色标识 | 该事实的角色方 |
| 作用域 | 该事实生效的范围 |

**三条内容全同的记录只能存在一条。** 这条唯一性由库保证，而不是由"写入前先查一下"保证：后者在并发下不成立，而"重复授予同一角色"是最常见的重复写入来源。幂等在这里是硬要求，不是优化（见 [../rbac/role-model.md](../rbac/role-model.md) 的幂等/去重要求）。

同一个主体的同一个角色可以在**不同作用域**上各持有一条，这是合法的——作用域是权限边界的一部分，不是绑定的附加属性。

绑定表**不引用**角色表与主体表：它记录的是一个已经通过校验的事实，而"角色是否存在""主体是否存在""是否违反互斥"这些**都是领域约束，唯一入口是授权面的校验**（见 [../rbac/role-model.md](../rbac/role-model.md) 的角色继承与约束）。把同一份判定再写一遍到库约束里，等于让它有两个会漂移的实现。

#### 会话表（认证模块）

存放已签发的访问凭证。**一个已签发的凭证一条记录**，凭证的摘要唯一。

| 内容 | 说明 |
|------|------|
| 凭证摘要 | 主键。是凭证本身的密码学摘要，**不是凭证原文**（见下） |
| 主体标识 | 这个会话代表谁 |
| 主体类型 | 签发时该主体的类型。与绑定作用域一样，是签发那一刻的快照 |
| 绑定作用域 | 签发时绑定在凭证上的默认作用域 |
| 签发时间 | 排障与审计用，不参与判定 |
| 过期时间 | 到点即失效 |

主体标识与主体类型是**快照**，不是对主体表的引用：凭证一旦签发，它代表的那一方就固定下来。这样校验路径只读这一张表，不必回头再查主体表。

**凭证原文不入库。** 库里存的是它的摘要，校验时对送来的凭证现算摘要再比。这样一次数据库泄露交出的是摘要而不是可以直接用的凭证——攻击者拿到摘要也构造不出原文，因为它是一个单向函数的结果。会话因此可以在"库被读到不等于凭证被拿走"这条性质下持久化。

摘录用不涉及密钥的通用摘要函数即可，**不需要**口令哈希那类刻意放慢的算法：凭证是密码学随机数，不存在"被猜到"的风险，放慢只会让每个请求都白付一次代价。这条与口令的区别要在实现时守住——把两者用同一个函数处理，等于把凭证降级成口令。

**过期行会被清理**，否则这是一张只增不减的表。清理时机与"过期即失效"的关系见 [../identity/session-token.md](../identity/session-token.md)——正确性**不依赖**清理：判定时已过期的行一律视同不存在，清理只负责不让表无限增长。

会话表**不引用**主体表，理由与绑定表相同（见上）：主体是否存在是领域约束，唯一入口是认证流程的登记动作，不复制成库约束。

#### 迁移版本表

记录库结构已经演进到哪一步：每个已应用的迁移一条记录，标识唯一。

它由迁移机制自己维护，业务代码不读写它。

### 连接串

#### sqlite

取值有两种形态，按形状自动区分：

| 形态 | 判据 | 行为 |
|------|------|------|
| 文件路径 | 不含 `?` 且不以 `file:` 开头 | 按它定位数据库文件，并补上默认的底层参数 |
| 完整连接串 | 含 `?` 或以 `file:` 开头 | 原样使用，不补任何参数 |

默认补上的三个参数及其理由：

| 参数 | 作用 | 为什么是默认值 |
|------|------|--------------|
| 等待锁的超时 | 遇到写锁时等待而非立刻报错 | sqlite 只有一个写者；不设它，一次并发写会直接变成一个失败请求 |
| 预写日志 | 读写不互相阻塞 | 默认的日志模式会让读操作阻塞在写事务上 |
| 外键约束 | 启用外键检查 | 本模块不建外键，但底层默认关闭会让**将来**加上的外键静默失效——静默失效的约束比没有约束更糟 |

路径的**父目录必须存在**。不自动创建目录：自动创建会让一个拼错的路径变成"在这个奇怪的地方建了个空库"，而数据看起来全丢了。宁可拒绝启动。

路径本身**不能指向一个已存在的目录**。这一条不查也能跑到第一次查询才失败，但那时错误来自底层驱动，只会说"打不开数据库文件"，不会提示"你把目录当成了文件"。配置错误应该在配置这一层被说清楚。

文件路径的解析基准与配置文件一致（启动时的工作目录），见 [../config/README.md](../config/README.md)。

#### MySQL

取值是完整的连接串，原样使用。本模块不解析、不拼接、不补默认参数——MySQL 的连接串已经有成熟且被广泛理解的形态，在其上再叠一层默认值只会让"为什么连到了别处"更难回答。

### 数据来源的唯一性

**同一份事实只能有一个存储位置。** 具体地：

- 角色、主体、绑定只存在于数据库。服务端**不再**持有这些数据的第二份可写副本；进程内不保留跨请求的状态副本。
- **会话与身份别名同理**：已签发的会话只在数据库。进程内内存实现只用于测试，不得在生产装配路径上出现——两份可写副本意味着一次撤销可能只落到其中一份上，而"撤销了但仍然能用"是认证里后果最重的一类错。身份别名更是如此：两份可写副本意味着同一个人可能被解析成两个主体，而这正是本模块要消灭的那件事。
- 读取一律走 `rbac.Store`。任何模块想直接查库都必须先回到这个抽象上加方法，而不是绕过它自己写查询。认证模块的会话与身份别名读取同理，走它自己的存储抽象。
- 内置角色的**定义**来自权限目录（唯一信源），**绑定关系**来自数据库。两者冲突时以数据库为准——那正是"部署时可调整"的含义。

## 边界与约束

- 表结构变更一律通过追加迁移完成，不在业务代码中建表或改列。
- 本模块不定义任何与**权限判定**有关的列：判定所需的一切都是角色、主体、绑定三类事实的组合。
- **不存放口令，也不存放任何凭证的原文。** 会话以**摘要**存放（见下）：拿到库的人拿到的是摘要，不是可以直接拿去用的凭证。这是"库被读到不等于凭证被拿走"这条性质的落点，也是本节唯一一处为认证模块开的存放许可。
- 认证模块的表与 RBAC 的表**同样在本文件声明、由同一套迁移推进**。表结构与迁移机制是全库共用的基础设施，各模块只拥有自己的表；不存在第二处建表入口，也不存在第二套迁移清单。
- 主体的标识是"已确认的一方"，不是"如何确认这一方"。**会话表**因此只记录这次确认的结果（谁、到什么时候为止），不记录确认的方式；"这个主体有哪些进入方式"是**另一类事实**——它是一条映射（身份别名表），既不是主体的属性，也不是一次确认的留痕，所以既不落在主体表上，也不落在会话表上。
- **身份的归属只有一处决定**：登录时的查-或-建，以及已登录主体对自己发起的绑定（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。没有任何一列、也没有任何一次判定读邮箱或显示名来决定"这个身份是谁"——那会引入一条能被渠道侧改名或回收直接改写的权限路径。

## 可验证性与长程执行

**非长程任务。** 表结构与连接串的解析都是确定性的同步过程，没有中间状态。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 表与列符合约定 | 迁移后比对冻结的结构快照（`internal/database` 测试） |
| 绑定唯一性由库保证 | 同一 `(主体, 角色, 作用域)` 重复写入后表内仍只有一条记录（`internal/rbac/gormstore` 测试） |
| 身份唯一归属由库保证 | 同一个 `(身份来源, 身份标识)` 指向第二个主体时写入失败，表内归属不变（`internal/identity/gormstore` 测试） |
| 一个主体可有多个身份 | 同一主体下写入两个不同来源的身份后都能读回，且都指向该主体（`internal/identity` 测试） |
| 主体标识与渠道无关 | 同一个主体先后用两个渠道登录，读回的主体标识相同；换渠道不改主体标识（`internal/identity` 测试） |
| 未登记主体视为不存在 | 对未登记主体的绑定查询返回"主体不存在"这一类别（契约测试） |
| 会话原文不入库 | 直接读会话表，任何一列的值都不是签发出去的凭证本身（`internal/identity` 测试） |
| 过期会话即失效 | 过期行存在时用它认证失败，且失败类别是"未认证"（契约测试） |
| 会话撤销立即生效 | 撤销后同一凭证的下一次请求被拒（契约测试） |
| 内存实现与 SQL 实现同结果 | 同一套会话用例在两个实现上得到相同的结论与错误类别（契约测试） |
| 连接串两形态区分正确 | 路径形态补参数、连接串形态原样（`internal/database` 测试） |
| 口令不外泄 | 含口令的连接串不出现在任何脱敏摘要与错误信息中（`internal/database` 测试） |
| sqlite 父目录缺失即拒绝 | 指向不存在目录的路径导致启动失败，而不是新建一个空库（`internal/database` 测试） |
