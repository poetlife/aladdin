# 持久化 — 表结构与连接串

## 背景与目标

本文件回答两个问题：**库里存了什么、它们之间有什么不变式**，以及**连接串怎么填**。

它不描述用什么类型、什么列名之外的技术细节——那些跟着实现走。它描述的是：数据的形状、哪些事实必须成立、以及当同一份事实有两个来源时以谁为准。

## 功能行为

### 表

#### 角色表

存放角色的定义。一个角色一条记录，标识唯一。

| 内容 | 说明 |
|------|------|
| 角色标识 | 主键。一旦发布不可更改——标识变更在模型上是"删除旧角色 + 新建角色"（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 显示名 | 可改。标识不可改而名称可改，是这个模型刻意的区分 |
| 内置标记 | 该角色是否由权限目录派生。内置角色不可删除 |
| 权限码集合 | 该角色直接持有的权限码 |
| 被继承的角色标识 | 该角色继承的父角色 |
| 静态互斥的角色标识 | 不可与它同时授予同一主体的角色 |

后三项是**有序无关的集合**：读出来的顺序不影响判定（判定会排序，见 `internal/rbac/sort.go`）。

#### 主体表

存放发起操作的一方。一个主体一条记录，标识唯一。**主体是规范实体**：RBAC 的角色绑定挂在它身上，与"这个人用哪个渠道登进来"无关。

| 内容 | 说明 |
|------|------|
| 主体标识 | 主键。首次见到一个未知身份时由 aladdin 分配，此后不再改变 |
| 主体类型 | 人类用户 / 服务账号 / 机器凭证 |
| 默认作用域 | 未显式指定作用域时使用的值 |

**主体标识不由渠道标识派生，也不含任何渠道取值。** 它是一条只在 aladdin 内部有意义的规范标识：分配即冻结，永不复用，不随渠道、邮箱或显示名的变化而变化。因此"用什么渠道登进来"这件事不出现在这张表上——一个主体可以有多个渠道，把它写成主体的一列等于替它选定唯一一个，与多渠道登录直接冲突。

**未登记的主体在判定时视为不存在**，而不是"存在但没有权限"。这两者的区别会反映到错误类别上：前者是"主体不存在"，后者是"权限不足"，客户端的处理方式不同（见 [../rbac/enforcement.md](../rbac/enforcement.md)）。

主体的**登记**属于认证流程，不属于授权面：授权面对一个未登记的主体授权，不代替认证模块把它创建出来。

#### 身份别名表（认证模块）

存放"某个渠道上的某个身份属于哪个主体"这一事实。一个身份一条记录，身份本身唯一。

| 内容 | 说明 |
|------|------|
| 身份来源 | 这个身份由谁签发（如 Google） |
| 身份标识 | 该来源签发的不可变标识 |
| 主体标识 | 这个身份属于谁 |
| 展示信息 | 该渠道给出的可读标识（如邮箱），仅供展示与排障 |

前两项构成主键：**同一个来源的同一个身份只能属于一个主体**，由库保证。这条唯一性不是防重复写入的优化，而是归并语义的地基——它同时给出了"登录时用哪个主体"和"这个身份不能再被别人认领"两个结论。

**一个主体可以有多个身份，一个身份只能属于一个主体。** 这就是多渠道登录同一个用户的全部机制：登录时先按（来源，身份标识）查这张表，命中即用其指向的主体，未命中才分配一个新主体并写入一条。因此"同一个人两次登录不会变成两个主体"由这张表保证，而不是由主体标识的构造方式保证。

**展示信息落在身份这一层，不落在主体上。** 同一个人在两个渠道上可能有两个不同的邮箱；把它记在主体上，等于要求回答"哪个邮箱才是这个人的"，而这个问题没有正确答案。它**不参与任何判定**，也不参与身份归属的确定——按邮箱归并意味着邮箱在渠道侧被回收的那天，另一个人接管了这个主体已有的全部绑定（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。

**与主体表之间不建外键**，理由与绑定表相同：主体是否存在是领域约束，唯一入口是认证流程的登记动作，不复制成库约束。

按主体标识建索引：列出"这个人已经绑了哪些渠道"是绑定与解绑界面的常规读取路径（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。这与"不为想象中的查询先付写入代价"不冲突——这是一个确定存在的查询，与绑定表刻意不加的索引不同类。

#### 绑定表

存放"主体在某个作用域上持有某个角色"这一事实。一条事实一条记录。

| 内容 | 说明 |
|------|------|
| 主体标识 | 该事实的主体方 |
| 角色标识 | 该事实的角色方 |
| 作用域 | 该事实生效的范围 |

**三条内容全同的记录只能存在一条。** 这条唯一性由库保证，而不是由"写入前先查一下"保证：后者在并发下不成立，而"重复授予同一角色"是最常见的重复写入来源。幂等在这里是硬要求，不是优化（见 [../rbac/role-model.md](../rbac/role-model.md) 的幂等/去重要求）。

同一个主体的同一个角色可以在**不同作用域**上各持有一条，这是合法的——作用域是权限边界的一部分，不是绑定的附加属性。

绑定表**不引用**角色表与主体表：它记录的是一个已经通过校验的事实，而"角色是否存在""主体是否存在""是否违反互斥"这些**都是领域约束，唯一入口是授权面的校验**（见 [../rbac/role-model.md](../rbac/role-model.md) 的角色继承与约束）。把同一份判定再写一遍到库约束里，等于让它有两个会漂移的实现。

#### 会话表（认证模块）

存放已签发的访问凭证。**一个已签发的凭证一条记录**，凭证的摘要唯一。

| 内容 | 说明 |
|------|------|
| 凭证摘要 | 主键。是凭证本身的密码学摘要，**不是凭证原文**（见下） |
| 主体标识 | 这个会话代表谁 |
| 主体类型 | 签发时该主体的类型。与绑定作用域一样，是签发那一刻的快照 |
| 绑定作用域 | 签发时绑定在凭证上的默认作用域 |
| 签发时间 | 排障与审计用，不参与判定 |
| 过期时间 | 到点即失效 |

主体标识与主体类型是**快照**，不是对主体表的引用：凭证一旦签发，它代表的那一方就固定下来。这样校验路径只读这一张表，不必回头再查主体表。

**凭证原文不入库。** 库里存的是它的摘要，校验时对送来的凭证现算摘要再比。这样一次数据库泄露交出的是摘要而不是可以直接用的凭证——攻击者拿到摘要也构造不出原文，因为它是一个单向函数的结果。会话因此可以在"库被读到不等于凭证被拿走"这条性质下持久化。

摘录用不涉及密钥的通用摘要函数即可，**不需要**口令哈希那类刻意放慢的算法：凭证是密码学随机数，不存在"被猜到"的风险，放慢只会让每个请求都白付一次代价。这条与口令的区别要在实现时守住——把两者用同一个函数处理，等于把凭证降级成口令。

**过期行会被清理**，否则这是一张只增不减的表。清理时机与"过期即失效"的关系见 [../identity/session-token.md](../identity/session-token.md)——正确性**不依赖**清理：判定时已过期的行一律视同不存在，清理只负责不让表无限增长。

会话表**不引用**主体表，理由与绑定表相同（见上）：主体是否存在是领域约束，唯一入口是认证流程的登记动作，不复制成库约束。

#### 档案表（个人档案模块）

存放主体的展示信息。一个主体最多一条记录。

| 内容 | 说明 |
|------|------|
| 主体标识 | 主键 |
| 昵称 | 可空，空表示未设置 |
| 简介 | 可空 |
| 头像对象键 | 可空；指向对象存储里的一个对象，空表示没有头像。**库里存的是键，不是字节** |
| 更新时间 | 展示与排障用，不参与判定 |

**行是惰性创建的**：主体登记时不写这一行，本人第一次保存档案才写入。认证流程因此完全不依赖本模块——把"登记主体"与"初始化档案"绑在一起，只会让认证流程多一个与被认证者无关的失败点。

**昵称不加唯一约束，也不建议按它建索引。** 唯一约束会把它变成一个查找键，也就是第二条身份路径（理由见 [../profile/README.md](../profile/README.md) 的"边界与约束"）。本表不建按昵称的索引：没有任何一条读取路径按昵称查。

**头像字节不在这张表里。** 字节在对象存储（见 [../profile/avatar-storage.md](../profile/avatar-storage.md)）；库内的对象键是"这个主体有没有头像"的**权威**，对象存储上可能留下无从被引用的孤儿对象。

档案表**不引用**主体表，理由与绑定表、会话表相同：主体是否存在是领域约束，唯一入口是认证流程的登记动作，不复制成库约束。

#### 工程表（galaxy 模块）

存放用户创作的作品单元。一个工程一条记录，标识唯一。

| 内容 | 说明 |
|------|------|
| 工程标识 | 主键。由 aladdin 分配，**不可猜、不可改、不复用**——它是发布地址的一部分，而发布态是公开匿名的 |
| 拥有者主体标识 | 创建它的主体。不可转移 |
| 名称 | 可改。**仅用于本人识别，不加唯一约束、不建索引** |
| 简介 | 可空 |
| 创建时间 / 更新时间 | 展示与排障用，不参与判定 |

**工程表上不放清单，也不放发布指针。** 草稿与版本的文件清单、发布的产物清单都不在这张表上——工程列表接口会读这一行，把每个工程的清单一起读上来是一笔与列表无关的代价。**发布指针住在内容槽表上**（每槽一个，见下）；**整张表也不含任何字节**（见下）。**工程也没有"形态"这一列**：它有哪几种内容，由内容槽表里有哪些行回答。

**名称不加唯一约束、不建索引。** 与昵称同理（见上文档案表）：一旦它成为查找键，它就成了一条可以被改名或抢注改写的路径；而发布地址用的是不可猜标识，用不着名字。

#### 内容槽表（galaxy 模块）

存放一个工程启用了哪些内容槽，以及每个槽的发布指针。**一个槽一条记录。**

| 内容 | 说明 |
|------|------|
| 工程标识 / 槽 | 联合主键。槽取 `site` 或 `docs` |
| 当前发布标识 | 可空。空表示这个槽未发布；指向发布表里的一条记录 |

**行存在即槽启用。** "这个工程有哪些内容槽"这件事只有这一处定义，工程表上不重复存一份——那会是同一事实的第二个来源，两者不一致时无从判断谁对。**槽只增不删**（见 [../galaxy/site-model.md](../galaxy/site-model.md)），因此这张表不会出现"某一行曾经存在过"的历史。

**发布指针按槽分开，是这一层最要紧的一条。** 两个槽各有各的指针，发布、撤回都只碰自己那一行：站点发出去不影响文档，撤回一个也不影响另一个。这与"每个槽各有一套草稿、版本与地址"是同一件事在存储上的落点。

#### 草稿表（galaxy 模块）

存放**每一个内容槽**的当前编辑内容。一个槽最多一条记录。

| 内容 | 说明 |
|------|------|
| 工程标识 / 槽 | 联合主键 |
| 文件清单 | 一组「路径 → 内容摘要或资产标识」。**整组替换**：保存草稿写的是这一整列 |
| 更新时间 | 展示与排障用 |

**清单里没有字节。** 文本条目的字节是对象存储里按内容摘要寻址的对象（见 [../galaxy/site-model.md](../galaxy/site-model.md)）。清单的承载方式（一列序列化，或一组子行）属于实现细节，但**必须整组读写**——保存草稿表达的是完整状态，不是增量。

**与版本表分开，而不是在工程行上放一列。** 草稿是可变的、随时被覆盖写的；版本是不可变的。放在一起会让"这一行到底是不是历史"取决于一个额外的标志位，而两张表让不可变性由表的存在方式表达。

**每一槽的草稿行是惰性创建的**，理由与档案表相同：工程创建时不写这一行，该槽第一次保存草稿才写入。

#### 草稿快照表（galaxy 模块）

存放**被替换掉的**那些草稿清单。一份快照一条记录。

| 内容 | 说明 |
|------|------|
| 快照标识 | 主键。由 aladdin 分配。**前缀与版本不同**（`snp_` 对 `ver_`） |
| 工程标识 / 槽 | 它属于哪个槽 |
| 序号 | 在**槽内**递增，**仅用于排序**。不按时间排序：两次替换可能落在同一个时间刻上（时间列精度有限），那时"哪一条最近"会变成由标识的随机性决定的答案（见 [../galaxy/project-versioning.md](../galaxy/project-versioning.md)） |
| 文件清单 | 被替换掉的那份清单。**字节不在库里** |
| 来源 | 替换它的那一端（`web` / `cli`），取自上报端标识 |
| 操作者主体标识 / 时间 | 留痕。时间同时参与保留策略的判定 |

**它不是版本。** 没有"发布"这条路可走，也不进版本列表；保留有上限（每个槽最近 50 条、且不超过 14 天），清理挂在**写入**那一处（与预览凭证同一条做法），因此表的大小只由"还有多少条活的快照"决定，读的那条路是只读的。

**写入与草稿行在同一个事务里。** 先读旧清单、再写新清单，中间隔着一次返回——中途失败留下的是"新草稿已经生效、旧的那份没有任何记录"，而那正是这张表要消掉的东西。

#### 版本表（galaxy 模块）

存放内容清单的不可变快照。一个版本一条记录。

| 内容 | 说明 |
|------|------|
| 版本标识 | 主键。由 aladdin 分配 |
| 工程标识 / 槽 | 该版本属于哪个工程的哪个内容槽 |
| 序号 | **在槽内**递增。**仅用于展示与排序，不是标识** |
| 文件清单 | 保存那一刻草稿的清单。**写入后不再修改** |
| 说明 | 可选的一句短文本，**可事后改**。它是元数据层：不可变说的是清单与渲染规则版本（见 [../galaxy/project-versioning.md](../galaxy/project-versioning.md)） |
| 渲染规则版本 | 保存时所处的渲染规则版本。只有 `docs` 槽使用它，重新发布时按它渲染（见 [../galaxy/site-model.md](../galaxy/site-model.md)） |
| 保存时间 | 排障与展示用 |

**版本引用了哪些资产由这张表的清单直接读出。** 清单的每一条写明它是文本条目还是资产条目——文本里那一处的写法（构建产物的路径，或手写的 `asset://` 记号）与条目由写入校验绑在一起，因此这件事不必解析任何文本，也没有第二处集合（见 [../galaxy/project-versioning.md](../galaxy/project-versioning.md)）。

**序号可以有空洞**：删除一个版本不重排后续序号。把序号当标识意味着删除会波及所有更大的序号。

#### 资产表（galaxy 模块）

存放工程资产库里的媒体文件。一个资产一条记录。

| 内容 | 说明 |
|------|------|
| 资产标识 | 主键。由 aladdin 分配 |
| 工程标识 | 该资产属于哪个工程 |
| 内容摘要 | 字节的密码学摘要。**是"同一份字节"的标识**；公开区按**（内容摘要，媒体类型）**寻址，因此同一份字节以两种类型出现时是两个对象（见 [../galaxy/asset-library.md](../galaxy/asset-library.md)）。由上传方声明，提交时由服务端核对（让存储侧算，给不出时读回自己算） |
| 媒体类型 | **上传方声明的类型**，服务端只校验它在白名单内。它同时决定下发时的内容类型 |
| 字节数 | 展示与配额用 |
| 原始文件名 | 仅供展示与排障。**不作为对象键，不参与任何判断** |
| 展示标题 | 可选的展示名，与文件名分离。空时界面回退到文件名 |
| 备注 | 自由文本说明。**不进对象键、不进发布产物、不进日志原文** |
| 上传时间 | 排障与展示用 |

**字节不在这张表里。** 私有区的对象键由工程标识、条目类别与标识或内容摘要构成，公开区按（内容摘要，类型）寻址，两者都是确定性的、不需要在库里再存一遍（见 [../galaxy/asset-library.md](../galaxy/asset-library.md)）。

**资产不可变，因此这张表没有"版本"或"历史"的概念**：换一张图是新增一条记录，再改**引用它的地方**（文本里的记号，或构建产物里的路径），不是修改这一行。

**可变的只有说明层**（展示标题、标签、备注）。改它们**不碰**这一行里的内容摘要、媒体类型、类别与字节数——"资产不可变"说的是字节层（见 [../galaxy/asset-library.md](../galaxy/asset-library.md)）。

#### 资产标签表（galaxy 模块）

存放资产的标签。一个资产的一个标签一条记录。

| 内容 | 说明 |
|------|------|
| 工程标识 / 资产标识 | 这个标签挂在哪个资产上 |
| 标签 | **归一化之后**的标签串（小写，规则见 [../galaxy/asset-library.md](../galaxy/asset-library.md)） |

**标签独立成表，而不是资产行上的一列。** 它要支持"按标签列出工程里的资产"，而那在资产行的一列里只能靠模糊匹配；独立表让这件事走索引。代价是列表读取要合并一次标签查询、写入要与资产行落在同一个事务里。

**(工程标识, 资产标识, 标签) 唯一**，因此同一资产上的同一个标签不会产生第二行。删除资产时这一组行一并删除——它描述的是那个资产，资产没有了它就没有意义。

**表里只有归一化之后的值。** 原始写法不保留：标签一律小写存储与展示，因此不存在"库里存一份、比较时另算一份"的第二处规则。

#### 发布表（galaxy 模块）

存放每次发布产生的对外产物。一次发布一条记录。

| 内容 | 说明 |
|------|------|
| 发布标识 | 主键。由 aladdin 分配 |
| 工程标识 / 槽 / 版本标识 | 这次发布的是哪个工程的哪个槽的哪个版本 |
| 产物清单 | 一组「路径 → 内容摘要」。对外地址按它分派；**字节不在库里** |
| 发布人主体标识 / 发布时间 | 留痕 |

**产物清单落库，而不是每次请求现算。** 库里存着"当前发布的是什么"这一事实，取用者只读它，不必重新读文件清单、重新查资产、重新渲染——那会把一个已经完成并校验过的结论变成每次请求都要重算的东西。这与头像"库内的对象键是权威"同构。**清单只有路径与摘要，因此这张表也不随内容增长。**

**撤回发布只清掉内容槽表上的指针，不删这张表的记录。** 因此撤回之后可以重新指向它，也保留了排障所需的历史。这条记录的清理策略见 [../galaxy/publication.md](../galaxy/publication.md) 的待定决策。

#### 客户端事件表（遥测模块）

存放客户端上报的**本地动作**（前端拦下的保存、按上限早退的上传、命令行在配置阶段就退出的失败）。一条事件一条记录。它是站内只读遥测页的数据源，语义见 [observability.md 的「客户端事件」](../../observability.md)。

| 内容 | 说明 |
|------|------|
| 自增标识 | 主键 |
| 发生时间 | **服务端**收到并落库的时刻，不由上报端提供。建索引：按时间窗查询与保留期回收都要按它筛选 |
| 上报端 / 界面 / 动作 / 结局 | 有界取值。动作是**字符串而不是枚举**——清单会扩展，而这里是历史数据 |
| 耗时 | 上报端声明的毫秒数；0 表示未提供 |
| 客户端链路 ID | 上报端当时所在链路的 `trace_id`。**不是**本行所属请求那条链路的 |
| 主体标识 | 服务端从会话得出；空表示匿名 |
| 属性 | 白名单键与取值域，整份读写 |

**事件没有自然主键，用自增列。** 同一毫秒内的两条相同事件是两条合法记录，用（时间，动作）之类的组合当键会把它们合并成一条。自增列不是图省事，而是承认"每一条都是独立事实"。

**属性整份读写，不拆关联表。** 读侧要么整行取出展示，要么按（上报端，动作，结局）计数，没有任何"按某个属性值反查"的路径。拆表会引入一次 join 与一套写入顺序，换不到当前需要的能力。这与角色权限集合的取舍相同。

**这张表只有保留期，没有"删除"入口。** 行一旦记下就是有效的事实，不存在被撤销的语义；超出保留期的行由**服务端启动时的一次回收**清掉（与过期会话回收同形，见 [identity/session-token.md](../identity/session-token.md)）。保留是**策略而不是正确性**：读取一律带时间条件，一条没被清掉的超窗行不会被任何查询看见。

**与主体表之间不建外键**，理由与绑定表、会话表相同。匿名事件根本没有主体，加外键还会把"合法的空值"变成一个结构错误。

#### skill：技能目录

平台纳管的创作辅助技能：**一份不可变的文件树快照，加说明层与使用记录**。语义见 [../skill/README.md](../skill/README.md)。

| 表 | 一行是什么 | 内容 |
|----|-----------|------|
| `skills` | 一个技能 | 说明层（标题、简介，**原值**，空表示回退）· 来源（仓库两段名、引用、子路径、已同步到的提交）· **当前版本指针** |
| `skill_versions` | 一份不可变快照 | 提交标识 · 从 `SKILL.md` 解析出的 `name` 与 `description` · **文件清单**（路径 → 内容摘要 + 字节数） |
| `skill_tags` | 一个技能的一个标签 | 归一化之后的标签串。建立成表是为了按标签筛选 |
| `skill_images` | 一个技能的一张展示图 | 图标识 · **顺序**（第一张即封面）· 对象键 · 字节数。建立成表是为了有序、可重排，且顺序与对象键无关 |
| `skill_favorites` | 一个主体收藏一个技能 | 主体标识 + 技能标识 |
| `skill_usage_daily` | 一个主体在一天里取用过某个技能 | 日期串 + 最后一次使用的时刻 |

**没有"拥有者"这一列。** 目录是部署级的：技能不属于任何主体，谁能看见由权限码表达、不由归属表达（见 [../skill/README.md](../skill/README.md) 的"归属与权限"）。纳管是谁做的只进留痕。

**来源分开存两段名字，而不是一个地址串**：地址串的形状规则将来若变，存量行不会因此解析不出来；而取字节的地址由这两段现拼，不存在"存进去的地址与用出去的地址不是一回事"这条缝。

**文件清单是版本行上的一列，不拆子表。** 它从来是整份读写的——校验、取用与界面上的文件列表都要整棵树，没有"按某一条路径反查版本"的查询。整份读写在一列上是一次赋值，在一组子行上却要先删后插，而"删到一半"会留下一个库里有、内容不全的版本。

**字节不在这五张表的任何一张里。** 内容对象按内容摘要存放在对象存储的私有区，且**跨技能共享**（键上不带技能标识）——因此删除一个技能只删行：同一份字节可能正被别处引用，而"哪些对象还在被引用"要一次全量对账才答得上来（与 galaxy 的孤儿对象回收合并处理）。

**使用量按（技能，主体，日期）归并成一条，而不是一次取用一条。** 一次取用通常连着取好几个文件（正文加它引用的说明），按次记的数字主要由"这个包有几个文件"决定，与"有没有人在用"无关。归并之后行数有天然上界（技能数 × 主体数 × 天数），"最近 30 天有多少人在用"是一次分组计数。这张表**只增不减，靠保留期回收**，与客户端事件同形：回收在服务端启动路径上做，读取本来就带时间窗。

**日期用日期串（`2006-01-02`）而不是时间戳。** 时间戳在两种后端之间的时区处理并不一致（一种带时区存储、一种不带），而"哪一天"这个判据不该取决于库里怎么存。日期串是它实际的含义，也顺带让"早于某天"成为一次字典序比较。

#### 迁移版本表

记录库结构已经演进到哪一步：每个已应用的迁移一条记录，标识唯一。

它由迁移机制自己维护，业务代码不读写它。

### 连接串

#### sqlite

取值有两种形态，按形状自动区分：

| 形态 | 判据 | 行为 |
|------|------|------|
| 文件路径 | 不含 `?` 且不以 `file:` 开头 | 按它定位数据库文件，并补上默认的底层参数 |
| 完整连接串 | 含 `?` 或以 `file:` 开头 | 原样使用，不补任何参数 |

默认补上的三个参数及其理由：

| 参数 | 作用 | 为什么是默认值 |
|------|------|--------------|
| 等待锁的超时 | 遇到写锁时等待而非立刻报错 | sqlite 只有一个写者；不设它，一次并发写会直接变成一个失败请求 |
| 预写日志 | 读写不互相阻塞 | 默认的日志模式会让读操作阻塞在写事务上 |
| 外键约束 | 启用外键检查 | 本模块不建外键，但底层默认关闭会让**将来**加上的外键静默失效——静默失效的约束比没有约束更糟 |

路径的**父目录必须存在**。不自动创建目录：自动创建会让一个拼错的路径变成"在这个奇怪的地方建了个空库"，而数据看起来全丢了。宁可拒绝启动。

路径本身**不能指向一个已存在的目录**。这一条不查也能跑到第一次查询才失败，但那时错误来自底层驱动，只会说"打不开数据库文件"，不会提示"你把目录当成了文件"。配置错误应该在配置这一层被说清楚。

文件路径的解析基准与配置文件一致（启动时的工作目录），见 [../config/README.md](../config/README.md)。

#### MySQL

取值是完整的连接串，原样使用。本模块不解析、不拼接、不补默认参数——MySQL 的连接串已经有成熟且被广泛理解的形态，在其上再叠一层默认值只会让"为什么连到了别处"更难回答。

### 数据来源的唯一性

**同一份事实只能有一个存储位置。** 具体地：

- 角色、主体、绑定只存在于数据库。服务端**不再**持有这些数据的第二份可写副本；进程内不保留跨请求的状态副本。
- **会话与身份别名同理**：已签发的会话只在数据库。进程内内存实现只用于测试，不得在生产装配路径上出现——两份可写副本意味着一次撤销可能只落到其中一份上，而"撤销了但仍然能用"是认证里后果最重的一类错。身份别名更是如此：两份可写副本意味着同一个人可能被解析成两个主体，而这正是本模块要消灭的那件事。
- **档案同理**：档案行只在数据库；进程内不保留跨请求的状态副本。头像字节的唯一位置是对象存储，库内只存对象键，两者**不互为副本**——键失效时表现为"没有头像"，而不是"两份数据不一致"（见 [../profile/avatar-storage.md](../profile/avatar-storage.md)）。
- **galaxy 的工程、草稿、版本与发布记录同理**：只在数据库，且**库内只有清单与元数据，不含任何字节**。字节（文本条目的内容对象与资产的字节）的唯一位置是对象存储的私有区，库内只存路径、摘要与媒体类型；**公开区是媒体的第二份存放位置，但与私有区不互为副本**——它们服务两条不同的下发路径（编辑态与发布态），撤回发布不影响私有区，删除私有资产也不影响已发布的页面（见 [../galaxy/asset-library.md](../galaxy/asset-library.md) 与 [../galaxy/publication.md](../galaxy/publication.md)）。
- **技能目录同理**：技能、版本、标签、收藏与使用日次只在数据库；技能内容的字节按内容摘要存放在对象存储的私有区，库内只存路径与摘要。
- **发布的产物清单只存在于发布表**：对外地址按它分派，而不是每次请求重新计算。清单不得有第二处可写副本；它指向的对象是按内容摘要寻址的不可变对象，因此不需要副本。
- 读取一律走 `rbac.Store`。任何模块想直接查库都必须先回到这个抽象上加方法，而不是绕过它自己写查询。认证模块的会话与身份别名读取同理，走它自己的存储抽象；个人档案的读取走它自己的。
- 内置角色的**定义**来自权限目录（唯一信源），**绑定关系**来自数据库。两者冲突时以数据库为准——那正是"部署时可调整"的含义。

## 边界与约束

- 表结构变更一律通过追加迁移完成，不在业务代码中建表或改列。
- 本模块不定义任何与**权限判定**有关的列：判定所需的一切都是角色、主体、绑定三类事实的组合。
- **不存放口令，也不存放任何凭证的原文。** 会话以**摘要**存放（见下）：拿到库的人拿到的是摘要，不是可以直接拿去用的凭证。这是"库被读到不等于凭证被拿走"这条性质的落点，也是本节唯一一处为认证模块开的存放许可。
- 认证模块与个人档案模块的表与 RBAC 的表**同样在本文件声明、由同一套迁移推进**。表结构与迁移机制是全库共用的基础设施，各模块只拥有自己的表；不存在第二处建表入口，也不存在第二套迁移清单。galaxy 的五张表同此。
- 主体的标识是"已确认的一方"，不是"如何确认这一方"。**会话表**因此只记录这次确认的结果（谁、到什么时候为止），不记录确认的方式；"这个主体有哪些进入方式"是**另一类事实**——它是一条映射（身份别名表），既不是主体的属性，也不是一次确认的留痕，所以既不落在主体表上，也不落在会话表上。
- **身份的归属只有一处决定**：登录时的查-或-建，以及已登录主体对自己发起的绑定（见 [../identity/identity-linking.md](../identity/identity-linking.md)）。没有任何一列、也没有任何一次判定读邮箱或显示名来决定"这个身份是谁"——那会引入一条能被渠道侧改名或回收直接改写的权限路径。

## 可验证性与长程执行

**非长程任务。** 表结构与连接串的解析都是确定性的同步过程，没有中间状态。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 表与列符合约定 | 迁移后比对冻结的结构快照（`internal/database` 测试） |
| 绑定唯一性由库保证 | 同一 `(主体, 角色, 作用域)` 重复写入后表内仍只有一条记录（`internal/rbac/gormstore` 测试） |
| 身份唯一归属由库保证 | 同一个 `(身份来源, 身份标识)` 指向第二个主体时写入失败，表内归属不变（`internal/identity/gormstore` 测试） |
| 一个主体可有多个身份 | 同一主体下写入两个不同来源的身份后都能读回，且都指向该主体（`internal/identity` 测试） |
| 主体标识与渠道无关 | 同一个主体先后用两个渠道登录，读回的主体标识相同；换渠道不改主体标识（`internal/identity` 测试） |
| 未登记主体视为不存在 | 对未登记主体的绑定查询返回"主体不存在"这一类别（契约测试） |
| 会话原文不入库 | 直接读会话表，任何一列的值都不是签发出去的凭证本身（`internal/identity` 测试） |
| 过期会话即失效 | 过期行存在时用它认证失败，且失败类别是"未认证"（契约测试） |
| 会话撤销立即生效 | 撤销后同一凭证的下一次请求被拒（契约测试） |
| 内存实现与 SQL 实现同结果 | 同一套会话用例在两个实现上得到相同的结论与错误类别（契约测试） |
| 连接串两形态区分正确 | 路径形态补参数、连接串形态原样（`internal/database` 测试） |
| 口令不外泄 | 含口令的连接串不出现在任何脱敏摘要与错误信息中（`internal/database` 测试） |
| sqlite 父目录缺失即拒绝 | 指向不存在目录的路径导致启动失败，而不是新建一个空库（`internal/database` 测试） |
| 档案行惰性创建 | 写入之前读该主体返回"档案不存在"，写入之后才出现（`internal/profile/gormstore` 契约测试） |
| 昵称无唯一约束 | 两个主体写入同一昵称都成功，表内两条记录各自独立（`internal/profile/gormstore` 契约测试） |
| 头像字节不入库 | 表里没有承载字节的列（`internal/database/migrate` 结构快照），行内只有对象键（`internal/profile/gormstore` 契约测试） |
| 工程表不带清单 | 工程行上不存在承载草稿、版本或发布清单的列，也没有发布指针与形态列（`internal/database/migrate` 结构快照） |
| 槽行即启用 | 读工程返回的内容槽集合与内容槽表里的行一一对应，工程行上不重复存一份（`internal/galaxy/gormstore` 契约测试） |
| 发布指针按槽分开 | 发布一个槽只改它自己那一行的指针，另一个槽的行逐字不变（`internal/galaxy/gormstore` 契约测试） |
| 工程名称无唯一约束 | 两个工程写入同一名称都成功，表内两条记录各自独立（`internal/galaxy/gormstore` 契约测试） |
| 草稿行惰性创建 | 写入之前读该槽返回"草稿不存在"，写入之后才出现；另一个槽不受影响（`internal/galaxy/gormstore` 契约测试） |
| 版本清单写入后不可改 | 对已保存版本发起修改不改变表内清单（`internal/galaxy/gormstore` 契约测试 + `internal/galaxy` 测试） |
| 清单即分派依据 | 清单的每一条写明条目类别；被引用资产集合由它直接得出，发布态按它分派（`internal/galaxy` 测试） |
| 序号可空洞 | 删除中间一个版本后，其余记录的序号不被重排（`internal/galaxy/gormstore` 契约测试） |
| 序号在槽内递增 | 两个槽各自的第一个版本序号都是 1，互不干扰（`internal/galaxy/gormstore` 契约测试） |
| 字节一律不入库 | 六张表里没有承载字节的列；文本条目与资产都只留路径与摘要（`internal/database/migrate` 结构快照） |
| 资产不可变 | 同一资产标识重复读回摘要与媒体类型不变；接口面上无修改入口（`internal/galaxy/gormstore` 契约测试） |
| 产物清单可按键读回 | 用发布标识能读回产物清单，且与写入时逐字相同（`internal/galaxy/gormstore` 契约测试） |
| 撤回不删发布记录 | 撤回后内容槽行的指针为空，发布记录仍在且可读回（`internal/galaxy/gormstore` 契约测试） |
| 引用集合由清单决定 | 同一清单里的资产条目集合在草稿与各版本上一致（`internal/galaxy` 测试） |
| 迁移无损 | 以旧形状（工程行带形态与发布指针）造数据后跑迁移，每个工程得到与它原来形态对应的一个槽，存量草稿、版本、发布与凭证都被盖上那个槽，且清点前后数量一致（`internal/database/migrate` 测试） |
| 保留段的影响面被记录 | 迁移在 `site` 形态的存量清单里遇到以 `docs/` 为首段的路径时留下一条记录，而不是静默（`internal/database/migrate` 测试） |
| galaxy 的表同样受管 | 六张表出现在同一份冻结快照中，且 `internal/galaxy` 不自行建表或迁移（快照测试 + 代码审查关卡） |
