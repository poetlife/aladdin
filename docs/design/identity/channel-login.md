# 身份认证 — 渠道登录

> 本文件是"一个人如何通过某个外部渠道登录进来"的**唯一信源**中与渠道无关的那部分。各渠道自身的校验要求见 [google-login.md](google-login.md) 与 [github-login.md](github-login.md)。

## 背景与目标

Web 前端需要一种"人可以直接用"的登录方式：不需要管理员预先为每个人发放令牌，也不需要 aladdin 自己维护一套口令。用已有的外部账号登录满足这一点——组织里每个人已经有账号，认证过程由该渠道完成。

本文件描述**所有渠道共有**的那部分行为：登录流程的形状、从渠道凭证到主体的确定方式、新主体的权限、以及渠道清单如何下发给客户端。单个渠道各自如何校验凭证，不属于本文件。

成功的衡量标准：

1. 主体标识由 aladdin 分配，跨重启、跨部署稳定，且**与登录渠道无关**。同一个人两次登录不会变成两个主体；同一个人用两个渠道登录、并把第二个渠道绑上之后，仍然是同一个主体。
2. "未认证"与"无权限"永远是两个可区分的结论，三端都不会把前者当后者处理。
3. 首次登录一个没有任何角色的主体是**成功**的：他拿到会话，只是什么都做不了，界面是空的。这是预期路径，不是错误路径。
4. 客户端不需要硬编码"有哪些登录方式"：渠道清单由服务端下发，未启用的渠道在客户端根本不出现。
5. 凭证本身不出现在日志、错误信息与 `--debug` 输出中。

## 模块边界

| 问题 | 归属 |
|------|------|
| 你是谁 | [identity/](README.md) |
| 某个渠道的凭证怎么校验 | 该渠道的子模块（如 [google-login.md](google-login.md)） |
| 多个渠道怎么归到同一个人 | [identity-linking.md](identity-linking.md) |
| 登录成功后签发的凭证 | [session-token.md](session-token.md) |
| 你能做什么 | [../rbac/](../rbac/README.md) |

**本模块只回答"你是谁"。** 它产出的是一份"这个主体是谁、到什么时候为止有效"的事实，交给 RBAC；它不读角色、不算权限、不参与任何一次放行判定。

两个方向上的边界都要守住：

- **不代替 RBAC 发权限。** 新主体的默认权限是**零**；唯一能让它非零的是注册策略里那份默认角色，而那是一条管理面的记录、写下的是一条真实的角色绑定，判定路径仍然只读那张表（见 [registration.md](registration.md)）。登录路径本身没有任何"首次登录送一个角色"的逻辑——那会让"谁能拿到什么"这件事出现第二个来源。
- **不代替 RBAC 做判定。** 本模块只回答"这份凭证是不是真的、代表谁、过期没有"，回答不了"他能不能删这个角色"。

主体登记的归属在这里，不在授权面：[schema.md](../persistence/schema.md) 明确"主体的**登记**属于认证流程，不属于授权面"。因此登录流程会把确认过的主体写进主体表——这是授权面刻意不做、留给本模块做的那一步。

## 功能行为

### 渠道凭证的到达方式

**目前接入的渠道都是重定向型**：渠道把**浏览器**重定向回服务端的一个端点，凭证（授权码）由渠道直接交给服务端，客户端从不经手。

| 形态 | 凭证如何到达服务端 | 本仓库的渠道 |
|------|------------------|------------|
| **重定向型** | 渠道把浏览器重定向回服务端的一个端点，凭证由渠道直接交给服务端 | Google、GitHub |

> Google 曾经是**搬运型**——浏览器内的第三方登录控件返回一份自证身份的凭证，由前端交给服务端的登录接口。那条路已经**整体去掉**：它要求登录页嵌入并加载第三方控件，而控件的观感（圆角、字号、明暗）不受本站控制；同时它给同一条渠道留下了第二个信任面。现在这个仓库里没有搬运型的渠道。

这个差别只在**凭证如何到达**：从哪里来、谁经手、要不要额外凭据（如客户端密钥）。一旦凭证到达服务端，后续完全相同——校验、解析主体、登记、签发会话，**只有一份实现**（见 [internal/identity/channel.go](../../../internal/identity/channel.go) 的 `TokenVerifier`：它只接受"一份凭证"，返回"一个身份或者一个拒绝理由"，不关心凭证是怎么来的）。

**不为没有的形态保留代码路径。** 将来若真接入一个搬运型渠道，按同一个接口接上即可；现在就为它留一个没人走的入口，等于凭空多一个需要被审计、被测试、被记住的信任面。

**重定向型多出来的约束**：凭证的到达是一次跨站浏览器导航，因此渠道方与 aladdin 之间必须就"这个凭证是为哪一次登录签发的"达成一致，否则任何人都能把自己账号的凭证塞进别人的浏览器，让受害者被登进攻击者的主体。这条防护由渠道子模块描述。

**凭证由谁传递，不改变它的可信度从哪来。** 任何形态下，凭证的可信度都只来自服务端校验，客户端的任何字段都不参与信任决策。客户端拿不到、也不需要知道如何校验——它没有能力伪造一份能通过校验的凭证。

### 登录流程

1. 客户端向服务端询问当前启用了哪些登录方式。
2. 服务端回答**已启用的渠道清单**（只有渠道来源标识）。**未启用的渠道不出现在清单里，客户端也就不渲染对应入口**——不是渲染了再报错。
3. 用户选择一个渠道：浏览器导航到服务端为该渠道准备的**起点端点**，服务端把它交给渠道，渠道再把浏览器送回服务端的**回调端点**（端点的取值与要求见各渠道子模块）。
4. 服务端校验凭证（要求见各渠道子模块），从中解出身份来源与不可变标识。
5. 服务端解析出对应的主体——未命中则登记一个新主体（见下），然后签发会话凭证并交付客户端。

第 5 步是渠道之间**共用的那一段实现**。交付方式上多一步：服务端把浏览器送回前端，会话凭证随这次跳转一并交回（具体形式见渠道子模块）。

### 身份的识别与主体登记

**一个渠道上的身份只由该渠道签发的不可变标识确定，绝不由邮箱或用户名确定。**

这是本模块最硬的一条。理由不是洁癖：

- 邮箱与用户名在认证服务侧**可改名、可回收**。今天 `zhang@example.com` 是张三，明天张三离职、账号回收、分给了李四——同一条字符串指向了另一个人。以它确定身份，这一天就是一次**无痕提权**：李四登录进来，直接继承了张三的全部角色绑定，而系统里没有任何一步记录了这个交接。
- 不可变标识在认证服务侧**唯一且永不复用**，回收账号也不会把它发给别人。

识别是**确定性**的：同一个渠道上的同一个不可变标识永远解析到同一个主体，两次登录不会产生两个主体。这个"同一个主体"由**身份别名表**保证：登录时按（身份来源，不可变标识）去查，命中即用其指向的主体；未命中才分配一个新主体，并记下这条对应关系。表结构与不变式见 [../persistence/schema.md](../persistence/schema.md)。

**主体标识本身不由渠道标识拼接而成，也不含任何渠道取值。** 它是 aladdin 内部的一条规范标识，分配即冻结、永不复用。理由是模型上必须能表达"一个人有多个渠道"——把渠道信息编进主体标识，等于替这个人选定了一个渠道；而"一个人两个渠道登录进来是同一个主体"恰恰是要支持的（见 [identity-linking.md](identity-linking.md)）。

**身份来源记在身份上，不记在主体上。** 这样两个来源的身份各归各位、不会撞到一起：同一个不可变标识字符串在两个来源下是两个不同的身份。这也让"一个人在不同渠道上有不同的可读标识"成为一件可表达的事。

渠道给出的可读标识（邮箱、登录名）**可以**被记录用于展示与排障（"这个主体是谁"），但它记在那个身份上，**不参与任何判定**，也不参与身份的确定。

### 新主体的默认权限

**缺省是零。** 首次登录成功后：

- 主体被登记进主体表，并记下这个渠道身份与它的对应关系；
- **没有任何角色绑定**；
- 默认作用域为空，会话权限集合为空。

用户能登录、能看到界面框架、能看到自己的标识，但什么都点不了。这是**预期行为**，登录页与空白界面上的文案要说清楚这一点，否则第一个接入的人会以为登录坏了。

**唯一的例外是注册策略指定了一份默认角色**，见 [registration.md](registration.md)。那是**管理面的一条记录**、不是配置项：注册时写下的是一条真实的角色绑定，判定路径只读那张表，改策略不改变任何一次判定结果（与 [AGENTS.md](../../../AGENTS.md) 第 7 条的引导例外同一条判据——配置是初始化的输入，不是判定的输入）。默认角色不能是一个能授予角色或改写注册策略的角色。

**登录流程自己不做这个决定。** 它把"这是一次新登记"这件事交给注册策略，登记与授予的落点见 [registration.md](registration.md) 的"闸门落在哪一步"。登录路径里没有一行代码判断"该给这个新主体什么角色"。

**换一个渠道登录不会拿到已有主体的权限。** 用一个新渠道首次登录，登记的是一个**新主体**，看到的是那个新主体的权限（通常为空），而不是"我原来那个账号"。让两个渠道通向同一个主体是 [identity-linking.md](identity-linking.md) 的绑定动作，登录本身不做归并——登录遇到未知身份只会建新的。界面必须说明这一点，否则表现为"我的权限丢了"。

**后续绑上别的渠道也不会带来权限。** 归并改变的是"哪些渠道通向这个主体"，不是"这个主体有什么权限"——两条路径都不经过角色。

把它做成"首次登录自动获得某个角色"——由**登录路径自己**决定给什么——等于让认证流程成为权限的来源——那正是 [AGENTS.md](../../../AGENTS.md) 第 7 条禁止的事情。需要给某个人权限，是管理员显式授予一次角色的动作；要给出**所有**新主体一份默认角色，是管理员改一次注册策略的动作，两者都写在管理面上、都落到同一张绑定表上（见 [registration.md](registration.md)）。

### 第一个管理员

系统里还没有任何角色绑定时，"第一个管理员从哪来"是一个真实的问题：此时没有任何人有权授予自己角色。

它由**引导配置**解决——在配置里指定一个主体标识与作用域，系统在首次启动且存储为空时据此建立第一条绑定。引导的边界与四条性质见 [AGENTS.md](../../../AGENTS.md) 第 7 条与 [../config/server-config.md](../config/server-config.md)。

引导值取的是**主体标识**，或**已登记身份的邮箱**。

邮箱那条是引导专属的窄口子：它只在该邮箱恰好命中一个已登记身份时生效，命中 0 个或多个一律拒绝启动（同一个邮箱字符串可以分别挂在两个身份上，见上文的"绝不由邮箱确定"）。它**不是**"身份可以按邮箱确定"的先例——登录与绑定两条路径仍然只认不可变标识，邮箱在任何一次判定里都不参与，那两个子模块的行为一字未变。

两种写法都要求**先有一次真实登录**，因为主体是在那一刻分配的。登录后主体标识界面上就显示（侧边栏账号区与首页各一处），取到它的操作步骤见"可验证性"一节。

### 渠道的启用与下发

**一个渠道"未启用"是一个明确的状态，不是一个宽松的实现。** 未配置该渠道所需的取值时，那条登录路径整体缺席：客户端拿不到它、也就不渲染入口；即使有人直接构造请求打过来，服务端也回答"这条路没开"，而不是"凭证无效"——把配置缺失说成凭证问题，会让排障的人去查客户端拿的是什么凭证。

**客户端不硬编码渠道清单。** 有哪些登录方式由服务端下发，客户端只据此渲染。客户端自己维护一份清单会与"实际启用了什么"有两个来源，而它们迟早会漂移，表现为"界面上有个入口，点了一直报错"。

清单里只出现**公开**取值，且只有**来源标识**：渠道的客户端标识由服务端持有、直接交给渠道，客户端拿它没用（所有渠道都是重定向型：入口只是一个指向服务端起点的导航）。下发一个客户端用不上的值，只会多一处"看起来该用它"的地方。

**注册模式随同一份清单下发**（见 [registration.md](registration.md)）：登录页要能说明白"这里需要邀请码"或"这里不接受新账号"。它同属公开取值——本来就会展示给任何一个打开登录页的人。

### 浏览器来源白名单

允许发起登录的浏览器来源（协议 + 主机 + 端口）**只配置在渠道侧的控制台，仓库里没有对应的配置项，也不应该有**；渠道那边还要登记**回调地址**（把浏览器送回来的那个端点，见 [google-login.md](google-login.md) 与 [github-login.md](github-login.md)）。

理由是它不改变 aladdin 的任何行为：来源不匹配时请求根本到不了服务端。在 aladdin 侧再放一份，只会得到一份**永远不会被读到、却会在迁移部署时被误改**的副本。

因此部署到新域名时，改的是渠道控制台，不是 aladdin 的配置文件——这一条要写进部署说明，否则表现为"换了域名之后登录按钮点了没反应"。

## 边界与约束

本模块**明确不处理**：

- 会话凭证本身的签发与失效：见 [session-token.md](session-token.md)。
- 主体拿到会话之后能做什么：[../rbac/](../rbac/README.md)。
- 渠道控制台的申请与配置：这是部署动作。

约束：

- **渠道凭证绝不进入日志、错误信息与 `--debug` 输出。** 它与口令同级——它是一次登录的全部凭据。排障时需要的是主体标识与拒绝原因，不是凭证本身。
- **校验清单只有一份。** 绑定一个新渠道时要校验的项与登录完全相同，复用同一个校验器（见 [identity-linking.md](identity-linking.md)）；为绑定另写一套会让"哪条路径校验得更松"变成一个只能靠比对代码来回答的问题。
- **身份的归属只有一处实现。** 登录时的查-或-建是其中一个入口，绑定时写入别名是另一个；任何"按邮箱匹配一下"的便利写法都不得参与。
- **校验实现不得自行解析凭证。** 用成熟的、经过审计的校验库完成签名与声明校验；自研实现漏掉一条声明的概率远高于它带来的收益。
- **校验过程不得依赖调用方提供的任何参数来决定信任什么。**

## 可验证性与长程执行

**非长程任务。** 一次登录是一个同步的即时判定，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 身份解析稳定 | 同一个（来源，不可变标识）连续登录两次得到同一主体标识（`internal/identity` 测试） |
| 身份识别不随展示值变化 | 同一个不可变标识配不同展示值登录，得到同一主体；两个不同身份配同一展示值，得到两个主体（`internal/identity` 测试） |
| 多次登录不重复登记 | 同一个身份登录两次后主体表只多出一条记录（`internal/identity` 测试） |
| 拒绝类别正确 | 所有校验失败都返回"未认证"，**不是**"无权限"（端到端测试） |
| 新主体零权限 | 首次登录成功后该主体的绑定列表为空、会话权限集合为空（端到端测试） |
| 新渠道不继承旧主体权限 | 用一个未绑定的新渠道登录，得到的主体与已有主体不同（端到端测试） |
| 未启用时这条路整体缺席 | 渠道不在下发清单里；直接访问该渠道的起点端点返回"没找到"而不是"凭证无效"（`internal/server` 测试 + `make test-web`） |
| 清单只含已启用渠道 | 未配置取值的渠道不出现在下发清单中（`internal/server` 测试） |
| 渠道之间共用同一段流程 | 每个重定向型渠道跑**同一组**端点行为断言（`internal/server` 测试），且登录/绑定的登记与签发结论一致（端到端测试） |

测试**不得联网**：校验器藏在一个接口后面，测试注入一个用测试自己生成的密钥签发的假实现，覆盖上表每一条。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 配置模块 | 消费各渠道所需的取值；不自行读取来源（见 [../config/server-config.md](../config/server-config.md)） |
| RBAC 模块 | 登记主体（认证流程的职责）；不读取角色、不参与判定（见 [../rbac/role-model.md](../rbac/role-model.md)） |
