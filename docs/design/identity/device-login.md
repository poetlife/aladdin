# 身份认证 — 命令行的设备码登录

> 本文件是"**没有浏览器的终端如何以某个人的身份登入**"的功能行为唯一信源。登录之后能做什么属于 [../rbac/](../rbac/README.md)，签发出的凭证本身见 [session-token.md](session-token.md)。

## 背景与目标

命令行此前只有一条进入方式：管理员发放一份**机器凭证**。它服务机器是对的，服务人不对——它答不了"这次改动是谁做的"，因为系统里根本没有这个人。而终端起不了浏览器回调，[channel-login.md](channel-login.md) 的两条到达方式都用不上：搬运型要一个能跑渠道登录控件的浏览器，重定向型要一次浏览器导航。

设备码流程补的就是这一段：终端上打印一个短码，人在**自己已经登录的浏览器**里确认，终端随后拿到一份属于这个人的会话凭证。

**它不是渠道登录，这一点必须先说清楚。** 批准者在浏览器里已经是某个主体了，整个过程不引入任何新的渠道身份，因此：

- **不产生身份别名、不登记新主体**——身份识别与登记（[channel-login.md](channel-login.md)）完全不参与；
- 拿到的是一份**已有的**主体的会话，其权限就是该主体当时已有的权限；
- 因此[identity/README.md](README.md) 里原先"CLI 的渠道登录（设备码流程）"的措辞是错的：它借用了渠道登录的舞台，实际落点是会话的签发。

成功的衡量标准：

1. 终端上的人拿到的是**他自己**的身份，而不是一个共享的机器身份。
2. 批准只可能发生在**批准者自己的主体**上：请求里不存在"替别人批准"的形状。
3. 一份短码只交付**一次**；交付之后同一份设备码再也取不到凭证。
4. 一个不属于任何人的短码，无法被用来骗取任何凭证。
5. 设备码、短码与令牌都不出现在日志、错误信息与 `--debug` 输出中。

**本文件不引入任何新的身份语义。** 它不解析渠道凭证、不碰身份别名表、不登记主体，也不给任何主体增删权限。它做的唯一一件事是：把一个**已经认证过的主体**的一份新会话，交给一个正在终端上等待的设备。

## 功能行为

### 两个角色、三段时间

| 角色 | 是谁 | 手里有什么 |
|------|------|-----------|
| 发起方 | 终端上的命令行 | 一份高熵的**设备码**（不可人工输入） |
| 批准方 | 浏览器里已登录的会话 | 一个短、可人工输入的**短码** |

过程分三段，中间隔着一段**等人**的时间：

1. **发起**。命令行向服务端发起一次设备码登录。服务端返回设备码（给命令行）、短码（给人看）、批准页地址、有效期与建议的轮询间隔。命令行把短码与地址**显著地**打印出来。
2. **批准**。人在浏览器里打开批准页，输入短码。页面此时**必须先显示"你正在以哪个账号批准"**，再由人选择批准或拒绝。服务端把这一次批准记在短码上，归属只取当前会话的主体。
3. **交付**。命令行按建议间隔轮询。批准之后的那一次轮询拿到会话凭证与过期时间，此后同一份设备码再也取不到凭证。

**轮询的结果是一个状态，不是一个错误。** 待批准、已批准、已拒绝、已过期是四个明确的取值：把"还没批准"表达成一个错误码，会让"这次轮询失败"与"你未认证"变成同一个结论，而它们该有完全不同的走向——前者该继续等，后者该重新登录。这与 [channel-login.md](channel-login.md) 的"未认证与无权限不得混为一谈"是同一条规矩的延伸。

### 短码的形态

短码是给人读、给人打的，因此：

- **足够短**（一次性输入，不能要求抄一长串）；
- **字母表不含易混字符**（`0` 与 `O`、`1` 与 `I` 之类），大小写不敏感，连字符可有可无；
- **同一时刻服务端不得存在两个相同的短码**——生成时若撞上已存在的短码就重来一次。

设备码相反：**高熵、不可人工输入**，它只需要被命令行保管与出示，因此没有任何可读性要求。

### 为什么只给裸地址、要求手输短码

批准页地址**不含短码**，短码由人在页面上手动输入。这一点是刻意的，不是省事：

终端上显示短码的意义在于**人会去比对**——"页面上显示的这次请求，是不是我刚刚在终端上发起的那一次"。若把短码直接嵌进地址，人会直接点开链接、跳过这次核对。而被跳过的这次核对，正是挡住下面这条攻击的唯一东西：攻击者在自己的浏览器上替**受害者终端显示的短码**按下批准，受害者终端于是拿到**攻击者主体**的会话，此后受害者在这个终端上做的一切都落在攻击者能登录的账号里。

附带的好处是短码不进 URL，因此**不需要**像[重定向型渠道的回调](github-login.md)那样要求反向代理对这条路径不记访问日志。

### 归属：只由批准者的凭证决定

短码只能被**当前已认证的凭证所代表的主体**批准。请求里**没有任何字段可以指定主体**——不存在"替某个主体批准"的形状，正如 [identity-linking.md](identity-linking.md) 里不存在"把身份绑到任意主体"的形状。若存在，任何拿到别人短码的人都能让别人的终端登进自己指定的账号。

批准页必须显示当前账号的展示名。这不是装饰：人在按批准之前要看清楚"我是在以谁的名义批准"，而展示名是这个主体唯一可读的标识。

### 交付恰好一次

- 一份设备码在批准之后**恰好交付一次**会话凭证。第二次轮询不再返回凭证——这与[会话凭证"只交付一次"](session-token.md)的既有性质一致。
- **会话在被交付的那一刻签发**，未交付期间服务端不持有任何明文令牌：待批准的是一个**主体**，不是一个令牌。
- 被拒绝、已过期、从未存在过的短码，对批准方是**同一个结论**（"这次批准不能完成，让命令行重新发起"）。区分它们只会把一次失败的批准变成对"这份短码是否曾经有效"的探测。

### 未批准状态的寿命

- 一次设备码登录有**有效期**（以分钟计），过期即不再被批准、也不再交付。人在终端上看到的提示要说明这一点，否则会对着一个早就失效的短码反复输入。
- 未批准的记录**有上界**：发起设备码登录的接口谁都能调，一张没有上界的表会被打进内存。超时的先清掉，到上界时淘汰最快过期的一条。淘汰的代价是一次进行中的登录要重来。
- 记录**不跨重启**：服务端重启会让进行中的登录作废，重新发起一次即可。为这些分钟级的记录建一张表并写一次迁移不划算。

### 启用与不启用

设备码登录需要服务端知道自己的**对外地址**，用来构造批准页地址。未配置对外地址时这条路径整体缺席：

- 它不出现在下发的登录方式清单里，命令行据此不去发起；
- 即使有人直接构造请求打过来，服务端也回答"这条路没开"，而不是"设备码无效"——把配置缺失说成凭证问题，会让排障的人去查客户端拿的是什么。

这是**启用开关**，不是权限来源：它不决定谁能拿到什么，只决定这条路在不在。

前端**没有指向批准页的入口**：批准页是终端把地址打给人看的，界面上不渲染任何
"去批准"的按钮——终端才是这条路径的起点，在界面上放一个入口只会让人点进一个
手上没有短码的页面。

### 留痕

发起、批准、拒绝、交付各留一条记录，含**主体标识**与结果类别，**不含设备码、短码与会话令牌**。批准这条尤其要落到主体标识上——"谁把自己的会话交给了终端"是这里唯一值得事后回答的问题。

## 边界与约束

本模块**明确不处理**：

- 渠道凭证的校验、身份的识别与主体登记：[channel-login.md](channel-login.md)。
- 会话凭证的签发参数、撤销与回收：[session-token.md](session-token.md)。
- **用设备码做绑定**（让终端把一个新的渠道身份绑到某个主体上）：本文件只做登录。绑定仍然只在浏览器里完成（见 [identity-linking.md](identity-linking.md)）。
- 命令行的安装与升级：见 [../cli/self-update.md](../cli/self-update.md)。

约束：

- **不引入新的身份语义。** 身份别名表、主体登记、空主体认领都不参与；任何"顺手认领一下"的写法都会让这条路径成为第二个身份归属入口。
- **不发放权限。** 交付的会话其作用域是批准者主体既有的默认作用域快照，不是请求里给的、也不是为这次登录新算的。命令行因此也**不接受**声明作用域的开关：给出来就以用法错误拒绝。静默忽略一个"看起来能收窄权限"的参数，会让使用者以为自己按最小权限登录了，实际拿到的是批准者的完整作用域。
- **短码与设备码都不进日志。** 短码能换来一次批准，设备码能换来一份会话，两者都与口令同级。
- **批准页必须显示批准者的身份**，且批准动作必须由人显式触发，不得由页面自动完成。
- **不得提供把短码嵌进地址的形态**（理由见上文）。

## 可验证性与长程执行

**非长程任务。** 一次设备码登录是一个同步的即时判定，不跨阶段推进；三段之间只是等人的时间，服务端不推进任何状态机。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 批准只能落在批准者自己的主体上 | 请求里带任何主体相关字段都不改变归属；以 A 的凭证批准得到的是 A 的主体（`internal/server` 测试） |
| 未认证不能批准 | 无凭证调用批准接口返回"未认证"，且不产生任何记录（`internal/server` 测试 + 端到端测试） |
| 交付恰好一次 | 批准后并发两次轮询，只有一次拿到令牌，另一次拿到非已批准的状态（`internal/server` 测试） |
| 未批准的设备码取不到凭证 | 未批准时轮询只返回"待批准"，不返回令牌（`internal/server` 测试） |
| 拒绝不被当作批准 | 拒绝之后轮询返回"已拒绝"，且永远取不到令牌（`internal/server` 测试 + 端到端测试） |
| 轮询失败不是"未认证" | 未知、过期、已被交付的设备码都以状态表达，不以未认证错误码表达（`internal/server` 测试） |
| 无效短码的结论统一 | 从未存在、已过期、已被交付的短码在批准时给出**同一条**答复（`internal/server` 测试） |
| 过期即不可用 | 超过有效期后同样一份设备码不再被批准、也不再交付（`internal/server` 测试） |
| 短码不重复 | 同时存在的多条记录里短码互不相同（`internal/server` 测试） |
| 未配置对外地址时不提供 | 批准页地址取不到时这条路径不在下发清单里，四个方法（发起、轮询、批准、拒绝）都返回"未实现"而非"设备码无效"（`internal/server` 测试） |
| 会话在交付时签发 | 已批准但未交付期间，服务端不存在与这次登录对应的可用会话（`internal/server` 测试） |
| 不登记主体、不新增身份 | 走完整条流程后主体表与身份别名表没有新增记录（`internal/server` 测试 + 端到端测试） |
| 不发放权限 | 批准者主体零权限时，交付的会话权限集合为空（端到端测试） |
| 短码与令牌不进日志 | 发起、批准、交付的日志里不出现短码、设备码与会话令牌（`internal/server` 测试） |
| 两种协议结论一致 | 同一份设备码登录用 grpc-go 与 Connect 分别走完，得到的结论一致（端到端测试） |

测试**不得联网**，也不依赖任何外部渠道的可用性。

手工验证：

1. 启动服务端与前端，在浏览器登录任一个已启用的渠道。
2. 终端执行 `aladdin login` → 应打印短码与批准页地址。
3. 在浏览器打开该地址、输入短码 → 页面应显示**当前账号的展示名**；批准。
4. 终端应在数秒内打印登录成功并写出凭证文件；`aladdin whoami` 返回的主体应与浏览器当前账号**一致**。
5. 重复一次但在页面上选拒绝 → 终端应以未认证结束，且不写出凭证。
6. 输入一个自己编的短码 → 页面给出与"已过期"完全相同的那条答复。
7. 让一次登录等到过期 → 终端应提示重新发起，且不写出凭证。
8. 去掉服务端配置里的对外地址重启 → 命令行不再打印短码，而是明确说明这条路径未启用。

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 短码输入失败限流（防在线猜码） | 暂不做（**未定**） | 短码空间足够大、且批准需要已认证会话，当前不构成一条可被利用的路径；引入限流会影响多设备同时登录 |
| 批准页显示发起方的设备信息（如 User-Agent） | 暂不做（**未定**） | 纵深防御，帮助人判断"这次请求是不是我这台机器发起的"；需要把发起时的一点上下文带进批准页 |
| 一次登录的会话有效期与批准者会话是否一致 | 与既有会话有效期取值一致（**未定**） | 只影响签发参数，见 [session-token.md](session-token.md) |
