# 身份认证 模块总览

> 本目录是 aladdin **"你是谁"** 这一问题的功能行为唯一信源。实现细节变更只改代码；**登录方式、主体标识的确定、会话凭证的签发与失效**的变更必须先改本目录。

## 背景与目标

aladdin 是前端（React + antd）、服务端（Go + gRPC）、命令行（cobra）三端一体的仓库。RBAC 模块解决了"你能做什么"，但它明确把自己限定在**消费一个已经确认的主体标识**上——[../rbac/README.md](../rbac/README.md) 写着它"不负责登录、口令校验、令牌签发"，[../rbac/enforcement.md](../rbac/enforcement.md) 的判定入口只接受一个已经确定的主体。

这个缺口此前由骨架填着：登录接口只接受一个预先配置好的机器令牌并**原样返回**它。这在一个只服务机器凭证的系统里勉强够用，但它不是认证——没有"确认一方是谁"的过程，只有一次共享密钥的比对。它无法回答"这个请求真的是张三发的吗"，因为它根本没有张三这个概念。

本模块把这块补成真的：**人用外部账号登录 Web 前端，服务端确认其身份、把它对应到一个稳定的主体、签发一份有期限的会话凭证。**

**并非本模块的每一条路径都是渠道登录。** 没有浏览器的终端走的是**设备码流程**：人在自己已登录的浏览器里批准一个短码，终端随后拿到一份属于那个主体的会话。它不解析任何渠道凭证、不产生身份别名、不登记主体——身份语义一个字都没动，只是把一份已有的会话交给终端（见 [device-login.md](device-login.md)）。

成功的衡量标准：

1. 主体标识由 aladdin 分配，跨重启、跨部署稳定，且**与登录渠道无关**。同一个人两次登录不会变成两个主体；同一个人用两个渠道登录、并把第二个渠道绑上之后，仍然是同一个主体。
2. 服务端签发的会话凭证**可撤销**，撤销立即生效，撤销后无需等待任何超时。
3. "未认证"与"无权限"永远是两个可区分的结论，三端都不会把前者当后者处理。
4. 首次登录一个没有任何角色的主体是**成功**的：他拿到会话，只是什么都做不了，界面是空的。这是预期路径，不是错误路径。
5. 凭证本身不出现在日志、错误信息与 `--debug` 输出中。

## 模块边界

| 问题 | 归属 |
|------|------|
| 你是谁 | **本模块** |
| 你叫什么、长什么样（展示信息，不进判定） | [../profile/](../profile/README.md) |
| 你能做什么 | [../rbac/](../rbac/README.md) |
| 主体、角色、绑定、会话存在哪 | [../persistence/](../persistence/README.md) |
| 登录方式与各项配置从哪来 | [../config/](../config/README.md) |

**本模块只回答第一个问题。** 它产出的是一份"这个主体是谁、到什么时候为止有效"的事实，交给 RBAC；它不读角色、不算权限、不参与任何一次放行判定。

两个方向上的边界都要守住：

- **不代替 RBAC 发权限。** 新主体的默认权限是**零**。本模块没有任何"首次登录送一个角色"的逻辑——那会让"谁能拿到什么"这件事出现第二个来源。
- **不代替 RBAC 做判定。** 本模块只回答"这个凭证是不是真的、代表谁、过期没有"，回答不了"他能不能删这个角色"。

主体登记的归属在这里，不在授权面：[schema.md](../persistence/schema.md) 明确"主体的**登记**属于认证流程，不属于授权面"。因此登录流程会把确认过的主体写进主体表——这是授权面刻意不做、留给本模块做的那一步。

**归并也只在这里。** 一个渠道上的身份属于哪个主体，唯一入口是本模块的解析与绑定动作（见 [identity-linking.md](identity-linking.md)）。RBAC 只认主体，既不参与也不感知"这个主体有几个渠道"。

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| Workspace 群组同步为角色 | 暂不做。角色绑定仍由管理员显式授予（**未定**） | 引入一个外部权限来源，需重新审视"配置不得成为权限来源"的同源约束 |
| 邀请码自带角色与范围 | **已决，不做**。邀请码只作准入闸门；进来拿什么由站点策略那一份决定（见 [registration.md](registration.md)） | 会让同一个码既是准入凭证又是权限凭证：泄漏一个码就泄漏它所带的那份权限，且"谁能拿到什么"出现第二个来源 |
| 按渠道分别设注册模式 | 暂不做。一份站点级策略（**未定**） | 策略多一维，管理面与测试面各多一维；不是新机制 |
| 注册审批（先申请、管理员逐个批准） | 暂不做（**未定**） | 是一条与邀请码不同的准入流程，需要"待批准的主体"这一状态 |
| 非空主体上的身份转移（含主体失去全部可用渠道之后的恢复） | 暂不做（**未定**） | 引入一个以他人为目标的动作，必须带权限码；空主体的认领已在 [identity-linking.md](identity-linking.md) 里定下 |
| 会话有效期长度 | 见 [session-token.md](session-token.md)（**未定**） | 只影响签发参数 |
