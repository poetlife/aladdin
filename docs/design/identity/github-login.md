# 身份认证 — 用 GitHub 账号登录

> 登录流程、身份识别与主体登记、新主体的默认权限、渠道的启用与下发等**与渠道无关**的部分见 [channel-login.md](channel-login.md)。本文件只描述 **GitHub 这个渠道特有**的部分。

## 背景与目标

GitHub 是第二个接入的渠道，也是第一个**重定向型**渠道：认证过程由 GitHub 完成，但它交给浏览器的是一个**授权码**，而不是一份自证身份的凭证。（Google 后来也改成了这一形态，见 [google-login.md](google-login.md)；现在这个仓库里的渠道**全是**重定向型，两个渠道走的是同一段流程。）

这个差别带来三件搬运型渠道不需要的东西——本文件逐项定义，Google 那份逐字同构：

1. 浏览器要经过一次**跨站导航**才能把授权码送到服务端；
2. 服务端必须用一份**客户端密钥**去换授权码，因为授权码本身不自证任何东西；
3. 服务端必须能确信"这个授权码是为**这一次**登录签发的"，否则会被用来把受害者登进攻击者的主体。

## 功能行为

### 两个浏览器直连端点

这条路径有两个**面向浏览器**的端点，它们不是 RPC：浏览器导航无法携带请求头，因此它们不经过方法级的鉴权注解体系。

| 端点 | 作用 |
|------|------|
| `/auth/github/start` | 生成一次导航的凭据，把浏览器交给 GitHub。导航可以声明这次是登录还是绑定 |
| `/auth/github/callback` | 接收 GitHub 送回来的授权码，完成登录或产出待绑定凭据，把浏览器送回前端 |

**这两个端点同时服务登录与绑定。** 用途标记由起点导航携带，服务端把它记进一次性导航状态；它不是信任边界——绑定的归属只在导航结束后那次已认证的兑换里决定（见 [identity-linking.md](identity-linking.md)）。

**这两个地址是对外契约的一部分**：`/auth/github/callback` 必须登记在 GitHub 控制台的授权回调地址里，且与 aladdin 配置中的对外源一致（见下）。换域名时要同时改这三处（GitHub 控制台、对外源配置、反向代理规则），漏掉任何一处都表现为"点登录没反应"或"回调 404"。

反向代理必须把这两个路径**转发到服务端**，而不是交给前端静态页面的兜底路由——否则浏览器会拿到一份 HTML 页面，表现为"点了没反应"。它还必须对这两个路径**不记访问日志**：回调请求的地址里带着授权码与凭据，而默认的访问日志格式会把整个请求行原样写进去。这两条都要写进部署说明（见 [../../deploy.md](../../deploy.md)）。

### 一次登录的完整过程

1. 浏览器导航到 `/auth/github/start`。
2. 服务端生成一份**一次性随机凭据**，在服务端记住它，并把它放进一个**浏览器无法被脚本读取**的短期 cookie，然后把浏览器重定向到 GitHub 的授权地址。这一次请求**不携带任何 scope**——只取身份所需的信息不需要任何额外授权范围，多要一项就多一次用户被吓退的机会。
3. 用户在 GitHub 完成授权。GitHub 把浏览器重定向回 `/auth/github/callback`，并在地址中带上授权码与第 2 步那份凭据。
4. 服务端**先比对 cookie 与地址里的凭据**，一致**且这份凭据尚未被用过**才继续（见下）。
5. 服务端用授权码与客户端密钥向 GitHub 换取访问令牌，再用它取回该用户的**不可变标识**与展示名。
6. 之后的步骤与任何渠道相同：解析主体、未命中则登记、签发会话（见 [channel-login.md](channel-login.md)）。
7. 服务端把浏览器重定向回前端，**会话凭证随这次跳转交回**。

### 防止被塞入他人的授权码

第 2 步生成的凭据存在的唯一理由是防住这件事：攻击者完成**自己**账号的授权，拿到一个授权码，然后诱导受害者的浏览器去访问回调地址并带上这个码。若服务端不检查"这个码是不是这次浏览器会话发起的"，它会为**攻击者的主体**签发一份会话交到受害者手里——受害者此后的一切操作都落在攻击者能登录的账号上。

因此：

- 凭据必须由**服务端**生成**并记住**，**不能由客户端生成**。浏览器是直接导航到回调端点的，页面脚本根本没有机会参与；而且按仓库的既有约定，客户端的本地判断不是安全边界。**记住它是单次使用的前提**："这份凭据用过没有"是服务端的事实，cookie 由浏览器保管，回答不了这个问题。
- 凭据由 cookie 承载，cookie 必须**不可被脚本读取**（否则一次脚本注入就能读走它，防护归零），且只在**这两个端点**上有效。
- cookie 必须是 **SameSite=Lax**。回调是一次来自 GitHub 的跨站顶层导航，`Strict` 会让 cookie 恰好在这次导航上不发送，于是每一次登录都会失败。这是本项唯一一处"不改就无法工作"的属性。
- cookie 是否要求加密传输由**对外源的协议**决定，而不是写死：对外是 https 就要求，是本地回环的 http 就不要求。写死会让本地开发无法登录，而放宽会让线上少一道防护。
- 凭据**单次使用**：服务端在回调时把它原子地消费掉，同一份凭据的第二次回调**不再签发会话**——即便 cookie 还在。这一条由服务端自己的记录保证；浏览器在回调后删掉 cookie、渠道方的授权码一次性，都是额外的纵深，不是这一条的实现。
- 凭据有**有效期**，过期即不再被接受；服务端的记录**有上界**（超时的先清掉，到上界时淘汰最快过期的一条），使"发起登录"这个谁都能调的地址不会把服务端内存堆起来。淘汰的代价是一次进行中的登录要重来。记录**不跨重启**：服务端重启会让进行中的登录作废，用户重新点一次即可。
- 比对必须是**常数时间**的，避免通过响应时间逐字节猜出凭据。

**不一致或缺失时不签发任何会话**，把浏览器送回前端的登录页并附一条固定的失败信息。失败信息里不含任何内部细节（哪一步失败、凭据是什么）。

### 换取访问令牌

服务端用授权码、客户端标识与**客户端密钥**向 GitHub 换取访问令牌。

- **失败时 GitHub 仍返回成功状态码**，错误写在响应体里。因此必须**解析响应体**判断是否真的换到了令牌，不能只看状态码——只看状态码会把每一次失败的登录都当成成功，然后在下一步以一次空令牌的请求失败告终，而其表象与真正的原因（授权码已用过、已过期）相距很远。
- 请求头必须显式要求 JSON 响应；不要求时 GitHub 返回的是表单编码，解析会失败。

### 客户端密钥

**它是真密钥，只从环境变量读，没有配置键**，与头像存储的密钥同级（见 [../config/credentials.md](../config/credentials.md)）：

- 放进配置文件就等于让它进入版本库、进镜像、被贴给别人排查问题；
- 它**不进启动日志、不进任何错误信息、不进 `--debug` 输出**，访问令牌同理；
- 它与客户端标识**必须同时给出**：只给其一属于半套配置，**拒绝启动**。半套配置的失败方式既不是"没启用"（界面会渲染一个点不通的入口），也不是"配错了"（启动时就能看见），而是"看起来配好了"，直到有人点了登录才失败。

**已启用与未启用**：客户端标识与客户端密钥缺一即视为未启用——这条路径整体缺席，不出现在下发的渠道清单里，直接访问起点端点也不得发起授权。

**对外源不受这一对约束。** 它有自己的、与渠道无关的用途（[命令行登录](device-login.md)的批准页地址也由它构造），因此**只给出对外源是合法配置**，那时 GitHub 未启用、命令行登录可用。反过来，启用 GitHub 时对外源必填——回调地址与回跳地址都由它构造。

### 取回不可变标识

服务端用访问令牌取回 GitHub 用户信息，从中取出：

- **不可变标识**：GitHub 的用户编号。它**永不复用**，改用户名、改邮箱都不变，是唯一可用的身份键。
- **展示名**：登录名。它**可被改名、可被回收**，因此只用于展示与排障，**绝不参与身份的确定**（理由见 [channel-login.md](channel-login.md) 的"身份的识别与主体登记"）。

用户编号是数值，转换为字符串时必须是**十进制、无填充、与地区设置无关**的形式，否则同一个用户在两次登录里会得到两个身份键。

**取不到用户编号（缺失或为零）判定为"未认证"**，不得退化成用登录名顶上。

**不申请邮箱相关的授权范围。** 用户信息的接口无条件返回身份键与登录名，因此不需要邮箱；而 GitHub 上的邮箱可能被设为不公开，依赖它会让一部分用户进不来，且邮箱本身也不该参与判定。

### 回跳前端

服务端把浏览器送回前端时，会话凭证放在地址的 **fragment** 里，而不是查询串：

- fragment **不会发往服务端**，因此不会进入服务端的访问日志，也不会出现在跳转来源（Referer）里；
- 查询串会进入服务端日志、浏览器历史与 Referer，把一份可直接使用的会话凭证散到多个地方。

**跳转目标只能由配置中的对外源构造，绝不能由请求头推导。** 用请求头（`Host`、`X-Forwarded-Host`）构造跳转目标，等于给攻击者一个把会话凭证送到任意主机、并把浏览器导向任意站点的原语。这是本路径上最要紧的一行。

前端在挂载时读取这份凭证并**立即把它从地址栏抹掉**，再按既有流程使用它。抹掉这一步不能让凭证留在浏览器历史里。

### 绑定到已有主体的两段式

GitHub 的绑定与登录复用上面那两个端点，差别只在用途标记与回调之后的去向。归属语义（绑到当前会话的主体、凭据指身份不指主体、兑换同时要会话与 cookie）见 [identity-linking.md](identity-linking.md)，这里只写 GitHub 特有的部分：

- 起点导航带"绑定"用途；服务端把用途记进一次性导航状态，回调据此分支。
- 回调校验通过后**不登记主体、不签发会话**，而是把已校验的 GitHub 身份记成一份**待绑定凭据**，把凭据写进 HttpOnly cookie，再把浏览器送回前端。回跳地址里**不带凭据**，只带一个固定的结果标记。
- 前端在回调页用**当前会话**发起一次已认证的兑换请求；服务端同时要求该 cookie 与有效会话，缺一即拒。
- 已属于当前主体的 GitHub 身份幂等成功；已属于一个**空主体**（只有这条身份、没有任何角色绑定）时按"空主体认领"把身份移到当前主体，并告诉用户"此前单独登录过、已并入当前账号"；已属于任何**非空**主体时仍拒绝、不转移。
- **待绑定凭据的 cookie 与登录起点 cookie 是两份不同的东西**：前者只用于绑定兑换，后者只用于这次回调的导航校验。两者都必须 HttpOnly，是否要求加密传输都由对外源的协议决定。

### 对外源

服务端需要知道自己的**对外地址**，用来构造交给 GitHub 的回调地址与回跳前端的地址。这是一个配置项，**不是秘密**（它只是一个主机名），因此与客户端标识一样放在配置文件里。

它只在**配置了重定向型渠道**时必填——因为它只服务那些渠道。取值的约束见 [../config/server-config.md](../config/server-config.md)。

## 边界与约束

本模块**明确不处理**：

- 登录流程、身份识别、主体登记与默认权限：[channel-login.md](channel-login.md)。
- 会话凭证的签发与失效：[session-token.md](session-token.md)。
- **把 GitHub 身份绑到已有主体**：归属语义、凭据边界与可验证性见 [identity-linking.md](identity-linking.md)；本文件只描述 GitHub 特有的导航、回跳与 cookie。
- GitHub 控制台的申请与配置：这是部署动作。

约束：

- **客户端密钥、访问令牌与授权码都不进入日志、错误信息与 `--debug` 输出。** 服务端只记主体标识与失败类别；回调地址天然带着授权码与凭据，因此反向代理对这一条路径也不记访问日志（见上文"两个浏览器直连端点"）。
- **授权码换取访问令牌只有一处实现**，启动端点的授权地址构造同理。
- **对外源不得由请求头推导**（见"回跳前端"）。
- 失败一律**不签发会话**，且不向浏览器透露失败发生在哪一步。

## 可验证性与长程执行

**非长程任务。** 一次登录是一个同步的即时判定，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 起点端点把浏览器交给 GitHub | `/auth/github/start` 返回一次跳转，目标含客户端标识与凭据，且**不含任何 scope**（`internal/server` 测试） |
| 凭据不可被脚本读取且只在此路径有效 | 起点端点写出的 cookie 带不可读取属性、作用路径限于该路径（`internal/server` 测试） |
| 凭据随对外源协议决定是否要求加密传输 | 对外 http 时不要求、对外 https 时要求（`internal/server` 测试） |
| 凭据不匹配即拒绝 | 缺失或与 cookie 不符的凭据一律**不签发会话**，浏览器被送回登录页（`internal/server` 测试 + 端到端测试） |
| 凭据单次使用 | 同一份凭据用第二次不签发会话（`internal/server` 测试） |
| 未发出的凭据即拒绝 | cookie 与地址一致、但服务端没有这份凭据的记录时不签发会话（`internal/server` 测试） |
| 凭据超时即失效 | 超时后同一份凭据不再被接受（`internal/server` 测试） |
| 换取失败能识别 | GitHub 以成功状态码返回错误体时判定为未认证（`internal/identity` 测试） |
| 渠道限流不被当成凭证问题 | GitHub 返回 403 / 429 时判定为渠道不可用，而不是凭证无效（`internal/identity` 测试） |
| 不可变标识稳定 | 同一用户的两次登录得到同一身份键；大数值编号不丢精度（`internal/identity` 测试） |
| 缺不可变标识即拒绝 | 用户信息缺编号或编号为零时判定为未认证（`internal/identity` 测试） |
| 不申请额外授权范围 | 授权地址中不含 scope 参数（`internal/identity` 测试） |
| 跳转目标来自配置 | 构造跳转目标时不读请求头（`internal/server` 测试：伪造 Host 不改变目标） |
| 半套配置拒绝启动 | 客户端标识与客户端密钥只给其一、或两者齐备而缺对外源时启动失败，信息里指出缺的是哪一项；**只有对外源**是合法配置（`internal/config` 测试） |
| 密钥不进日志 | 启动日志、错误信息与 `--debug` 输出中不出现客户端密钥与访问令牌（`internal/config` 测试 + 启动冒烟） |
| 密钥不可由配置提供 | 配置文件的键集合里没有承载客户端密钥的键（`internal/config` 测试） |
| 端到端一致 | 两种 RPC 协议（grpc-go 与 Connect）对同一次登录得到的结论一致（端到端测试） |
| 绑定用途不在回调签发会话 | 带绑定用途走完回调后，浏览器拿不到会话凭证，库里也没有新增主体（`internal/server` 测试 + 端到端测试） |
| 失败标记按用途选 | 绑定用途的导航在凭据不符、超时或渠道校验失败时回跳 `github_bind_failed`，登录用途的对应情形回跳 `github_login_failed`（`internal/server` 测试）。凭据**已被兑换过**（重放）时用途已无从判断，按登录标记回跳——这是刻意接受的边界 |
| 绑定凭据不进地址 | 回跳前端的地址里不含待绑定凭据（`internal/server` 测试） |
| 绑定兑换需要 cookie | 缺 cookie、cookie 与凭据不符、或没有有效会话时不产生绑定（`internal/server` 测试） |
| 绑定与登录共用校验器 | 伪造、过期、受众不符的渠道凭证在绑定路径同样失败（`internal/identity` 测试） |
| 回调后的认领走完整链路 | GitHub 身份已属于空主体时，走完回调与已认证兑换后该身份归当前主体，原主体只剩零身份、零角色（端到端测试） |
| 非空主体的 GitHub 身份不被夺走 | 原主体有任何角色或别的身份时，绑定被拒且归属不变（`internal/server` 测试） |

测试**不得联网**：校验器藏在一个接口后面，测试注入一个指向本机假 GitHub 的实现，覆盖上表每一条。

手工验证（需先在 GitHub 建 OAuth App，回调地址填服务端的 `/auth/github/callback`）：

1. 客户端标识与对外源填进服务端配置，客户端密钥进环境变量。
2. 启动服务端与前端 → 登录页应出现 GitHub 入口（未配置时不出现）。
3. 走一次完整登录 → 回到前端应已登录、界面全空（验证"新主体零权限"）。
4. 手工删掉起点端点写下的 cookie 再走完回调 → **不应**登录成功，应带一条失败信息回到登录页。
5. 半套配置（配了客户端标识但缺对外源或客户端密钥）→ **拒绝启动**。
6. 用一个已有主体登录，从个人资料发起 GitHub 绑定 → 应提示绑定成功；随后退出并用 GitHub 登录 → 应得到**同一个主体**，而不是新的零权限主体。
7. 直接打开绑定成功的回跳地址（不带待绑定 cookie）→ **不应**产生绑定，也不应泄露凭据是否曾经有效。
8. 先单独用 GitHub 登录一次（得到零权限主体），再用 Google 登录并在个人资料里绑定 GitHub → 应提示"此前单独登录过、已并入当前账号"；随后用 GitHub 登录 → 应得到 Google 那个主体。

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 授权请求携带 PKCE 挑战 | 暂不做（**未定**） | 纵深防御。授权码单次使用、且换取发生在服务端到服务端之间，因此当前不构成一条可被利用的路径 |
