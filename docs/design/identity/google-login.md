# 身份认证 — 用 Google 账号登录

> 登录流程、身份识别与主体登记、新主体的默认权限、渠道的启用与下发等**与渠道无关**的部分见 [channel-login.md](channel-login.md)。本文件只描述 **Google 这个渠道特有**的部分：凭证是什么、必须校验什么、不能确定什么。

## 背景与目标

用 Google 账号登录是最早接入的渠道。它曾经是**搬运型**：浏览器内的 Google 登录控件（Google Identity Services）返回一份自证身份的**身份令牌**（ID token），由前端原样交给服务端。那个形态有两个直接后果：

- 登录页必须加载并嵌入一份 Google 的第三方控件，**按钮由 Google 画**，它的圆角、字号与边框不受本站主题控制；
- 服务端不需要任何密钥——令牌靠签名自证。

现在这条路径改为**重定向型**，与 [github-login.md](github-login.md) 同构：浏览器被交给 Google，Google 把**授权码**送回服务端的一个端点，服务端用授权码与**客户端密钥**换回令牌。两条动机：

1. **登录入口回到本站手里。** 不再请求 `accounts.google.com` 的脚本、不再嵌入任何第三方控件；入口就是本站主题下的一个普通按钮，暗色下的白底、圆角不一致这一整类问题从根上消失（它们都是"第三方在自己页面里画东西"的后果）。
2. **凭证的到达方式与 GitHub 统一。** 服务端用授权码与客户端密钥换令牌，因此这条路径与 GitHub 一样需要一份真密钥，也一样不必让浏览器经手任何可自证身份的凭证。

**身份模型一个字都没变**：身份来源仍是 Google，不可变标识仍取自**令牌的 `sub` 声明**，校验清单仍是下文的四项。变的只是凭证怎么到达服务端。

## 功能行为

### 两个浏览器直连端点

与 GitHub 同构，同为**面向浏览器**的非 RPC 端点：

| 端点 | 作用 |
|------|------|
| `/auth/google/start` | 生成一次导航的凭据，把浏览器交给 Google。导航可以声明这次是登录还是绑定 |
| `/auth/google/callback` | 接收 Google 送回来的授权码，完成登录或产出待绑定凭据，把浏览器送回前端 |

**这两个端点同时服务登录与绑定**，用途标记的语义、以及"它不是信任边界"这一条与 [github-login.md](github-login.md) 完全相同，见该文件的同名章节。

**这两个地址是对外契约的一部分**：`/auth/google/callback` 必须登记在 Google 控制台的"已获授权的重定向 URI"里，且与 aladdin 配置中的对外源一致。换域名时要同时改三处（Google 控制台、对外源配置、反向代理规则），漏掉任何一处都表现为"点登录没反应"或"回调 404"。

反向代理必须把这两个路径**转发到服务端**，并且**不记访问日志**——回调请求的地址里带着授权码。两条都要写进部署说明（见 [../../deploy.md](../../deploy.md)）。

### 一次登录的完整过程

1. 浏览器导航到 `/auth/google/start`。
2. 服务端生成一份**一次性随机凭据**，在服务端记住它，并把它放进一个**浏览器无法被脚本读取**的短期 cookie，然后把浏览器重定向到 Google 的授权地址。这次请求带上 `openid` 与 `email` 两个授权范围（理由见"申请哪些授权范围"）。
3. 用户在 Google 完成授权。Google 把浏览器重定向回 `/auth/google/callback`，并在地址中带上授权码与第 2 步那份凭据。
4. 服务端**先比对 cookie 与地址里的凭据**，一致**且这份凭据尚未被用过**才继续（与 GitHub 逐条相同：服务端生成并记住、cookie 不可被脚本读取、SameSite=Lax、单次使用、有效期与条数上界、常数时间比对；见 [github-login.md](github-login.md) 的"防止被塞入他人的授权码"——两处是同一套要求，不各写一份）。
5. 服务端用授权码、客户端标识与**客户端密钥**向 Google 换取令牌。
6. 换回来的**身份令牌就是第 5 步的产物**，它走本模块原有的校验（下节），从中解出身份来源与不可变标识。
7. 之后的步骤与任何渠道相同：解析主体、未命中则登记、签发会话（见 [channel-login.md](channel-login.md)）。
8. 服务端把浏览器重定向回前端，**会话凭证随这次跳转交回**（放在地址的 fragment 里，理由与实现要求见 [github-login.md](github-login.md) 的"回跳前端"）。

### 换取令牌

- 向 Google 的令牌端点发起一次 `authorization_code` 换取，带上授权码、客户端标识、**客户端密钥**与回调地址。
- **回调地址必须与授权时给出的逐字一致**，否则 Google 会拒绝这次换取。
- 授权码**一次性**：已用过、已过期、不是签给这个应用的，都表现为换取被拒绝。

**失败必须分成两类：**

| 渠道的回答 | 结论 | 为什么 |
|-----------|------|--------|
| 授权码本身不成立（已用过、已过期、不是签给本应用） | **未认证** | 这是"这次登录不成立"，用户重新点一次即可 |
| 本服务的配置不成立（客户端标识或密钥不对、回调地址与登记的不一致） | **渠道不可用** | 它一次也换不到令牌，表现为"所有人都登不进来"。报成"你的凭证无效"会把排障引向客户端 |
| 传输出错、上游 5xx、限流 | **渠道不可用** | 同上：一次上游故障不该表现成"所有人的凭证都失效了" |

**换取的响应体与错误原文绝不带出去**：里面装着访问令牌与身份令牌，而错误信息会进日志。

### 身份令牌的校验要求

以下每一条都必须成立，缺一不可。**任何一条不满足都判定为"未认证"**，不是"无权限"：

| 校验项 | 要求 | 为什么 |
|--------|------|--------|
| 签名 | 由 Google 公布的公钥验证通过 | 这是"这份令牌确实由 Google 签发"的唯一依据 |
| 签发方 | 属于 Google | 防止拿另一个签发者签的、格式相同的令牌来冒充 |
| **受众** | **等于本服务配置的客户端标识** | 见下，这是最容易被漏掉、后果最重的一条 |
| 有效期 | 未过期 | 过期的令牌不是身份证明 |
| 不可变标识 | 非空 | 它是这个渠道上唯一的身份键；缺了它就查不到对应主体，也就无从确定这是谁 |

**这份清单要保持短。** 只放"不满足就必须拒绝"的项——每多一项，就多一种把合法用户挡在门外的失败方式。下面这条因此被刻意排除在外。

**邮箱与它的验证状态不参与校验。** 令牌里会带上邮箱，我们也会记下来用于展示与排障（记在该渠道的身份上），但**没有任何一次判定读它**——身份完全由不可变标识确定。既然它不参与判定，它的"是否已验证"也就不构成一条准入条件：要求一个没人用的字段，只会在某天把一个合法用户挡在门外，而挡住的原因与他能不能进来毫无关系。

> 注意：这里排除的是"把已校验的邮箱当作身份"。若将来要做"只允许某域名登录"，正确的做法是用 Google 侧的受众配置限制（把受众设为**内部**），而不是在前端或服务端按邮箱后缀放行——后者一旦生效，改邮箱就能改权限。

**受众校验必须做，且必须严格相等。** 身份令牌是签给某一个应用的，`受众` 字段就是"签给谁"。不校验它，就意味着**任何**一个 Google 应用的令牌都能登录 aladdin——包括攻击者自己注册的那个应用的令牌。签名是真的、签发方是 Google、也没过期，唯独不是签给你的。这一条漏掉时，前面四条形成的信任全部失效。

**清单只有一处实现。** 这条路径上"Google 的身份令牌怎么校验"与本仓库此前完全一致：换回来的令牌交给同一个校验器，不因为它是重定向换来的就换一套判断。

### 不需要在浏览器内加载任何第三方脚本

登录页**在用户点击之前不向 Google 发出任何请求**：入口是一个指向 `/auth/google/start` 的普通导航，页面里没有 Google 的脚本、没有它的 iframe、也没有它的按钮。因此：

- 入口的观感（圆角、字号、明暗、悬停）由本站主题决定，与其它按钮一致；
- 不存在"第三方控件比按钮大一圈、露出一层它自己的底色"这类与本站无关的表现问题。

### 客户端密钥

**它是真密钥，只从环境变量读，没有配置键**，与 GitHub 的客户端密钥同级（见 [../config/credentials.md](../config/credentials.md)）：

- 放进配置文件就等于让它进入版本库、进镜像、被贴给别人排查问题；
- 它**不进启动日志、不进任何错误信息、不进 `--debug` 输出**，访问令牌与身份令牌同理；
- 它与客户端标识**必须同时给出**：只给其一属于半套配置，**拒绝启动**。半套配置的失败方式既不是"没启用"（界面会渲染一个点不通的入口），也不是"配错了"（启动时就能看见），而是"看起来配好了"，直到有人点了登录才失败。

**已启用与未启用**：客户端标识与客户端密钥缺一即视为未启用——这条路径整体缺席，不出现在下发的渠道清单里，直接访问起点端点返回"没找到"。

**对外源在启用时必填**：回调地址与回跳地址都由它构造。它本身与渠道无关，只给出对外源（不启用任何重定向型渠道）是合法配置。

### 申请哪些授权范围

只有两项：**`openid` 与 `email`**。

- `openid` 是"换回一份能自证身份的令牌"的必要条件。没有它，换回来的东西确定不了身份。
- `email` 是渠道给出的**可读标识**，用于展示与排障，也是引导按邮箱认领的依据（见 [channel-login.md](channel-login.md) 的"第一个管理员"）。它**不参与任何判定**。

**不申请 `profile` 之类的范围。** 昵称与头像由本仓库的档案模块管理，不从渠道取（见 [../profile/README.md](../profile/README.md)）；多要一项就多一次用户被授权页吓退的机会。

### 取回不可变标识

不可变标识取自**身份令牌的 `sub` 声明**，它**永不复用**，改邮箱、改昵称都不变，是这条渠道上唯一可用的身份键。

**取不到（缺失或为空）判定为"未认证"**，不得退化成用邮箱顶上——那正是 [channel-login.md](channel-login.md) 最硬的一条禁止。

### 回跳前端、绑定到已有主体的两段式、对外源

这三项与 [github-login.md](github-login.md) 的对应章节**逐字同构**，只是把渠道名换掉：会话凭证放 fragment、跳转目标只能由对外源构造（绝不用请求头）、绑定走"回调产出待绑定凭据 + 前端用当前会话兑换"的两段式、失败标记为 `google_login_failed` / `google_bind_failed`。重定向型渠道在这几点上没有渠道差异，因此**不各写一份**。

## 边界与约束

本模块**明确不处理**：

- 登录流程、身份识别、主体登记与默认权限：[channel-login.md](channel-login.md)。
- 会话凭证的签发与失效：[session-token.md](session-token.md)。
- **把 Google 身份绑到已有主体**：归属语义、凭据边界与可验证性见 [identity-linking.md](identity-linking.md)。
- Google 控制台的申请与配置：这是部署动作。

约束：

- **客户端密钥、访问令牌、身份令牌与授权码都不进入日志、错误信息与 `--debug` 输出。** 服务端只记主体标识与失败类别；回调地址天然带着授权码与凭据，因此反向代理对这一条路径也不记访问日志。
- **授权码换取令牌只有一处实现，授权地址的构造同理。** 重定向流程本身（导航凭据、cookie、回跳）与 GitHub **共用同一段实现**，渠道之间只差取值。
- **对外源不得由请求头推导。**
- **不提供"浏览器直接把身份令牌交给服务端"的入口。** 这条路径只有重定向一条：保留一个并行的搬运型入口，等于给同一条渠道留两条信任面，而它没有消费者。
- 失败一律**不签发会话**，且不向浏览器透露失败发生在哪一步。

## 可验证性与长程执行

**非长程任务。** 一次登录是一个同步的即时判定，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 受众校验生效 | 签发方与签名都合法、但受众为另一个应用的令牌被拒绝（`internal/identity` 测试） |
| 其它校验项逐条生效 | 过期的、签发方不符的、签名不符的、缺不可变标识的令牌各自被拒绝（`internal/identity` 测试） |
| 换回来的令牌走同一套校验 | 令牌端点返回一份受众不符的令牌时，登录被拒绝（`internal/identity` 测试） |
| 授权码不成立判为未认证 | 令牌端点回答"授权码不成立"时判定为未认证（`internal/identity` 测试） |
| 配置不成立判为渠道不可用 | 客户端标识或密钥不对、回调地址不一致时判定为渠道不可用，而不是"凭证无效"（`internal/identity` 测试） |
| 上游故障判为渠道不可用 | 令牌端点 5xx、限流、传输失败时判定为渠道不可用（`internal/identity` 测试） |
| 不申请多余范围 | 授权地址只带 `openid` 与 `email`，不含 `profile` 之类（`internal/identity` 测试） |
| 起点端点把浏览器交给 Google | 起点端点返回一次跳转，目标含客户端标识与凭据（`internal/server` 测试） |
| 凭据不可被脚本读取且只在此路径有效 | 起点端点写出的 cookie 带不可读取属性、作用路径限于该渠道的路径（`internal/server` 测试） |
| 凭据随对外源协议决定是否要求加密传输 | 对外 http 时不要求、对外 https 时要求（`internal/server` 测试） |
| 凭据不匹配、未发出、已用过、已超时一律拒绝 | 四种情形都不签发会话，浏览器被送回登录页（`internal/server` 测试） |
| 半套配置拒绝启动 | 客户端标识与客户端密钥只给其一、或两者齐备而缺对外源时启动失败，信息里指出缺的是哪一项（`internal/config` 测试） |
| 密钥不可由配置提供 | 配置文件的键集合里没有承载客户端密钥的键（`internal/config` 测试） |
| 密钥不进日志 | 启动日志、错误信息与 `--debug` 输出中不出现客户端密钥与令牌（`internal/config` 测试 + 启动冒烟） |
| 浏览器不经手任何可自证身份的凭证 | 下发的渠道清单与登录页里没有 Google 的客户端脚本入口；前端不再有搬运型调用（`make test-web`） |
| 没有并行的搬运型入口 | proto 的登录与绑定请求里不存在 Google 的凭证字段（`api/` 与 `make gen` 的产物；端到端测试不再存在该调用） |
| 未启用时这条路整体缺席 | 不在下发清单里；起点端点返回"没找到"（`internal/server` 测试） |
| 绑定用途不在回调签发会话 | 带绑定用途走完回调后，浏览器拿不到会话凭证，库里也没有新增主体（`internal/server` 测试 + 端到端测试） |
| 绑定凭据不进地址 | 回跳前端的地址里不含待绑定凭据（`internal/server` 测试） |
| 绑定与登录共用校验器 | 伪造、过期、受众不符的令牌在绑定路径同样失败（`internal/identity` 测试） |
| 两种渠道共用同一段重定向流程 | 两个渠道各自的用例跑同一组断言（`internal/server` 测试） |

测试**不得联网**：校验器藏在一个接口后面，与 Google 的真实交互由本包的用例指向本机的假令牌端点覆盖；服务端与端到端用例注入一个不做交互的替身。

手工验证（需先在 Google 控制台完成配置）：

1. 建（或改用）一个 **Web 应用**类型的 OAuth 客户端；在"已获授权的重定向 URI"里填 `<对外地址>/auth/google/callback`；受众建议选**内部**，这样只有本组织的账号能登录。不再需要"已获授权的 JavaScript 来源"——本站不再在浏览器内调用 Google。
2. 客户端标识填进服务端配置，**客户端密钥放进 `ALADDIN_GOOGLE_CLIENT_SECRET` 环境变量**。
3. 启动服务端与前端，用 Google 账号点登录 → 应登录成功但界面全空（验证"新主体零权限"）。
4. 从服务端日志里读这次登录的**主体标识**（登录成功那一行带着它）。
5. 手工删掉起点端点写下的 cookie 再走完回调 → **不应**登录成功，应带一条失败信息回到登录页。
6. 从个人资料发起 Google 绑定 → 应提示绑定成功；随后退出并用 Google 登录 → 应得到**同一个主体**。

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 授权请求携带 PKCE 挑战 | 暂不做（**未定**） | 纵深防御。授权码单次使用、且换取发生在服务端到服务端之间，因此当前不构成一条可被利用的路径（与 [github-login.md](github-login.md) 同一结论） |
| 授权请求带 `prompt=select_account` | 暂不做（**未定**） | 每次都让用户选账号，代价是单账号用户多一次点击。当前行为是"已登录的账号直接过" |
