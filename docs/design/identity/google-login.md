# 身份认证 — 用 Google 账号登录

> 登录流程、身份识别与主体登记、新主体的默认权限、渠道的启用与下发等**与渠道无关**的部分见 [channel-login.md](channel-login.md)。本文件只描述 **Google 这个渠道特有**的部分：凭证是什么、必须校验什么、不能确定什么。

## 背景与目标

用 Google 账号登录是最早接入的渠道。它是**搬运型**渠道：浏览器内取得的凭证本身自证身份，服务端独立校验它，不需要向 Google 发出任何请求来确认。

本文件描述这条路径的**行为要求**。

## 功能行为

### 凭证形态

浏览器内的 Google 登录控件在用户完成登录后，向页面返回一份**身份令牌**（ID token）。前端把它原样交给服务端的登录接口；服务端校验它，从中解出身份来源与不可变标识。

**身份来源固定为 Google，不可变标识取自令牌的 `sub` 声明。**

### 身份令牌的校验要求

以下每一条都必须成立，缺一不可。**任何一条不满足都判定为"未认证"**，不是"无权限"：

| 校验项 | 要求 | 为什么 |
|--------|------|--------|
| 签名 | 由 Google 公布的公钥验证通过 | 这是"这份令牌确实由 Google 签发"的唯一依据 |
| 签发方 | 属于 Google | 防止拿另一个签发者签的、格式相同的令牌来冒充 |
| **受众** | **等于本服务配置的客户端标识** | 见下，这是最容易被漏掉、后果最重的一条 |
| 有效期 | 未过期 | 过期的令牌不是身份证明 |
| 不可变标识 | 非空 | 它是这个渠道上唯一的身份键；缺了它就查不到对应主体，也就无从确定这是谁 |

**这份清单要保持短。** 只放"不满足就必须拒绝"的项——每多一项，就多一种把合法用户挡在门外的失败方式。下面这条因此被刻意排除在外。

**邮箱与它的验证状态不参与校验。** 令牌里会带上邮箱，我们也会记下来用于展示与排障（记在该渠道的身份上），但**没有任何一次判定读它**——身份完全由不可变标识确定。既然它不参与判定，它的"是否已验证"也就不构成一条准入条件：要求一个没人用的字段，只会在某天把一个合法用户挡在门外，而挡住的原因与他能不能进来毫无关系。

> 注意：这里排除的是"把已校验的邮箱当作身份"。若将来要做"只允许某域名登录"，正确的做法是用 Google 侧的受众配置限制（把受众设为**内部**），而不是在前端或服务端按邮箱后缀放行——后者一旦生效，改邮箱就能改权限。

**受众校验必须做，且必须严格相等。** 身份令牌是签给某一个应用的，`受众` 字段就是"签给谁"。不校验它，就意味着**任何**一个 Google 应用的令牌都能登录 aladdin——包括攻击者自己注册的那个应用的令牌。签名是真的、签发方是 Google、也没过期，唯独不是签给你的。这一条漏掉时，前面四条形成的信任全部失效。

### 不需要客户端密钥

**客户端标识不是秘密。** 它明文出现在浏览器里，任何人都能读到，这是这类登录方式的设计前提，不是疏漏。因此它可以放在服务端配置文件里，不违反"配置中不得出现凭证"。

**真正需要保密的是客户端密钥，而这条路径不使用它**——服务端靠**签名**而非密钥确认令牌，因此仓库里不存在也不需要这一项。若要新增一个看起来像密钥的配置项来"加强"这条路径，先回答"它防住了什么"，答案通常是不存在的东西。

（这是搬运型渠道共有的性质。重定向型渠道不同：它需要客户端密钥，见 [github-login.md](github-login.md)。）

### 已启用与未启用

客户端标识为空表示**未启用** Google 登录：这条路径整体缺席，不出现在下发给客户端的渠道清单里，直接调用其登录接口回答"这条路没开"。

客户端标识非空即视为启用，服务端据此构造校验器。**不装一个"什么都通过"的实现**——那会让未启用的登录方式变成一个可用的后门。

## 边界与约束

本模块**明确不处理**：

- 登录流程、身份识别、主体登记与默认权限：[channel-login.md](channel-login.md)。
- 会话凭证的签发与失效：[session-token.md](session-token.md)。
- Google 控制台的申请与配置：这是部署动作。

约束：

- **身份令牌绝不进入日志、错误信息与 `--debug` 输出。** 它与口令同级。
- **校验实现不得自行解析令牌**：用成熟的、经过审计的校验库完成签名与声明校验；自研实现漏掉一条声明的概率远高于它带来的收益，而漏掉的那条通常正是受众校验。
- **校验过程不得依赖调用方提供的任何参数来决定信任什么。**
- **不得为了"减少一次网络往返"而跳过提供方公钥的获取**：那一步正是"这份令牌由 Google 签发"的依据。公钥的获取应当是**惰性**的（首次需要时才做），使 Google 不可达不至于让整个服务端起不来——这是一个同时服务 CLI 与机器凭证的权限平台，一个可选登录方式的上游故障不该让它整体不可用。

## 可验证性与长程执行

**非长程任务。** 一次登录是一个同步的即时判定，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 受众校验生效 | 签发方与签名都合法、但受众为另一个应用的令牌被拒绝（`internal/identity` 测试） |
| 其它校验项逐条生效 | 过期的、签发方不符的、签名不符的、缺不可变标识的令牌各自被拒绝（`internal/identity` 测试） |
| 邮箱不参与身份确定 | 同一不可变标识配不同邮箱得到同一主体；不同身份配同一邮箱得到两个主体（`internal/identity` 测试） |
| 未启用时报"未实现" | 客户端标识为空时该渠道不在下发清单中，且其登录接口返回"未实现"（`internal/server` 测试 + `make test-web`） |
| 不需要客户端密钥 | 配置项集合里不存在承载 Google 客户端密钥的键（`internal/config` 测试） |
| 提供方不可达不阻断启动 | 提供方不可达时服务端照常启动，仅该渠道登录返回"服务不可用"（`internal/identity` 测试） |

测试**不得联网**：校验器藏在一个接口后面，测试注入一个用测试自己生成的密钥签发的假实现，覆盖上表每一条。

手工验证（需先完成 Google 侧的申请）：

1. 建项目，配置 Google Auth Platform；建 **Web 应用**类型的 OAuth 客户端；把开发地址加进"已获授权的 JavaScript 来源"；受众建议选**内部**，这样只有本组织的账号能登录。
2. 客户端标识填进服务端配置。
3. 启动服务端与前端，用 Google 账号登录 → 应登录成功但界面全空（验证"新主体零权限"）。
4. 从服务端日志里读这次登录的**主体标识**（登录成功那一行带着它）。

第 4 步是这套设计里唯一一处需要人工搬运的值，也是"主体标识在日志里可检索"这件事的用处所在。
