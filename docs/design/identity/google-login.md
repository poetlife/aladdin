# 身份认证 — 用 Google 账号登录

## 背景与目标

Web 前端需要一种"人可以直接用"的登录方式：不需要管理员预先为每个人发放令牌，也不需要 aladdin 自己维护一套口令。用 Google 账号登录满足这一点——组织里每个人已经有账号，认证过程由 Google 完成。

本子模块描述这条登录路径的**行为要求**：前端拿到什么、服务端必须校验什么、从校验结果里能确定什么、不能确定什么。

## 功能行为

### 登录流程

1. 前端向服务端询问当前启用了哪些登录方式。
2. 服务端回答是否启用了 Google 登录，以及对应的客户端标识。**未启用时前端不渲染 Google 登录入口**——不是渲染了再报错。
3. 用户点击后，前端调起 Google 的登录控件，Google 在浏览器内向页面返回一份**身份令牌**（ID token）。
4. 前端把这份身份令牌原样交给服务端登录接口。
5. 服务端校验它（见下），从中解出身份来源与不可变标识，解析出对应的主体——未命中则登记一个新主体（见下），然后签发会话凭证并返回。

**身份令牌由前端传递，但其可信度不来自前端。** 前端只是个搬运工：第 5 步的校验完全在服务端进行，客户端的任何字段都不参与信任决策。前端拿不到、也不需要知道如何校验——它没有能力伪造一份能通过校验的令牌。

### 身份令牌的校验要求

以下每一条都必须成立，缺一不可。**任何一条不满足都判定为"未认证"**，不是"无权限"：

| 校验项 | 要求 | 为什么 |
|--------|------|--------|
| 签名 | 由 Google 公布的公钥验证通过 | 这是"这份令牌确实由 Google 签发"的唯一依据 |
| 签发方 | 属于 Google | 防止拿另一个签发者签的、格式相同的令牌来冒充 |
| **受众** | **等于本服务配置的客户端标识** | 见下，这是最容易被漏掉、后果最重的一条 |
| 有效期 | 未过期 | 过期的令牌不是身份证明 |
| 不可变标识 | 非空 | 它是这个渠道上唯一的身份键；缺了它就查不到对应主体，也就无从确定这是谁 |

**这份清单要保持短。** 只放"不满足就必须拒绝"的项——每多一项，就多一种把合法用户挡在门外的失败方式。下面这条因此被刻意排除在外。

**邮箱与它的验证状态不参与校验。** 令牌里会带上邮箱，我们也会记下来用于展示与排障（记在该渠道的身份上，见下），但**没有任何一次判定读它**——身份完全由不可变标识确定。既然它不参与判定，它的"是否已验证"也就不构成一条准入条件：要求一个没人用的字段，只会在某天把一个合法用户挡在门外，而挡住的原因与他能不能进来毫无关系。

> 注意：这里排除的是"把已校验的邮箱当作身份"。若将来要做"只允许某域名登录"，正确的做法是用 Google 侧的受众配置限制（把受众设为**内部**），而不是在前端或服务端按邮箱后缀放行——后者一旦生效，改邮箱就能改权限。

**受众校验必须做，且必须严格相等。** 身份令牌是签给某一个应用的，`受众` 字段就是"签给谁"。不校验它，就意味着**任何**一个 Google 应用的令牌都能登录 aladdin——包括攻击者自己注册的那个应用的令牌。签名是真的、签发方是 Google、也没过期，唯独不是签给你的。这一条漏掉时，前面四条形成的信任全部失效。

**客户端标识不是秘密。** 它明文出现在浏览器里，任何人都能读到，这是这类登录方式的设计前提，不是疏漏。因此它可以放在服务端配置文件里，不违反"配置中不得出现凭证"。真正需要保密的是**客户端密钥**，而浏览器登录流程**不使用**客户端密钥——服务端靠签名而非密钥确认令牌，因此仓库里不存在也不需要这一项。若要新增一个看起来像密钥的配置项来"加强"这条路径，先回答"它防住了什么"，答案通常是不存在的东西。

### 身份的识别与主体登记

**一个渠道上的身份只由该渠道签发的不可变标识确定，绝不由邮箱确定。**

这是本子模块最硬的一条。理由不是洁癖：

- 邮箱在认证服务侧**可改名、可回收**。今天 `zhang@example.com` 是张三，明天张三离职、账号回收、分给了李四——同一条邮箱字符串指向了另一个人。以邮箱确定身份，这一天就是一次**无痕提权**：李四登录进来，直接继承了张三的全部角色绑定，而系统里没有任何一步记录了这个交接。
- 不可变标识在认证服务侧**唯一且永不复用**，回收账号也不会把它发给别人。

识别是**确定性**的：同一个渠道上的同一个不可变标识永远解析到同一个主体，两次登录不会产生两个主体。这个"同一个主体"由**身份别名表**保证：登录时按（身份来源，不可变标识）去查，命中即用其指向的主体；未命中才分配一个新主体，并记下这条对应关系。表结构与不变式见 [../persistence/schema.md](../persistence/schema.md)。

**主体标识本身不由渠道标识拼接而成，也不含任何渠道取值。** 它是 aladdin 内部的一条规范标识，分配即冻结、永不复用。理由是模型上必须能表达"一个人有多个渠道"——把渠道信息编进主体标识，等于替这个人选定了一个渠道；而"一个人两个渠道登录进来是同一个主体"恰恰是要支持的（见 [identity-linking.md](identity-linking.md)）。

**身份来源记在身份上，不记在主体上。** 这样将来接入第二个来源时，两边的身份各归各位、不会撞到一起：同一个不可变标识字符串在两个来源下是两个不同的身份。这也让"一个人在不同渠道上有不同的邮箱"成为一件可表达的事。

邮箱**可以**被记录用于展示与排障（"这个主体是谁"），但它记在那个身份上，**不参与任何判定**，也不参与身份的确定。

### 新主体的默认权限

**零。** 首次登录成功后：

- 主体被登记进主体表，并记下这个渠道身份与它的对应关系；
- **没有任何角色绑定**；
- 默认作用域为空，会话权限集合为空。

用户能登录、能看到界面框架、能看到自己的标识，但什么都点不了。这是**预期行为**，登录页与空白界面上的文案要说清楚这一点，否则第一个接入的人会以为登录坏了。

**后续绑上别的渠道也不会带来权限。** 归并改变的是"哪些渠道通向这个主体"，不是"这个主体有什么权限"——两条路径都不经过角色。

把它做成"首次登录自动获得某个角色"，等于让认证流程成为权限的来源——那正是 [CLAUDE.md](../../../CLAUDE.md) 第 7 条禁止的事情。需要给某个人权限，是管理员显式授予一次角色的动作。

### 第一个管理员

系统里还没有任何角色绑定时，"第一个管理员从哪来"是一个真实的问题：此时没有任何人有权授予自己角色。

它由**引导配置**解决——在配置里指定一个主体标识与作用域，系统在首次启动且存储为空时据此建立第一条绑定。引导的边界与四条性质见 [CLAUDE.md](../../../CLAUDE.md) 第 7 条与 [../config/server-config.md](../config/server-config.md)。

引导值取的是**主体标识**，或**已登记身份的邮箱**。

邮箱那条是引导专属的窄口子：它只在该邮箱恰好命中一个已登记身份时生效，命中 0 个或多个一律拒绝启动（同一个邮箱字符串可以分别挂在两个身份上，见上文的"绝不由邮箱确定"）。它**不是**"身份可以按邮箱确定"的先例——登录与绑定两条路径仍然只认不可变标识，邮箱在任何一次判定里都不参与，那两个子模块的行为一字未变。

两种写法都要求**先有一次真实登录**，因为主体是在那一刻分配的。登录后主体标识界面上就显示（页头与首页各一处），取到它的操作步骤见"可验证性"一节。

### 浏览器来源白名单

允许发起登录的浏览器来源（协议 + 主机 + 端口）**只配置在 Google 控制台，仓库里没有对应的配置项，也不应该有**。

理由是它不改变 aladdin 的任何行为：来源不匹配时 Google 在前端就拒绝了，请求根本到不了服务端。在 aladdin 侧再放一份，只会得到一份**永远不会被读到、却会在迁移部署时被误改**的副本。

因此部署到新域名时，改的是 Google 控制台，不是 aladdin 的配置文件——这一条要写进部署说明，否则表现为"换了域名之后登录按钮点了没反应"。

## 边界与约束

本模块**明确不处理**：

- 会话凭证本身的签发与失效：见 [session-token.md](session-token.md)。
- 主体拿到会话之后能做什么：[../rbac/](../rbac/README.md)。
- Google 控制台的申请与配置：这是部署动作，步骤见"可验证性"一节。

约束：

- **身份令牌绝不进入日志、错误信息与 `--debug` 输出。** 它与口令同级——它是一次登录的全部凭据。排障时需要的是主体标识与拒绝原因，不是令牌本身。
- **校验清单只有一份。** 绑定一个新渠道时要校验的项与登录完全相同，复用同一个校验器（见 [identity-linking.md](identity-linking.md)）；为绑定另写一套会让"哪条路径校验得更松"变成一个只能靠比对代码来回答的问题。
- **身份的归属只有一处实现。** 登录时的查-或-建是其中一个入口，绑定时写入别名是另一个（见 [identity-linking.md](identity-linking.md)）；任何"按邮箱匹配一下"的便利写法都不得参与。
- 校验实现**不得自行解析令牌**。用成熟的、经过审计的校验库完成签名与声明校验；自研实现漏掉一条声明的概率远高于它带来的收益。
- 校验过程**不得**依赖调用方提供的任何参数来决定信任什么。

## 可验证性与长程执行

**非长程任务。** 一次登录是一个同步的即时判定，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 身份解析稳定 | 同一个（来源，不可变标识）连续登录两次得到同一主体标识（`internal/identity` 测试） |
| 身份识别不随邮箱变化 | 同一个不可变标识配不同邮箱登录，得到同一主体；两个不同身份配同一邮箱，得到两个主体（`internal/identity` 测试） |
| 多次登录不重复登记 | 同一个身份登录两次后主体表只多出一条记录（`internal/identity` 测试） |
| 受众校验生效 | 签发方与签名都合法、但受众为另一个应用的令牌被拒绝（`internal/identity` 测试） |
| 其它校验项逐条生效 | 过期的、签发方不符的、签名不符的、缺不可变标识的令牌各自被拒绝（`internal/identity` 测试） |
| 拒绝类别正确 | 以上所有失败都返回"未认证"，**不是**"无权限"（端到端测试） |
| 新主体零权限 | 首次登录成功后该主体的绑定列表为空、会话权限集合为空（端到端测试） |
| 未启用时不渲染入口 | 客户端标识为空时前端不出现 Google 登录入口（`make test-web`） |

测试**不得联网**：校验器藏在一个接口后面，测试注入一个用测试自己生成的密钥签发的假实现，覆盖上表每一条。

手工验证（需先完成 Google 侧的申请）：

1. 建项目，配置 Google Auth Platform；建 **Web 应用**类型的 OAuth 客户端；把开发地址加进"已获授权的 JavaScript 来源"；受众建议选**内部**，这样只有本组织的账号能登录。
2. 客户端标识填进服务端配置，**先不填引导配置**。
3. 启动服务端与前端，用 Google 账号登录 → 应登录成功但界面全空。这一步验证"新主体零权限"。
4. 从服务端日志里读这次登录的**主体标识**（登录成功那一行带着它），填进引导配置并重启 → 该主体成为管理员，日志出现 `warn` 级留痕。
5. 删掉引导配置再重启 → **仍然是管理员**（验证"物化"：配置不是判定的输入）。

第 4 步是这套设计里唯一一处需要人工搬运的值，也是"主体标识在日志里可检索"这件事的用处所在。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 配置模块 | 消费客户端标识与引导配置；不自行读取来源（见 [../config/server-config.md](../config/server-config.md)） |
| RBAC 模块 | 登记主体（认证流程的职责，见 [../rbac/role-model.md](../rbac/role-model.md)）；不读取角色、不参与判定 |
| 会话凭证 | 登录成功后调用其签发入口（见 [session-token.md](session-token.md)） |
| 持久化 | 主体、身份别名与会话分别落在各自的表上，表结构与迁移由持久化模块统一管（见 [../persistence/](../persistence/README.md)） |
| 可观测性 | 登录成功与失败留痕，含主体标识与失败类别，**不含令牌**（见 [../../observability.md](../../observability.md)） |
