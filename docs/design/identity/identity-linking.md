# 身份认证 — 登录渠道的绑定

## 背景与目标

一个人可以有多个登录渠道。如果每个渠道各登记一个主体，同一个人就会变成多个主体：管理员在渠道 A 上授的权，他从渠道 B 登进来一概看不见，而表象是"权限没生效"，不是"认错人了，这不是我"。

本子模块定义把多个渠道归到同一个主体的那**唯一一个动作**：绑。它同时定下这条动作的两条边界——能绑给谁、什么时候不能绑。

成功的衡量标准：

1. 绑定之后，两个渠道登录得到**同一个主体**，绑定关系立即生效，不需要重新登录、不需要重启。
2. **不存在**把某个身份绑到指定主体上的入口。归属只由"谁发起了这次绑定"决定，不由令牌里的任何字段决定。
3. 一个身份已经属于某个主体时，**不会**因为第二个主体再绑一次而改归属：拒绝，且拒绝不透露现状。
4. 绑定与解绑都留痕，且留痕里不含令牌原文。

## 功能行为

### 登录时的解析：查，或者建

登录确认了一份渠道令牌之后（校验要求见 [google-login.md](google-login.md)），服务端按（身份来源，身份标识）在身份别名表中查：

| 查到的结果 | 结论 |
|-----------|------|
| 命中一条记录 | 这条记录指向的主体，就是本次登录的主体 |
| 没有命中 | 分配一个新的主体标识、登记主体、写入一条别名，再照常签发会话 |

**登录只做"查或建"，不做归并。** 一个未知身份不会因为与某个已有主体同名、同邮箱而被并入。邮箱在令牌里、也会被记下来用于展示与排障，但**没有任何一次身份归属的确定读它**——按邮箱归并意味着邮箱在渠道侧被回收的那一天，另一个人直接接管了这个主体的全部角色绑定（理由见 [google-login.md](google-login.md) 与 [../persistence/schema.md](../persistence/schema.md) 的身份别名表）。

新分配的主体与首次登录一样是**零权限**的：没有绑定，默认作用域为空。归并改变的是"哪些渠道通向这个主体"，不是"这个主体有什么权限"。

### 绑定：已登录的主体加上一个渠道

已认证的主体可以发起一次绑定，把一个新的渠道加到自己身上：

1. 请求携带该渠道的身份令牌；
2. 服务端用**与登录完全相同的校验器**校验它（见 [google-login.md](google-login.md)）——不得为绑定另写一套校验，那会让"哪条路径校验得更松"成为一个只能靠比对代码来回答的问题；
3. 校验通过后写入一条别名，指向**发起请求的那个主体**。

**归属由发起者决定，这是本子模块最重要的一条。** 令牌只证明"发起者控制着这个身份"，不决定"这个身份应该属于谁"。因此不存在"把身份 X 绑到主体 Y"这样的入口——如果存在，任何一个持有他人令牌的人都能把他人身份挂到自己名下，或者反过来把自己挂到他人主体上，而后者就是一次直接提权。接口面上只有"绑到当前已认证的主体"这一种形状。

由此可以得到一条可推导的结论：**持有他人令牌去绑定，得到的是把该身份绑到自己身上**，不是获得对方的任何权限。这个后果之所以有限，靠的是下一条——身份的唯一归属。

### 已属于他人：拒绝，不转移

| 目标身份的状态 | 结果 |
|--------------|------|
| 未被任何主体持有 | 写入别名，绑定成功 |
| 已属于**发起绑定的这个**主体 | 成功，且是幂等的：重复绑定不产生第二条记录、不报错 |
| 已属于**另一个**主体 | 拒绝。不转移、不合并、不提示它属于谁 |

**自动转移是不允许的。** 转移意味着任何一个拿到该渠道令牌的人都能把别人的进入方式夺走一部分，而这个动作在系统里看起来与一次正常绑定没有区别。要改变归属，先解绑，再由对方自己绑——每一步都由掌握该渠道的人发起。

拒绝**不透露**该身份的现状：只说"这个身份已被使用"，不说被谁使用。透露占用者等于把一次失败的绑定变成一次"这个渠道对应哪个主体"的探测。

### 解绑

解绑把一个渠道从主体上摘下来。**解绑后的效果要说清楚**：这个渠道不再通向该主体，下一次用它登录会按"未命中"处理，登记出一个**新的、零权限的**主体。这是预期行为，不是权限丢失——如果界面不说明这一点，用户会以为"我的权限被清空了"，而实际上他进了另一个主体。

**不允许解绑最后一个身份。** 一个主体没有任何身份，等于它再也没有任何进入方式：它的角色绑定还在，却没有任何人能进来清理。与其在库里留下一批无人可达的主体，不如让这一步请求失败，并说明原因。

解绑与绑定一样，只作用于**发起者自己的主体**：不存在"解绑他人主体上的某个渠道"的入口。

### 留痕

绑定与解绑各留一条记录：主体标识、身份来源、身份标识、动作、时间。**不含令牌原文**——与登录、会话一致，令牌与口令同级。

## 边界与约束

本模块**明确不处理**：

- 渠道令牌本身的校验要求：复用 [google-login.md](google-login.md) 的校验清单，本文件不重复定义。
- 主体拿到会话之后能做什么：[../rbac/](../rbac/README.md)。
- 身份别名表的表结构与迁移：由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)）。

约束：

- **绑定的准入门槛是"已认证"，不是一个权限码。** 要拿到的是**自己**主体的属性，而这个动作没有任何以他人为目标的形状，因此不存在可被滥用的授权面。反过来说：一旦将来出现"管理员替他人绑定/解绑"的入口，它就是一个以他人为目标的动作，必须带权限码——这两件事不能混在一个入口里。
- **身份的归属只有一处实现**：登录时的查-或-建，与这里定义的绑定。任何其它路径（包括"按邮箱匹配一下"这类便利写法）都不得写入别名表。
- 绑定与解绑**不改变已有会话**：会话的权限集合来自主体的绑定关系，而绑定渠道不改绑定关系。因此绑定之后不需要重新签发会话。

## 可验证性与长程执行

**非长程任务。** 解析、绑定、解绑都是即时的同步操作，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 两个渠道归一到同一主体 | 用渠道 A 登录建立主体后绑定渠道 B，再用 B 登录，两次得到同一主体标识（`internal/identity` 测试） |
| 身份归属唯一 | 把已属于主体 X 的身份绑到主体 Y 上失败，且归属仍是 X（契约测试） |
| 幂等绑定 | 同一身份绑两次，结果一致、表内仍只有一条记录、不报错（契约测试） |
| 无"绑到指定主体"的入口 | 接口面上不存在以任意主体为目标的绑定/解绑方法（proto 审查关卡） |
| 绑定需真实渠道令牌 | 伪造的、过期的、受众不符的令牌一律导致绑定失败（`internal/identity` 测试） |
| 登录不按邮箱归并 | 两个不同身份带同一邮箱登录，得到两个不同主体（`internal/identity` 测试） |
| 拒绝不泄露现状 | 绑已被他人占用的身份时，错误信息中不含占用者的主体标识（契约测试） |
| 解绑后渠道失效 | 解绑后该渠道不再进入原主体；再次登录登记出的主体权限为空（契约测试） |
| 不允许摘掉最后一个身份 | 对唯一身份发起解绑被拒（契约测试） |
| 不改变已有会话 | 绑定前后，同一份会话的权限集合不变（契约测试） |
| 令牌不入留痕 | 用一份令牌走完绑定，它不出现在任何日志行与留痕记录中（端到端测试） |

测试**不得联网**：校验器藏在接口后面，测试注入用测试自己生成的密钥签发的假实现。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 渠道登录 | 复用其令牌校验清单与校验器（唯一入口）；本文件不重复定义校验要求（见 [google-login.md](google-login.md)） |
| 持久化 | 身份别名表与主体表；两者的表结构与迁移由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)） |
| 会话凭证 | 绑定要求调用方已认证，因此以一份有效会话为前提；绑定本身不签发也不撤销会话（见 [session-token.md](session-token.md)） |
| RBAC 模块 | 只涉及主体的**登记**（认证流程的职责），不读角色、不参与判定（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 可观测性 | 绑定与解绑留痕，含主体标识与身份来源，**不含令牌**（见 [../../observability.md](../../observability.md)） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 主体失去全部可用渠道之后的恢复路径 | 暂不做。真出现时由管理员侧单独设计（**未定**） | 引入一个以他人为目标的动作，必须带权限码，且需重新审视"谁能替谁换渠道"（见"边界与约束"） |
| 绑定是否需要一次专门的重新认证（如再输一次口令） | 不做。新渠道的令牌本身已是一次新鲜认证（**未定**） | 只影响绑定的请求形态，不影响归属语义 |
