# 身份认证 — 登录渠道的绑定

## 背景与目标

一个人可以有多个登录渠道。如果每个渠道各登记一个主体，同一个人就会变成多个主体：管理员在渠道 A 上授的权，他从渠道 B 登进来一概看不见，而表象是"权限没生效"，不是"认错人了，这不是我"。

本子模块定义把多个渠道归到同一个主体的那**唯一一个动作**：绑。它同时定下这条动作的两条边界——能绑给谁、什么时候不能绑。

成功的衡量标准：

1. 绑定之后，两个渠道登录得到**同一个主体**，绑定关系立即生效，不需要重新登录、不需要重启。
2. **不存在**把某个身份绑到指定主体上的入口。归属只由"谁发起了这次绑定"决定，不由令牌里的任何字段决定。
3. 一个身份已经属于某个主体时，**默认不会**因为第二个主体再绑一次而改归属：拒绝，且拒绝不透露现状。唯一例外是"空主体认领"（见下）：一个只有这条身份、且没有任何角色绑定的主体，可以被当前已认证、且刚刚校验过这条身份的主体认领。
4. 绑定与解绑都留痕，且留痕里不含令牌原文。

## 功能行为

### 登录时的解析：查，或者建

登录确认了一份渠道凭证之后（校验要求见 [channel-login.md](channel-login.md) 及各渠道子模块），服务端按（身份来源，身份标识）在身份别名表中查：

| 查到的结果 | 结论 |
|-----------|------|
| 命中一条记录 | 这条记录指向的主体，就是本次登录的主体 |
| 没有命中 | 分配一个新的主体标识、登记主体、写入一条别名，再照常签发会话 |

**登录只做"查或建"，不做归并。** 一个未知身份不会因为与某个已有主体同名、同邮箱而被并入。邮箱在令牌里、也会被记下来用于展示与排障，但**没有任何一次身份归属的确定读它**——按邮箱归并意味着邮箱在渠道侧被回收的那一天，另一个人直接接管了这个主体的全部角色绑定（理由见 [channel-login.md](channel-login.md) 与 [../persistence/schema.md](../persistence/schema.md) 的身份别名表）。

新分配的主体与首次登录一样是**零权限**的：没有绑定，默认作用域为空。归并改变的是"哪些渠道通向这个主体"，不是"这个主体有什么权限"。

### 绑定：已登录的主体加上一个渠道

绑定与登录共用同一条"渠道凭证有两种到达方式"（见 [channel-login.md](channel-login.md)）。两种形态的**归属语义完全相同，只有凭证怎么到达服务端不同**：

| 形态 | 凭证怎么到达 | 绑定发生在哪一步 |
|------|-------------|-----------------|
| 搬运型 | 客户端把渠道签发的身份令牌放进绑定请求 | 同一次已认证请求里：校验并绑到当前主体 |
| 重定向型 | 渠道把浏览器重定向回服务端，凭证经一次浏览器导航到达 | 分两段：回调先得到一份**待绑定凭据**，前端再在已认证请求里兑换 |

#### 搬运型

1. 请求携带该渠道的身份令牌；
2. 服务端用**与登录完全相同的校验器**校验它（见 [channel-login.md](channel-login.md)）——不得为绑定另写一套校验，那会让"哪条路径校验得更松"成为一个只能靠比对代码来回答的问题；
3. 校验通过后写入一条别名，指向**发起请求的那个主体**；该身份已属于一个空主体时，走的是下面"空主体可认领"那一条——与重定向型是**同一处实现**，不是各写一份。

#### 重定向型

重定向型的凭证由渠道直接交给服务端，发起绑定的那次浏览器导航带不了认证头，因此**主体不能、也不需要穿过这次导航**。穿过导航的是渠道凭证；真正决定归属的是导航结束后那次**已认证的兑换**。

1. 已认证的主体从界面上发起一次带"绑定"用途的渠道导航。这个用途标记不是信任边界：导航本身不带认证头，任何人都可以发起一次导航；它只决定回调把结果做成"待绑定凭据"还是"会话"。
2. 服务端按与登录完全相同的流程校验渠道凭证；校验通过后**不解析主体、不登记新主体、不签发会话**，而是把这份**已校验的身份**记成一份**待绑定凭据**：一次性、短期、有上界，并且只经浏览器不可读的 cookie 交回。
3. 浏览器回到前端。前端在**一次已认证的请求**里兑换这份凭据。
4. 兑换时，服务端从**当前会话**取主体，把凭据里那份已校验的身份绑到它身上。

**待绑定凭据指的是身份，不是主体。** 这是它安全性的全部来源：凭据里没有"目标主体"这一项，任何拿到它的人都只能把**那份已经校验过的身份**绑到**自己**的主体上——与持有他人的渠道令牌去绑定是同一个后果，不是一次提权。因此接口面上仍然不存在"把身份绑到任意主体"的形状，也不需要有哪一份凭据带着主体标识穿过浏览器导航。

**待绑定凭据必须同时满足两件事才能兑换**：一份有效会话（证明兑换者是谁）与那份 HttpOnly cookie（证明它就是完成这次重定向的浏览器）。缺任何一项都不产生绑定。凭据本身不出现在地址、fragment、日志与 Referer 里；它单次使用，超时即失效，数量有上界，兑换成功后即被消费。

**归属由发起者决定，这是本子模块最重要的一条。** 令牌只证明"发起者控制着这个身份"，不决定"这个身份应该属于谁"。因此不存在"把身份 X 绑到主体 Y"这样的入口——如果存在，任何一个持有他人令牌的人都能把他人身份挂到自己名下，或者反过来把自己挂到他人主体上，而后者就是一次直接提权。接口面上只有"绑到当前已认证的主体"这一种形状。

由此可以得到一条可推导的结论：**持有他人令牌去绑定，得到的是把该身份绑到自己身上**，不是获得对方的任何权限。这个后果之所以有限，靠的是下一条——身份的唯一归属。

### 已属于他人：默认拒绝；空主体可认领

| 目标身份的状态 | 结果 |
|--------------|------|
| 未被任何主体持有 | 写入别名，绑定成功 |
| 已属于**发起绑定的这个**主体 | 成功，且是幂等的：重复绑定不产生第二条记录、不报错 |
| 已属于**另一个主体**，且那个主体是一个**空主体** | **认领**：把这条身份移到发起绑定的主体；原空主体留下零身份、零角色的壳 |
| 已属于**另一个主体**，且那个主体不是空主体 | 拒绝。不转移、不合并、不提示它属于谁 |

**空主体**同时满足两件事：这条渠道是它**唯一**的身份，且它**没有任何角色绑定**。换句话说，除这条进入方式之外，它什么也没有——没有权限、没有别的进入方式、没有可被搁浅的东西。首次单独登录重定向型渠道后产生的零权限主体就是这一类。

"有没有角色绑定"是 RBAC 侧的一条只读事实。认证模块读它只用于**空主体认领这条生命周期判断**，不用它算权限、也不参与任何一次放行——边界仍是"认证回答你是谁，RBAC 回答你能做什么"。

**认领是对"自动转移一律不许"的一个窄口子。** 对**非空**主体，自动转移仍然一律不允许：转移意味着任何一个拿到该渠道令牌的人都能把别人的进入方式夺走一部分，而这个动作在系统里看起来与一次正常绑定没有区别。空主体之所以可以，是因为"夺走"的代价为零：能新鲜校验这条身份的人本来就能登录它；认领不会让他获得任何新权限，最多让一个没有任何角色的壳失去进入方式。认领必须同时具备当前会话（证明目标主体是谁）与新鲜校验过的渠道凭证（证明发起者控制这条身份），两者缺一不可。

要改变**非空**主体的归属，仍然先解绑，再由对方自己绑——每一步都由掌握该渠道的人发起；管理员替他人迁移属于另一类动作，见下方待定决策。

拒绝**不透露**该身份的现状：只说"这个身份已被使用"，不说被谁使用。透露占用者等于把一次失败的绑定变成一次"这个渠道对应哪个主体"的探测。认领成功时可以告诉发起者"这个渠道此前单独登录过、已并入当前账号"，但**不给占用者的主体标识**。

### 解绑

解绑把一个渠道从主体上摘下来。**解绑后的效果要说清楚**：这个渠道不再通向该主体，下一次用它登录会按"未命中"处理，登记出一个**新的、零权限的**主体。这是预期行为，不是权限丢失——如果界面不说明这一点，用户会以为"我的权限被清空了"，而实际上他进了另一个主体。

**不允许解绑最后一个身份。** 一个主体没有任何身份，等于它再也没有任何进入方式：它的角色绑定还在，却没有任何人能进来清理。与其在库里留下一批无人可达的主体，不如让这一步请求失败，并说明原因。

解绑与绑定一样，只作用于**发起者自己的主体**：不存在"解绑他人主体上的某个渠道"的入口。

**顺序仍然重要，但不再是死角。** 先用新渠道单独登录一次，会登记出一个空主体；之后从已有主体发起绑定，走的是上面的"空主体认领"，结果与预期一致。但有两件事要讲清楚：

- 认领的前提是那个主体仍是空主体。若它在这一期间被授予了任何角色、或又绑定了别的身份，认领不再成立（否则会把角色或别的进入方式搁浅），此时才落到下方"非空主体上的身份转移"这个待定决策。
- 更好的顺序仍然是**先在已有主体上绑定、再用新渠道单独登录**：这样不产生任何空壳，也就没有认领这一步。界面必须把这两条与"新渠道首次登录得到零权限主体"一起说清楚。

### 留痕

绑定与解绑各留一条记录：主体标识、身份来源、身份标识、动作、时间。**不含令牌原文**——与登录、会话一致，令牌与口令同级。

## 边界与约束

本模块**明确不处理**：

- 渠道凭证本身的校验要求：复用 [channel-login.md](channel-login.md) 及各渠道子模块的校验清单，本文件不重复定义。
- 主体拿到会话之后能做什么：[../rbac/](../rbac/README.md)。
- 身份别名表的表结构与迁移：由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)）。

约束：

- **绑定的准入门槛是"已认证"，不是一个权限码。** 要拿到的是**自己**主体的属性，而这个动作没有任何以他人为目标的形状，因此不存在可被滥用的授权面。反过来说：一旦将来出现"管理员替他人绑定/解绑"的入口，它就是一个以他人为目标的动作，必须带权限码——这两件事不能混在一个入口里。
- **重定向型绑定的准入门槛同样是"已认证"。** 起点导航本身不认证、也不决定归属；它只声明用途。归属只在兑换待绑定凭据的那次已认证请求里发生。
- **待绑定凭据与渠道令牌同级。** 它证明"服务端已经校验过某个渠道身份"，因此必须一次性、短期、有上界、不可被脚本读取，且不进日志、地址与 Referer。它不是会话，不携带权限，也不能用于登录。
- **身份的归属只有一处实现**：登录时的查-或-建、这里定义的绑定，以及窄口子的空主体认领。任何其它路径（包括"按邮箱匹配一下"这类便利写法）都不得写入别名表。
- 绑定与解绑**不改变已有会话**：会话的权限集合来自主体的绑定关系，而绑定渠道不改绑定关系。因此绑定之后不需要重新签发会话。

## 可验证性与长程执行

**非长程任务。** 解析、绑定、解绑都是即时的同步操作，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 两个渠道归一到同一主体 | 用渠道 A 登录建立主体后绑定渠道 B，再用 B 登录，两次得到同一主体标识（`internal/identity` 测试） |
| 身份归属唯一 | 把已属于**非空**主体 X 的身份绑到主体 Y 上失败，且归属仍是 X（契约测试） |
| 幂等绑定 | 同一身份绑两次，结果一致、表内仍只有一条记录、不报错（契约测试） |
| 无"绑到指定主体"的入口 | 接口面上不存在以任意主体为目标的绑定/解绑方法（proto 审查关卡） |
| 绑定需真实渠道令牌 | 伪造的、过期的、受众不符的令牌一律导致绑定失败（`internal/identity` 测试） |
| 登录不按邮箱归并 | 两个不同身份带同一邮箱登录，得到两个不同主体（`internal/identity` 测试） |
| 拒绝不泄露现状 | 绑已被他人占用的身份时，错误信息中不含占用者的主体标识（契约测试） |
| 解绑后渠道失效 | 解绑后该渠道不再进入原主体；再次登录登记出的主体权限为空（契约测试） |
| 不允许摘掉最后一个身份 | 对唯一身份发起解绑被拒（契约测试） |
| 不改变已有会话 | 绑定前后，同一份会话的权限集合不变（契约测试） |
| 令牌不入留痕 | 用一份令牌走完绑定，它不出现在任何日志行与留痕记录中（端到端测试） |
| 重定向型绑定归一到同一主体 | 已登录主体走完重定向绑定后，再用该渠道登录，得到同一个主体（契约测试 + 端到端测试） |
| 兑换必须同时具备会话与凭据 | 缺失有效会话、缺失 cookie、cookie 与凭据不符三者都不产生绑定（`internal/server` 测试） |
| 待绑定凭据单次使用 | 同一份凭据兑换两次，只有第一次产生绑定（`internal/server` 测试） |
| 待绑定凭据超时即失效 | 超时后同一份凭据不再被兑换（`internal/server` 测试） |
| 绑定流程不登记主体、不签发会话 | 走完重定向绑定后，库里没有新增主体，响应里没有会话凭证（契约测试 + 端到端测试） |
| 用途标记不能指定主体 | 任何请求都无法把身份绑到一个不是当前会话代表的那个主体上（proto 审查 + `internal/server` 测试） |
| 空主体可被认领 | 已登录主体绑定一条属于空主体的身份后，该身份归当前主体，之后用它登录得到当前主体；原空主体只剩零身份、零角色（契约测试 + 端到端测试） |
| 非空主体不可被认领 | 原主体有任何角色绑定、或除这条身份外还有别的身份时，绑定被拒且归属不变（契约测试） |
| 两条凭证到达方式归属语义一致 | 已属于空主体的身份，无论经搬运型还是重定向型绑定，都被认领到发起者；两条路径共用同一处实现（`internal/server` 测试） |
| 认领不搁浅角色 | 认领成立的判据里包含"原主体没有任何角色绑定"，测试直接断言这条前置条件（`internal/server` 测试） |
| 认领认的是新鲜凭证 | 缺有效会话或渠道凭证校验不通过时不产生认领（`internal/server` 测试 + 端到端测试） |
| 认领不与角色授予竞态 | "原主体没有角色绑定"的检查与身份移动在同一把锁内完成，且**授予走的是同一把锁**；并发测试分两侧断言——授予确实在持锁期间读绑定，认领在持锁期间看不到新落下的授予（`internal/server` 测试）。注意它关上的是"检查与移动之间插入一次授予"这一个窗口，不覆盖"授予排在移动之后"这个顺序（见待定决策） |
| 待绑定凭据不入留痕 | 用一份凭据走完兑换，它不出现在任何日志行与地址里（端到端测试） |

测试**不得联网**：校验器藏在接口后面，测试注入用测试自己生成的密钥签发的假实现。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 渠道登录 | 复用其令牌校验清单与校验器（唯一入口）；本文件不重复定义校验要求（见 [channel-login.md](channel-login.md)） |
| 浏览器直连端点 | 重定向型绑定复用登录的起点与回调；用途（登录 / 绑定）由一次性导航状态携带（见 [github-login.md](github-login.md)） |
| 持久化 | 身份别名表与主体表；两者的表结构与迁移由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)） |
| 会话凭证 | 绑定要求调用方已认证，因此以一份有效会话为前提；绑定本身不签发也不撤销会话（见 [session-token.md](session-token.md)） |
| RBAC 模块 | 主体的**登记**在认证流程；空主体认领只读一条 RBAC 事实（"这个主体有没有角色绑定"），用于生命周期判断，不参与任何权限判定（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 可观测性 | 绑定与解绑留痕，含主体标识与身份来源，**不含令牌**（见 [../../observability.md](../../observability.md)） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 非空主体上的身份转移（含主体失去全部可用渠道之后的恢复） | 暂不做。真出现时由管理员侧单独设计（**未定**） | 引入一个以他人为目标的动作，必须带权限码，且需重新审视"谁能替谁换渠道"（见"边界与约束"）。空主体的认领不属于这一类，已在"功能行为"里定下 |
| 绑定是否需要一次专门的重新认证（如再输一次口令） | 不做。新渠道的令牌本身已是一次新鲜认证（**未定**） | 只影响绑定的请求形态，不影响归属语义 |
| "授予排在认领之后"把角色落在一个已经没有身份的主体上（搁浅的另一种顺序） | 暂不做。生命周期锁关掉的是"检查与移动之间插入一次授予"这一个窗口，不覆盖这个顺序。要一起关掉，授予侧需要一条"该主体还有身份"的前置条件，而**引导**恰恰是在零身份主体上写第一条绑定（见 [AGENTS.md](../../../AGENTS.md) 第 7 条），因此这条前置条件不能无条件加，得单独设计（**未定**） | 只影响授予的准入门槛；空主体认领与其它授予路径不受影响。触发还需要管理员在身份移走之后仍以主体标识指名原主体，因此当前的现实代价有限 |
