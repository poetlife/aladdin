# 身份认证 — 注册策略与邀请码

> 本文件是 aladdin **"谁能成为新主体、成为新主体时拿到什么"** 这一问题的功能行为唯一信源。实现细节变更只改代码；**注册模式、默认角色、邀请码的语义**的变更必须先改本文件。

## 背景与目标

[channel-login.md](channel-login.md) 描述的登录流程里，主体登记是**无条件**的：一个渠道身份只要通过了渠道自己的校验，就登记成一个新主体。在只服务内部人员的部署里这没问题；一旦对外，它意味着**任何持有 Google/GitHub 账号的人都能占一个主体**，而管理员没有任何办法把入口关上。

本模块把"谁能进来"变成一件可管理的事，同时回答第二个问题：**注册上来的主体默认拿到什么**。

成功的衡量标准：

1. 管理员能用一句话表达站点的准入姿态：**开放注册 / 需要邀请码 / 不接受新账号**，且这个姿态**立即生效、无需重启**。
2. 新主体默认拿到什么，是一件**可读、可改、可审计**的管理面记录，而不是散落在文件与环境变量里的开关。
3. **改注册策略不改变任何一次既有的放行判定**：判定路径只读角色绑定，从不读注册策略。
4. "不接受新账号"只拦**新主体**：已经登记过的身份照常登录。把老用户一起关在门外，是把一次准入收紧变成一次全站事故。
5. 邀请码是一份**与口令同级**的凭证：服务端只存摘要，明文只在签发那一刻出现一次。

## 模块边界

| 问题 | 归属 |
|------|------|
| 一个新主体能不能被登记、登记时授什么角色 | **本模块** |
| 某份渠道凭证可不可信、代表哪个身份 | [channel-login.md](channel-login.md) 与各渠道子模块 |
| 角色是什么、怎么判定、怎么授予 | [../rbac/](../rbac/README.md) |
| 策略与邀请码存在哪 | [../persistence/schema.md](../persistence/schema.md) |

**本模块不代替 RBAC 做判定。** 它写下的是一条**真实的角色绑定**，与管理员在人员授权页上点一次"授予"写下的那条逐字相同；判定路径只读那张表，不知道注册策略存在。

**本模块不解析渠道凭证。** 它接受的是"一份已经校验过的身份"（见 [channel-login.md](channel-login.md) 的校验器契约）。

## 与 AGENTS.md 第 7 条的关系

第 7 条禁止"配置成为权限的来源"，[channel-login.md](channel-login.md) 也写着"新主体的默认权限是**零**……那会让'谁能拿到什么'这件事出现第二个来源"。默认注册角色看起来正是被禁的那件事，因此判据必须写死在这里。

**它是管理面的记录，不是配置项。** 它满足第 7 条给出的那条判据——**"配置是初始化的输入，不是判定的输入"**：

| 第 7 条的四条边界 | 本设计如何满足 |
|---|---|
| **物化** | 注册成功时写入的是一条真实的角色绑定；判定路径只读存储，从不读注册策略。**改策略不改变任何一次判定结果**，删掉策略记录也**不**撤销任何一条已写下的绑定 |
| **一次性** | 只对**这次登记**生效。改策略不追溯已登记的主体 |
| **留痕** | 策略的每一次变更、每一次注册都留痕：发起主体、被授予的主体与范围、走了哪条注册路径 |
| **不可复用标识** | 授在 aladdin 分配的主体标识上（分配即冻结、永不复用） |

三条额外约束让它与"配置文件里的权限开关"彻底不同：

1. **它有独立的权限码**（`identity.registration.read` / `identity.registration.write`）。写它就等于改权限边界，因此"谁碰得到文件谁说了算"不成立。
2. **它是一条可读、可审计的记录**，与角色绑定同处管理面。
3. **它不能自我放大**（见下一条）。

因此**仓库里不存在**任何一个与注册有关的配置键：`config/server-config.md` 不加，环境变量不加。任何以配置文件形式出现的"允许注册""默认角色"都不允许存在。

### 默认角色不能是一个能自我放大的角色

**默认注册角色不得持有 `*`、`rbac.subject.assign`、`rbac.policy.publish` 或 `identity.registration.write`**——含经角色继承得到的（判据见 [../rbac/role-model.md](../rbac/role-model.md) 的"授予前的校验"）。

理由是这类取值把一次输入失误放大成一次全站失效：

- 默认角色取系统管理员 ⇒ **开放注册等于把管理员位子摆在门口**；
- 默认角色取权限管理员 ⇒ 任何一个新来的人都能给自己加任意角色，于是"发一个邀请码"与"发一份任意权限"变成同一件事，而邀请码正是**按准入凭证而不是权限凭证**设计的（见下）。

这条约束与互斥约束同属"授权时即校验"，不是运行时护栏。

## 功能行为

### 三种注册模式

站点级**一份**策略，对全部渠道生效。

| 模式 | 一个**未登记**的渠道身份来登录时 |
|------|--------------------------------|
| `open` 开放注册 | 直接登记成新主体 |
| `invite` 邀请码 | 不登记，先要一份有效的邀请码 |
| `closed` 不接受新账号 | 拒绝，不登记 |

**"未登记"是唯一判据。** 三种模式都**只拦新主体**：已经登记过的身份走的是另一条路（解析命中即签发会话），策略一个字都不影响它。这条是本节最要紧的一句——它决定了收紧准入不会把既有用户关在门外。

**取值缺失等价于 `open` 且无默认角色。** 这一条同时满足两件事：新部署开箱是开放注册（与收紧之前的行为一致），既有部署升级后行为**逐字不变**。收紧是一个由管理员显式做出的动作，不是一个会突然生效的默认值。

**模式是三选一，不是三个开关。** "允许注册"与"需要邀请码"不可能同时为真或同时为假，拆成两个布尔量会造出四种状态，其中两种没有意义，而实现必须为它们各写一个分支。

### 新主体的默认角色与默认范围

策略里包含**一份默认角色**与**它的作用范围**，二者要么都给、要么都不给：

- 都不给（缺省）⇒ 新主体**零权限**，这就是此前唯一的形态；
- 都给 ⇒ 登记新主体时，写一条真实的角色绑定 `（新主体，默认角色，默认范围）`，并把新主体的**默认作用域**取成那个范围。

默认作用域取自这条绑定，而不是另有一个配置项：**主体的默认作用域只能来自绑定关系**（见 [../config/README.md](../config/README.md)）。这条绑定使"这个新主体在哪个范围下工作"成为一件可读的事。

两个都给的约束：

- 角色必须**存在**（与授予时"角色要有定义才能授"同构）；
- 范围必须**已登记**，或为全局（全局是模型的根，不是登记记录，见 [../rbac/scopes.md](../rbac/scopes.md)）；
- 角色必须过上面那条"不能自我放大"的校验。

**默认角色对邀请码同样适用。** 邀请码只决定"能不能进来"，不决定"进来拿到什么"——进来之后拿什么，三种模式共用这一份策略。合成两处意味着同一个码既是准入凭证又是权限凭证，泄漏一个码就泄漏了它所带的那份权限。

### 邀请码

一份邀请码由管理员签发，形如一串可读、可手抄、可粘贴的字符。

**它只回答一件事：这个未登记的身份可不可以被登记。** 它**不带**角色、**不带**范围、**不绑定**收件人。

一份邀请码有下列属性，全部由签发时确定：

| 属性 | 语义 |
|------|------|
| 说明 | 给管理员自己看的标签（"给张三""市场部批次"）。它**不参与任何判断**。 |
| 次数上限 | 最多能成功兑换几次。0 表示不限次。 |
| 有效期 | 到什么时候为止。留空表示不过期。 |
| 撤销 | 撤销后立即不可兑换 |

**只撤销，不删除。** 删掉会连用量与留痕一起丢掉，"这个码被谁用过、用过几次"就再也答不上来——与"角色标识一经发布不可更改"是同一条取向。

**同一份邀请码不会在被兑换时超发。** 两次并发的兑换不能同时吃掉最后一个次数：判据是"扣减"这一步本身是否成立，而不是"先查一次再决定"。

**兑换失败一律是同一个结论。** 不存在、已过期、次数用尽、已被撤销——对调用方是同一句话（"邀请码无效或已用尽"），不区分。区分它们只会把一次失败的注册变成对"这个码是否曾经有效"的探测，与 [device-login.md](device-login.md) 把四种"不能交付"合并成 `EXPIRED` 是同一条理由。

**明文只出现一次。** 服务端只存摘要（与口令、会话凭证同级，见 [session-token.md](session-token.md)）。签发时把明文交给管理员，此后再也读不回来；列表里只有说明、用量与状态。

### 闸门落在哪一步

闸门只有**一处**：主体登记的那一刻。放在别处都会漏——放在渠道起点上，渠道回调是浏览器直连的地址，任何字符串都能打过来；放在客户端上，客户端的本地判断不是安全边界（见 [../../rbac/frontend-permissions.md](../../rbac/frontend-permissions.md)）。

登录路径因此分成两支：

```
渠道凭证已校验
      │
      ├── 身份已登记 ──────────────► 签发会话（策略不参与）
      │
      └── 身份未登记 ─► 读策略
                          ├── open   ─► 登记 + 默认角色 ─► 签发会话
                          ├── invite ─► 等待邀请码 ─► 登记 + 默认角色 ─► 签发会话
                          └── closed ─► 拒绝，不登记
```

**`invite` 那一支要跨一次浏览器往返**，因为邀请码由人在浏览器里输入，而渠道回调那一步没有可填表的地方（它是一次跨站导航的落点）。这一步的凭据交换沿用与 [identity-linking.md](identity-linking.md) 的待绑定凭据**完全相同**的形状：

1. 回调把**已经校验过的身份**记成一份短时的一次性凭据，只经浏览器不可读的 cookie 交回；
2. 浏览器回到前端的填码页；
3. 人填码，前端把码经一次调用的**请求体**交给服务端（**不是地址**：地址会进访问日志、浏览器历史与跳转来源，而邀请码与口令同级）；
4. 服务端**先兑换邀请码、再取走凭据**，然后登记主体、授默认角色、签发会话，一次交回。

   两步的顺序是刻意的：**填错码是使用者在这一页上最常犯的错**，而"先取走凭据"会让每一次填错都把人打回登录页重来一遍。先兑换码，填错时凭据原封不动，改一个再提交即可。代价是"凭据已失效"那一支会白烧掉一次码的可用次数——它只在两次提交同时到达或中途过期时发生，比前者罕见得多、损失也小得多。
5. **归属只由那份凭据决定**：请求里只有邀请码，没有主体——不存在"替某个身份注册"的形状，与"不存在把身份绑到指定主体"同一条理由。

**这份凭据单次使用、短时有效。** 它换来的是一个新主体与一份会话，与[待绑定凭据](identity-linking.md)同级。

### 已登记身份的一支不受影响

**解析命中时，策略一个字都不参与**：不查模式、不查邀请码、不重算默认角色。因此：

- 把模式改成 `closed` 之后，既有用户照常登录；
- 改默认角色**不追溯**：此前注册的主体拿的还是当初那条绑定；
- **解绑最后一个渠道之后的重新登录会走注册路径**：那个身份不再指向任何主体，于是它是"未登记"的，闸门照常生效（见 [channel-login.md](channel-login.md) 的"换一个渠道登录不会拿到已有主体的权限"）。

### 渠道清单里带出模式

登录页要能说明白"这里需要邀请码"或"这里不接受新账号"，因此模式随**已启用渠道清单**一并下发。它是**公开**取值，与渠道清单同类：它本来就会展示给任何一个打开登录页的人，藏起来不保护任何东西，只会让前端去硬编码一份会漂移的副本。

## 边界与约束

本模块**不处理**：

- 判定本身：三元组怎么判、范围怎么包含，见 [../rbac/](../rbac/README.md)。
- 邀请码的发放方式（邮件、IM、口头）：它是 bearer 凭证，管理员怎么送出去不属于本模块。
- **按渠道分别设模式**（如 Google 开放、GitHub 需邀请码）：本模块只有一份站点级策略。要做的话是策略多一维，不是新机制。
- **注册审批**（先申请、管理员逐个批准）：那是另一条流程，与"邀请码"是不同的取舍，不顺手塞进这个模块。

约束：

- **邀请码明文不进入日志、错误信息与 `--debug` 输出**。它与口令同级——一份能换来一次注册的凭据。排障时需要的是说明、用量与拒绝类别，不是码本身。
- **归一化只有一处。** 邀请码是给人抄或粘的：大小写、连字符、易混字符（`I`/`l`/`1`、`O`/`0`）随人怎么写。折算散在各调用方各折一遍，迟早会有一条折得不一致，而那表现为"管理员发的码明明是对的，页面却说无效"。
- **摘要只有一处实现**：复用会话凭证的摘要入口，不另写一份。
- **注册的落库顺序是刻意的**：主体 → 默认角色绑定 → 身份别名。身份别名是"这个身份已经登记过"的**唯一事实来源**，因此只有在它写下去之前失败，下一次登录才会重新走一遍登记（含那次授予）。反过来先写别名，授予失败会留下一个"已登记、永远拿不到默认角色、且已经绕过闸门"的主体，而它看起来只是"这个账号权限不对"。
- **并发下认输的一方要把自己刚写下的绑定收回**：否则留下一个持有角色却没有任何进入方式的空壳，日后删那个角色会冒出"仍被主体 X 持有"。

## 可验证性与长程执行

**非长程任务。** 一次注册是一次调用一次结论；邀请码的扣减是存储里的一次原子操作，不做多阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 未登记身份是唯一判据 | 已登记身份在三种模式下都登录成功，且策略改动不改变它的权限（`internal/server` 测试） |
| `closed` 只拦新主体 | 未登记身份被拒且**库里没有多出任何主体或身份**；已登记身份照常（`internal/server` 测试 + 端到端） |
| `open` 与当前行为逐字一致 | 策略记录缺失时登记照常成功，且绑定列表为空（`internal/registration` 测试） |
| `invite` 需要码 | 无码或错码时不产生任何主体；正确码产生一个主体与一条真实绑定（端到端） |
| 邀请码不超发 | 同一份次数上限为 1 的码被并发兑换 N 次，恰好成功 1 次（`internal/registration` 的并发测试） |
| 拒绝不泄露状态 | 不存在 / 已过期 / 已用尽 / 已撤销四种情形返回**同一句话**（`internal/server` 测试） |
| 明文只出现一次 | 列表接口的返回值里没有任何字段能还原出明文；库里存的是摘要（`internal/registration` 测试） |
| 归一化一致 | 同一份码以大写、小写、带连字符、带易混字符替换的写法都能兑换到同一份码（`internal/registration` 测试） |
| 默认角色约束 | 取 `*` 或持有 `rbac.subject.assign`（含经继承）的角色被拒绝（`internal/rbac` 测试） |
| 绑定先于身份别名 | 在授予这一步注入失败，断言这个身份仍被视为未登记、下一次登录会重新走完登记（`internal/server` 测试） |
| 契约不漂移 | 三种模式在 grpc-go 与 Connect 两个客户端上结论一致（`test/e2e`） |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 渠道登录 | 本模块坐在"渠道凭证已校验"之后，接受一份已校验的身份；校验器与登录共用同一份（见 [channel-login.md](channel-login.md)） |
| RBAC 模块 | 写一条真实的角色绑定；不读角色做判定、不参与任何放行。默认角色的合资格约束在授权面的约束校验里（见 [../rbac/role-model.md](../rbac/role-model.md)） |
| 持久化 | 策略与邀请码各落一张表；表结构与迁移由持久化模块统一管（见 [../persistence/](../persistence/README.md)） |
| 会话凭证 | 注册成功后调用其签发入口（见 [session-token.md](session-token.md)） |
| 配置模块 | **没有交互**：本模块的取值一律不来自配置，见上文"与第 7 条的关系" |
| 可观测性 | 策略变更与注册成功/失败留痕，含主体标识与拒绝类别，**不含邀请码明文**（见 [../../observability.md](../../observability.md)） |
