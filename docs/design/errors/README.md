# 失败分类 模块总览

> 本目录是 aladdin **"一次失败是什么、客户端该拿它怎么办"** 这一问题的功能行为唯一信源。

## 背景与目标

鉴权这一条链路已经有结构：[../rbac/](../rbac/README.md) 用 `DenialReason` 枚举加 `DenialDetail` 说明"为什么被拒绝"，三端都按枚举分支，不做文本匹配。其余业务面没有跟上：服务层各自把领域错误翻译成"一个传输码 + 一句文案"，同一个失败原因在不同方法里可能给出不同结论，客户端只能按传输码或文案猜。

本模块把鉴权链路上已经成立的做法推广为**全业务面的失败分类**。它不重新定义任何一条业务规则，只回答三个问题：

1. 这次失败属于哪一类（机器可读）；
2. 它对应哪个传输码、默认对用户说什么；
3. 它怎么从领域代码送到客户端，且只经过一处转换。

成功的衡量标准：

1. 每个对外可观察的失败都有**一个**机器可读的失败原因；客户端按原因分支，不匹配文案。
2. 同一个失败原因在所有方法、所有协议上只有**一个**传输码。
3. 新增一种失败只需要改 proto 并重新生成，不需要在服务层新增一条"错误 → 码 + 文案"的映射。
4. 没有分类的失败对外只有一句固定文案；原因与因果链只进日志。
5. 三端（Web、CLI、SDK）能对同一个传输码下的两个不同原因给出不同处理。

## 模块边界

| 问题 | 归属 |
|------|------|
| 一次鉴权判定给不给过、为什么 | [../rbac/](../rbac/README.md)，本模块只消费它的结论 |
| 一次失败属于哪一类、对应哪个码与默认文案 | **本模块** |
| 失败怎么按连接协议编码成响应 | 传输层（Connect），本模块不重新实现 |
| 失败怎么留痕 | [../../observability.md](../../observability.md) |

两条边界要守住：

- **不重新定义业务语义。** 某个领域错误该不该是"找不到"、该不该让客户端重试，仍由该领域的 spec 决定；本模块只要求这个结论只有一个来源，且可被机器读取。
- **不扩传输码。** Connect 的十六个码是跨协议互操作的基础（见 [../rbac/server-permissions.md](../rbac/server-permissions.md) 的"拒绝语义"）。失败原因是在这十六个码之上的细分，不是第二套码表。

## 功能行为

### 失败原因是一份契约

失败原因定义在 proto 枚举里，由 `buf generate` 派生出 Go 与 TypeScript 两侧的同一组取值，三端都引用生成常量，不得手写字符串或第二份枚举。

每个非零取值在 proto 里同时声明两件事：

- **默认文案**：这个原因对用户该怎么说；
- **传输码**：它对应十六个 Connect 码中的哪一个。

构建期校验缺一不可：缺文案、缺码、码的拼写不认识、编号越出所属分段，都直接失败。**没有"漏填就回落到某个默认值"这回事**——回落会让一次新增失败静默地变成"内部错误"。

原因编号是**线上契约**：编号一旦发布就不再复用，删除一个原因时只把编号标记为保留。重新编号会让旧客户端把一次失败解释成另一件事。

### 原因的粒度

原因的粒度是**"客户端可能据此改变行为"的类别**，不是一句文案。

- "工程不存在"与"版本不存在"是两个原因：客户端可以给出不同的下一步。
- "工程名称超长"与"简介超长"可以共用一个"字段不合法"的原因，具体是哪一项、上限多少放在文案里——客户端不会因为这两者改变处理方式。
- 不为每一条现有文案造一个原因。那等于把文案表换成枚举表，客户端仍然没有可分支的语义。

判断标准只有一句：**如果两件事客户端要做的事一样，它们就是同一个原因。**

### 编号分段

原因按所属领域分段，新增领域先在本文件登记一段，再在 proto 里使用：

| 分段 | 归属 |
|------|------|
| 1000–1099 | 跨领域的通用失败（存储不可用等） |
| 1100–1199 | 认证与鉴权 |
| 1200–1299 | 身份与个人档案 |
| 1300–1399 | 平台技能目录 |
| 1400–1499 | galaxy 创作与发布 |
| 1500–1599 | 注册与邀请 |
| 1900–1999 | 服务端内部失败（含未分类兜底） |

区间同时登记在生成器的分段表里（见下方"代码入口"）：新增领域时两处一起改。生成期会检查每个原因的编号确实落在某个区间内，越界直接失败。它约束的是**编号归属**，不是依赖方向：任何领域都可以使用通用分段里的原因。

### 传输码与文案

传输码由原因**决定**，调用方不传。这是"同一原因只有一个码"能够成立的唯一做法：只要还允许调用点自己选码，两个方法迟早会给出不同结论。

默认文案同样由原因决定，但一次具体的失败可以补充上下文（哪一项超限、被哪个版本引用）。补充文案只用于展示，**客户端不得据此分支**；需要分支的信息进原因或结构化的补充信息。

没有分类的失败一律按"服务端内部失败"处理：对外固定文案，不带原因之外的任何内部细节；原始错误只进日志。这不是兜底美化，而是不泄漏实现细节、同时让排障的人仍能拿到因果链。

### 唯一的转换点

领域代码返回带原因的失败，**转换只发生在 RPC 边界的一处**。服务方法不再各自决定传输码与文案，也不再有每个服务一份的"错误映射表"。

三个例外必须原样透传，不得二次包装：

- 传输层自己产生的错误（请求体解码失败、超时、取消）；
- 鉴权拦截器与 HTTP 中间件已经编码好的拒绝；
- 流式调用中由框架产生的错误。

包装它们会改变协议行为（例如把一次"取消"变成"内部错误"），也会让同一个失败出现两个原因。

HTTP 中间件里的认证拒绝不在 RPC 拦截器范围内，因此它走与鉴权拒绝**同一个**拒绝入口，产出同形状的失败详情。

### 失败详情

每一次已分类的失败都随错误携带一份结构化详情，包含：

- 失败原因（客户端据此分支）；
- 展示文案（与错误消息同源同值，便于客户端不再读原始错误文本）；
- 结构化补充信息（例如"哪个方法漏写了注解"）。

详情里**不得**出现凭证、口令、对象存储的临时凭证、内部路径或因果链原文。

### 迁移状态

本模块按服务逐个收编，不要求一次改完。迁移期间：

- 鉴权链路的拒绝已经走统一分类，并同时携带新旧两种详情；
- 业务服务仍可能返回"码 + 文案"的旧形状：它们没有失败详情，客户端按码处理，行为与改造前一致；
- Web 与 CLI 仍读旧详情，尚未切换。

迁移状态不改变目标：新写的失败必须走统一分类，旧形状只减不增。切换客户端的时机在业务服务收编之后——那时新详情才覆盖了绝大多数失败。

### 与 DenialDetail 的迁移关系

鉴权拒绝原有的 `DenialDetail` 是已经发布出去的契约，不能在一夜之间消失。迁移期：

- 鉴权拒绝**同时**携带新详情与 `DenialDetail`，两者描述的是同一个结论；
- 新客户端优先读新详情，读不到再退回 `DenialDetail`；
- 其余业务失败只携带新详情，不再新增旧形状。

删除条件写死在这里，避免"临时兼容"变成永久的两份事实：**Web 与 CLI 都已改为只读新详情，且经过一个发布周期之后**，删除 `DenialDetail` 与旧枚举；此后拒绝原因只有一份定义。

迁移期不允许出现第三种形状，也不允许客户端为同一个原因维护两套判断逻辑。

### 三端的行为

以下是**迁移完成后**的客户端行为：

- **Web / CLI / SDK**：按原因分支，决定提示、退出码、是否重试；文案优先用详情里的展示文案，需要更贴合本入口的说法时才按原因覆写。
- **鉴权拒绝**：三端可以保留各自更可操作的措辞（例如 CLI 指向 `aladdin permissions`），但**分支依据仍是原因**，不是文案。
- **同一传输码下的两个原因**必须能被区分开。例如"权限不足"与"作用域不够"都是 `PermissionDenied`，客户端对前者提示联系管理员、对后者提示换更高层级的作用域。

### 日志

每一次失败至少留下：原因、传输码、过程名、因果链。分类为"内部失败"的（含未分类与注解缺失）按错误级别记录；业务失败由请求日志按结果码记录。

因果链只进日志，不上线。日志里也不重复记录详情里已有的结构化信息。

## 边界与约束

本模块**明确不处理**：

- 失败的**业务语义**：某个领域错误该映射到哪一类，由该领域自行决定并在其 spec 中说明。
- **软状态**：等待审批、尚未发布、正在处理都不是错误，不得表达为失败原因。
- **限流与重试策略**：本模块只给出"这个码意味着可以重试"这一层结论，退避参数由调用方决定（见 [../web/](../web/README.md) 与 [../cli/](../cli/README.md)）。
- **审计**：失败留痕是日志与遥测的事，见 [../../observability.md](../../observability.md)。

另外三条硬约束：

1. **不得新增传输码**，也不得引入自定义的状态字段；详情就是为此准备的。
2. **不得让配置成为失败分类的来源**：原因、码、文案都不由配置文件或环境变量提供。
3. **不得按文案分支**。发现一处按文案匹配，就是一处待迁移的旧代码，而不是一种可接受的兜底。

## 可验证性

| 要证明的事 | 验证方式 |
|-----------|---------|
| 每个原因都有文案与合法传输码，编号在分段内且不复用 | 构建期测试遍历 proto 描述符 |
| 生成产物与 proto 同步 | `make check-gen` 与构建期测试 |
| 未分类失败对外只有固定文案，因果链只进日志 | 单元测试 |
| 已编码的错误原样透传，不被二次包装 | 单元测试（含取消、超时） |
| 三种协议读到同一份失败详情 | 端到端测试（gRPC 与 Connect 客户端打同一端口） |
| 同一传输码下的两个原因可区分 | 端到端测试 |
| 鉴权拒绝在迁移期同时带两种详情 | 端到端测试 |
| 服务方法不再各自映射错误 | 代码评审 + 映射表删除后的编译结果 |
