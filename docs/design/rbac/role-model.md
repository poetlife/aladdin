# RBAC — 角色与权限模型

## 背景与目标

定义 aladdin 中"谁、对什么、能做什么"。本子模块只描述模型本身；**如何用这个模型做判定**见 [enforcement.md](enforcement.md)。

## 功能行为

### 四个基本概念

| 概念 | 含义 | 关键性质 |
|------|------|---------|
| 主体（Subject） | 发起操作的一方 | 有三类：人类用户、服务账号、机器凭证（CLI 使用，从属于某个用户或服务账号） |
| 角色（Role） | 一组权限的命名集合 | 可继承其他角色；分为内置角色与自定义角色 |
| 权限（Permission） | 对某个资源执行某个动作的许可 | 以**权限码**字符串标识，全局唯一 |
| 作用域（Scope） | 权限生效的范围 | 层次化路径，形如 `tenant/acme/project/web` |

### 权限码

权限码是权限在系统中的唯一标识，格式为三段式：`<领域>.<资源>.<动作>`，例如：

- `rbac.role.read` — 读取角色定义
- `rbac.role.write` — 创建、修改、删除角色
- `rbac.subject.assign` — 为某个主体授予或回收角色
- `rbac.policy.publish` — 使一次角色变更正式生效

支持通配，通配只能出现在**末段**或占据**整个权限码**：

| 写法 | 含义 |
|------|------|
| `rbac.role.*` | `rbac.role` 下的全部动作 |
| `rbac.*` | `rbac` 领域下的全部权限 |
| `*` | 全部权限，仅保留给系统管理员角色 |

**权限码的全集定义在权限目录 `api/permissions/catalog.yaml` 中，它是唯一信源。**
Go 侧常量与前端常量均由它派生（`make gen`），不允许任何一端手写权限码字符串字面量。

新增权限的行为约定：

1. 先在 `api/permissions/catalog.yaml` 登记权限码；
2. 再在 proto 的方法上引用它（`option (aladdin.rbac.v1.required_permission)`）；
3. 一致性由 `internal/rbac/catalog_test.go` 在构建期强制校验——漏了任何一步，测试立刻失败。

### 角色的继承与约束

- **继承**：角色可以继承一个或多个角色，继承是传递的。子角色持有父角色的全部权限，叠加自身权限。不允许循环继承。
- **静态互斥（SSD）**：两个角色不可同时授予同一主体。用于表达"不能既审批又执行"这类职责分离要求。
- **动态互斥（DSD）**：两个角色不可在同一会话中同时激活。SSD 的宽松版本，用于需要临时切换身份的场景。

互斥约束**在授权时即校验**，而不是等到使用时才拒绝——不合法的角色组合不应该被存进系统。

### 作用域的匹配规则

- 作用域是路径式的层级结构，父作用域天然包含子作用域。
- 主体在作用域 A 上被授予的权限，对 A 的所有后代生效。
- 判定时，**请求的作用域必须被授予的作用域包含**。授予在子作用域上的权限不能用于父作用域上的操作。
- 全局作用域（根）是唯一一个能覆盖所有其他作用域的值，仅内置管理员角色持有。

### 内置角色

| 角色 | 权限范围 | 是否可修改 |
|------|---------|-----------|
| 系统管理员 | 全部权限、全局作用域 | 不可删除、不可修改权限范围 |
| 权限管理员 | `rbac.*`，限于其被授予的作用域 | 可修改 |
| 审计员 | 只读权限 + 审计日志查阅，覆盖全部作用域 | 可修改 |
| 只读用户 | 业务资源的只读权限，限于其被授予的作用域 | 可修改 |

> 业务领域角色（如"操作员"）在业务资源落地时随其权限码一并加入权限目录。
> 骨架阶段只有上述四个内置角色——一个不持有任何权限的角色不是角色，是占位符。

内置角色的**存在**是模型的一部分（代码可依赖其标识），其**具体权限绑定**可在部署时调整。

### 主体的权限来源

一个主体最终持有的权限 = 直接授予的角色 ∪ 通过角色继承得到的角色，取并集后在作用域约束下展开。**不存在"拒绝"规则产生的负向权限**——模型中没有 deny 条目，拒绝只来自"没有匹配的授权"。这与 [enforcement.md](enforcement.md) 的"默认拒绝"语义配套。

## 边界与约束

本模块**明确不处理**：

- 认证：口令、OAuth、令牌签发与刷新。这些属于身份认证模块。
- 属性基访问控制（ABAC）：不基于资源属性、时间、地理位置做判定。若未来需要，应作为独立模块与本模型组合，而不是往角色里塞条件。
- 业务资源的可见性规则（如"只能看到自己创建的订单"）：这属于资源归属，不由 RBAC 表达。
- 跨租户的隔离策略细节：作用域只提供表达的载体，租户如何划分由部署决定。

约束：

- 角色数量与继承深度需有上限（具体阈值在实现时确定并记录），避免判定路径爆炸。
- 角色标识一旦发布不可更改；角色**名称**可改。标识的变更视为"删除旧角色 + 新建角色"。

## 可验证性与长程执行

**本模块属于长程任务。** 角色变更（授权、回收、发布）不是一次性的即时操作：它需要经过校验、落库、缓存失效、传播到已建立的会话，且可能因存储不可用而中断。因此必须可从外部判断进度与恢复。

### 阶段划分与完成判据

| 阶段 | 完成的可观测判据（产出了什么可检验的信号/记录） |
|------|-----------------------------------------------|
| 变更受理 | 变更请求已记录，带有唯一的变更标识与发起主体；校验未通过时在此阶段终止，不产生任何持久化影响 |
| 约束校验 | 互斥、循环继承、作用域合法性均已校验；校验结果（通过/拒绝及原因）已留痕 |
| 持久化 | 角色/绑定关系的存储写入已提交；可读回并比对与请求一致 |
| 缓存失效 | 受影响的缓存条目已被标记失效；失效范围（哪些主体、哪些作用域）已留痕 |
| 生效确认 | 一次新的判定请求能够观察到变更后的结果；生效时间已留痕 |

### 进度记录（让进展可见）

- 每个阶段开始/结束须产出**可被外部读取的记录**，使得无需重跑即可回答"现在到第几步、上一步结果如何"。
- 记录的具体字段与格式遵循 [observability.md](../../observability.md)，本节只声明**哪些阶段必须留痕、留痕需包含哪些信息维度**：

| 阶段 | 必须留痕的信息维度 |
|------|------------------|
| 变更受理 | 变更标识、发起主体、目标主体、角色标识、作用域、受理时间 |
| 约束校验 | 校验结论、被违反的约束种类（若有） |
| 持久化 | 影响的行数/条目数、提交时间 |
| 缓存失效 | 失效的缓存键范围、条目数 |
| 生效确认 | 观测到的生效时间、参与确认的判定请求标识 |

### 检查点与恢复（让失败可续跑）

- **检查点边界**：设置在"持久化"完成之后。持久化前的中断应整体回滚，不留下半成品绑定；持久化后的中断（缓存失效或生效确认失败）应**从缓存失效阶段继续**，而不是重新执行整个变更。
- **幂等/去重要求**：
  - 重复发起同一次变更（相同变更标识）不得产生重复的角色绑定。
  - 缓存失效必须幂等：对已经失效的条目再次失效不应报错。
  - 恢复执行时不得重复触发对外通知（若未来引入）。
- **检查点状态的可读性**：变更标识可作为查询键，读取该次变更当前所处阶段与各阶段的留痕记录。**不允许存在"只写日志、无法按键查询"的进度记录。**

> 闭环：本节定义的关键阶段，应纳入 [observability.md](../../observability.md) 的"关键路径日志链路"；每次因"中途无法判断进度/无法恢复"而排障，应回到本节补全对应阶段的判据或检查点。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 身份认证模块 | 只接收已确认的主体标识；本模块不解析凭证 |
| 持久化存储 | 经 `rbac.Store` 抽象读写角色、权限、绑定关系 |
| 权限目录 | 权限码全集来自 `api/permissions/catalog.yaml` |
