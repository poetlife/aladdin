# RBAC — 作用域的登记与生命周期

## 背景与目标

[role-model.md](role-model.md) 定义了什么是一次判定（主体 × 权限码 × 作用域），但作用域此前只以**字符串**的形式存在于绑定上：没有任何地方登记"这个部署里有哪些范围"，因此界面上只能让人手输一条层级路径。

本模块给作用域一个**登记表与生命周期**：谁在哪儿工作，是从一份可读的目录里选出来的，而不是猜出来的。它要同时满足两件看起来矛盾的事——作用域仍是**部署的自由**（层级怎么划、叫什么，由部署决定），而管理员在界面上不必知道路径语法。

成功的衡量标准：

1. 管理员能看懂"系统里有哪些范围"，并能从列表里选，而不是凭空写一条路径。
2. 引用是可信的：一条绑定指向的范围一定登记过，不会出现"绑到一个不存在的范围"这种悬空引用。
3. 判定本身没有变复杂：判定路径**不读**这份登记表。

## 功能行为

### 一个已登记的范围

- 由**路径**与**显示名**两部分构成。路径是标识（形如 `tenant/acme`，也是判定的输入），**一经登记不可更改**；显示名只用于展示，可改。
- 与角色完全同构：角色的标识一经发布不可更改、名称可改。"改路径"因此不是一次改名，而是"删掉旧范围 + 新建一个范围"，与本模型对角色标识的处理一致。
- **全局（根）不是一条登记记录。** 它永远可用、不可创建也不可删除；它是模型的根，不是目录里的一项。界面上一律显示「全局」。
- 父子关系由**路径本身**表达（父包含子），不另存一份父子关系——那会是第二个真相源，而包含语义只能有一处实现。

### 登记（创建）

- 任何路径都可以登记，**不要求它的祖先先被登记**：作用域名一直是自由文本，规范化或强制逐级登记都会让"这条路径到底能不能用"变成一个需要推理的问题。
- 登记一个已经登记过的路径不是错误，而是一次**改显示名**（与"重复授予同一角色是幂等的重复写入"同理）。

### 严格：绑定必须指向已登记的范围

- **授予角色时，目标范围必须已登记**；指向未登记的范围拒绝，并提示先登记该范围。
- 依据是与角色的一致性：授予角色时角色必须已存在，这是已有的校验。角色：定义存在 ↔ 可授予；作用域：登记存在 ↔ 可绑定。
- **全局始终合法**：它是根，不需要登记。
- **只在授予侧校验，回收侧不校验。** 撤收窄永远要能做——与"静态互斥只在授予时校验"同理。
- 这条约束属于**授权面的输入校验**，不是判定语义：判定仍然只看绑定，不查这份登记表。

### 删除

- 删除**不可逆**，且要求干净：**有绑定落在它或它的后代上就拒绝**，并说明还有多少条。这与"删除角色时角色仍被持有则拒绝"完全同构——引用还在，就不允许把被引用的东西抽走。
- 后代落在同一个约束里：绑定在 `tenant/acme/project` 上的人，就是"落在了 `tenant/acme` 之内"，因此父范围也删不掉，直到那些绑定被回收。
- **不检查主体的默认作用域**：它不是绑定，判定也不读登记表，因此删掉一个范围不会产生悬空引用；如果它是引导配置用的那个范围，下次启动会重新登记。这条刻意不检查，是为了不让"删一个范围"牵连到会话签发的配置。

### 空范围的两种含义（**最容易混，写死在这里**）

| 语境 | 空范围的含义 |
|------|-------------|
| 管理面（如授予角色，范围会被写进绑定） | **全局**（根） |
| 会话查询（如"我在这个范围下有哪些权限码"） | **不指定**：回落到凭证的默认作用域，并把解析结果回传 |

因此「全局」是**授予**时合法的目标，却不是**顶栏管理范围**的合法候选：顶栏填空是"不指定"，不是"我要全局"。界面上的对应表现见 [management-ui.md](management-ui.md)。

### 引导与迁移

- 引导（首次建立管理员）与开发种子**登记自己使用的范围**。否则一个新部署的范围目录是空的，引导管理员登录后连"我在哪些范围里"都无从选起——这与"引导管理员的默认作用域必须一起设置"是同一类坑。
- 从"作用域只是字符串"升级到登记表的既有部署，**在升级时把已在使用的范围补登进去**（绑定上的范围与主体的默认作用域），使目录开箱即反映现状。

## 边界与约束

本模块**不处理**：

- 判定语义：作用域怎么包含、怎么参与判定，见 [enforcement.md](enforcement.md) 与 [role-model.md](role-model.md)。**判定路径不读登记表**，这是本模块最重要的边界。
- 租户/项目树怎么划分：划分仍由部署决定（登记哪些路径、层级怎么切）。本模块只提供"登记过哪些"这一份事实。
- 展示名的生效范围：它只是展示，不参与判定、不参与匹配，因此两个范围可以重名。

约束：

- 删除是引用完整性约束的唯一入口，与角色删除的占用校验同属一类。
- 作用域数量与层级深度需在上限内（阈值在实现时确定并记录），避免列举与展示失控。

## 可验证性与长程执行

**非长程任务。** 登记与删除都是一次请求一次结论，不做多阶段推进；删除前的引用校验在受理阶段完成，不通过即终止、不产生任何持久化影响。

需要保证的是**引用可信**与**判定不受影响**，由测试而非运行时机制保证：

| 核查项 | 判据 |
|--------|------|
| 未登记不可绑定 | 授予一个未登记的范围被拒绝；全局始终可授 |
| 回收不受影响 | 对未登记范围（历史数据）的回收仍然成功 |
| 删除要干净 | 有绑定落在范围内或其后代上时删除被拒绝，并给出条数 |
| 判定不读登记表 | 判定与权限展开的结果不随登记表的内容变化 |
| 引导自足 | 引导与种子跑完后，目录里至少包含它们使用的范围 |
| 升级可续 | 升级后既有绑定上的范围都已登记 |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 角色与权限模型 | 复用"标识不可改、名称可改""删除前校验引用"两条既有规则，不新造 |
| 鉴权决策 | 登记表**不参与**判定；删除校验发生在管理面，不是判定 |
| 持久化存储 | 经 `rbac.MutableStore` 读写登记表；包含语义复用 `internal/rbac/scope.go` 的唯一实现 |
| 前端与命令行 | 顶栏的候选、授予时的目标范围都来自这份目录 |
