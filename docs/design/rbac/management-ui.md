# RBAC — 权限管理界面

## 背景与目标

描述 Web 上**管理面**（角色定义、人员授权）的取舍：界面在哪儿提"范围"、怎么给人授角色、哪些话不该出现。

本模块要解决的问题是**术语串台**。仓库里有三个都叫得上"范围/域"的东西，它们在界面上一旦混成一个自由文本输入框，管理员就会把它当成"业务域/产品线"，进而认为改它自己就被限制在某条产品线里——而它实际决定的是**这次判定在哪个范围上做**。三者区分如下。

| 叫法 | 是什么 | 由谁决定 | 改它会怎样 |
|------|--------|---------|-----------|
| **管理范围** | 当前主体这次在哪个范围上操作（Web 顶栏） | 调用方显式指定，随请求提交；留空则回落到凭证默认作用域 | 之后所有管理操作与权限展开都在这个范围上做。范围是层级路径，父包含子；「全局」覆盖一切 |
| **凭证默认作用域** | 签发会话时冻结在凭证里的那个范围 | 签发时确定，调用方改不了 | 只有**自服务类**方法按它鉴权（如"查我自己的权限码"）。它不是"我能管的范围" |
| **权限码的「领域」** | 权限码三段式里的第一段（`rbac`、`galaxy`） | 权限目录（`api/permissions/catalog.yaml`） | 与范围毫无关系，它只表明这个权限属于哪个功能域 |

成功衡量：一个没读过 RBAC 设计的管理员，能自己完成"选范围 → 给某人绑角色 → 看懂角色是什么"；并且不会把顶栏理解成业务域，也不会去找一个不存在的"当前产品线"。

## 功能行为

### 顶栏：管理范围

- 顶栏控件回答的问题是"**我在哪个授权范围下工作**"，它的标题就叫**管理范围**，不叫裸的"作用域"。
- 候选项来自**当前主体自己的角色绑定范围**（他的绑定在哪些范围上，那些范围就是他最可能管理的范围）；候选不够时允许直接手输路径。列不出绑定时（没有读主体的权限、主体还没登记、这次读取失败）不给任何候选，只留手输，并在提示里说明可以手输。
- 范围**留空表示"不指定"**：会话查询会回落到凭证的默认作用域，并把实际使用的那个回传回来。因此框里显示的是**解析结果**，而不是用户敲进去的字面量——这也正是"随手填个范围就把自己关在门外"不可能发生的原因。
- 界面上一律显示「**全局**」；空值与「全局」是同一个意思的两种写法。`<global>` 这类内部写法不出现在面向使用者的文字里。
- 它必须带一句解释：范围是层级路径、**父包含子**、最上层是「全局」，以及它与权限码「领域」不是一回事。
- 改管理范围等同于**会话权限变更**：必须重新获取权限码集合（见 [frontend-permissions.md](frontend-permissions.md)），不允许沿用旧集合。

### 人员授权

- 它回答"**某个主体持有哪些角色**"，并支持授予与回收——这是此前只存在于命令行的能力。
- 查询以**主体标识**为键。服务端没有"主体标识 → 可读名字"的解析入口，因此界面必须说明这一点，不能让管理员以为输错邮箱是查询失败。
- 回收**不需要二次确认**：它可以被重新授予，属于可撤回的操作（见 [../uiux/README.md](../uiux/README.md) 的"破坏性操作"）。
- 授予时可选范围，初值取当前管理范围。

### 角色定义

- 角色是**全局定义**，全库只有一份。角色页因此不随管理范围过滤。
- 管理范围在这里的作用只有一件：**判断调用方有没有资格在这个范围上读角色**。切换范围，列表内容不变，变的只是"还能不能读"。
- 因此角色页必须把这句话写在界面上；只把顶栏和表格摆在一起、不解释它们的关系，会被读成"改了范围筛选了列表"。
- 界面上不出现没有真实语义的动作。名称像"发布"、实际只是重新读取的按钮一律不出现。

### 管理面的作用域约定

- **管理面（`rbac.proto`）的范围一律取自请求体里显式的范围字段**，不从请求元数据（`aladdin-scope` 头）取。这条不是风格：管理操作的"在哪个范围上做"必须是被调用方明确写下来的，否则一次漏传就会静默落到全局范围上，看起来像"权限不够"。
- 前端不发送 `aladdin-scope` 头。该元数据来源目前没有任何方法使用；**保留**这个来源是刻意的——它是注解里合理的第三种形态，将来会话级调用可能用得上，而删掉它要动拦截器与既有测试，换来的只是少一个没人走的分支。
- 约定由构建期测试强制（见下方可验证性表），不靠人记。

## 边界与约束

本模块**不处理**：

- 判定本身：三元组怎么判、范围怎么包含，见 [enforcement.md](enforcement.md) 与 [role-model.md](role-model.md)。
- 认证："你是谁"由身份认证模块负责。
- 业务资源的可见性（如"只能看到自己创建的工程"）：那属于资源归属，不由 RBAC 表达。

已知边界（本轮不做，记录以免被当成遗漏）：

- **不校验"授予了超出自己持有的权限"**。能不能授予由 `rbac.subject.assign` 决定，与目标角色的权限内容无关，因此管理员可以授予自己并不持有的角色。加这条护栏属于**新的判定语义**，应作为独立设计推进，不能顺手塞进界面。
- 不提供"按管理范围列出全部绑定"的视图。当前只有"按主体查绑定"；要让管理员看到"这个范围内谁被授过什么"需要新增管理面查询，属于独立改动。

## 可验证性与长程执行

**非长程任务。** 管理界面的写入是一次请求一次结论，不做多阶段推进。

需要保证的是它与服务端的**语义一致**，由测试而非运行时机制保证：

| 核查项 | 判据 |
|--------|------|
| 角色列表不被范围裁剪 | 同一主体在两个不同范围上列出角色，得到同一份全集（服务端测试） |
| 管理面范围取自请求体 | `rbac.proto` 的每个方法都声明范围来源为请求字段（构建期测试） |
| 顶栏不出现内部写法 | 界面渲染的是「全局」，源码里不以 `<global>` 作为展示文案 |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 角色与权限模型 | 管理的是它定义的角色与绑定；不复制其语义 |
| 鉴权决策 | 管理面方法自身同样受权限码约束，判定复用同一条链路 |
| 前端权限码集合 | 顶栏改范围后必须重新获取；界面裁断只做集合成员测试 |
| 会话签发 | 凭证默认作用域只在签发时确定，界面不修改它、也不拿它当管理范围 |
