# 服务端推送（事件通道）

> 本文档是**"某个资源变了，怎么通知到别的客户端"**的唯一信源，当前被 galaxy 工作台消费。
> 它描述的是一条**连接级**的通道：**一条连接承载所有主题**，各业务只是往它上面加主题——不是每个业务各开一条流。

## 背景与目标

galaxy 的内容由**命令行写入**、**网页工作台只读展示**（见 [galaxy/authoring.md](../galaxy/authoring.md)）。工作台此前只在「页面重新可见 / 窗口重新获得焦点」时重拉草稿，因此**这一页开着不动时，别处 `push` / 存版本 / 发布产生的变化不会出现**——只能整页刷新。

这也不只是"少了一次刷新"：工作台上那份「这份草稿能不能发布」的结论是**关于另一份字节的**，而纯前端的状态无法表达「跨客户端陈旧」——它连"我看到的草稿已经不是服务端的那一份"都无从知道。同一个问题在更多场景复现（多标签、多设备、以后的协作），因此要修的是一条**服务端推送的工程级事件通道**。

**要修的是一次，不是一个页面。** 这条通道是**连接级**的：一条连接上可以订多个主题，下一个要推送的业务（另一类资源、另一个面板）只加主题，不再各开一条流、各写一遍重连与退避。判断这条设计是否成功的标准之一，就是**新增一个可订阅资源时，不需要动通道本身**。

成功的衡量标准：

1. 工作台打开时订阅它正在看的那个工程；别处 `push` 同一工程后，**无需刷新页面**，状态条与预览在约定时间内跟上。
2. 事件**不含正文、不含文件字节、不含短时地址**，也不含"变了什么"——它只说"这条主题变了"。
3. 客户端**不会静默停在旧状态**：它订着的主题上的变更不会被漏掉（合并后交付），而断线期间的变更由重连时每个主题各一条的 `RESYNC` 覆盖。
4. 没有相应权限就订阅不到那条主题；凭证失效或**被吊销**后，流在约定时间内结束。
5. 走既有的 Connect（同一端口、同一份业务实现、同一条鉴权链路），**不新增第二种推送协议**。
6. **事件是提示，不是事实**：客户端的正确性不依赖收到任何一条事件。
7. **新增一个可订阅资源 = 在属主模块注册一个主题类型**：通道、信封、服务端循环、前端重连都不动（见"主题"一节）。

## 功能行为

### 形状：一条连接，多个主题

客户端开一条流，在请求里给出它要订阅的**主题集合**；之后这些主题上发生的任何变化都会从这**同一条流**推过来，每条事件用 `topic` 标出是哪一条。

**主题是一条字符串**，形如 `<类型>/<资源标识>`，例如 `galaxy.project/prj_3fK9…`。

**订阅集合变了就重开一条**（切页、关掉某个面板）。这一点是刻意的：连接内改订阅要求双向流，而双向流要求**端到端 HTTP/2**——见下面"为什么不做双向流"。重开的代价是每个主题各重拉一次，而重连与退避本来就要有（见"流什么时候结束"），因此这只是一条既有路径的复用。

**为什么不推内容。** 正文与资产字节经直传进入对象存储、以短时地址下发（见 [objectstore/README.md](../objectstore/README.md)），在事件里推内容会立刻引出第二套地址、第二套大小上限与一套分片与背压处理——而这些都是既有 unary 入口已经解决的事。收窄成"这条主题变了"之后，事件的大小与内容体积无关，且永不过期。

于是客户端收到事件后调的是**既有的**读取入口：`GetProject` / `GetDraft` / `ListVersions` / `ListAssets` / `ValidateDraft` / `PreviewDraft`（见 [galaxy/README.md](../galaxy/README.md)）。**通道只负责"喊一声"，读取仍然只有那几条路。**

### 时序：先订阅，再逐个主题全量拉一次

```
  浏览器工作台                                     服务端
       │                                               │
       │  Watch(topics = ["galaxy.project/prj_…"])  ──▶  逐主题：鉴权 + 归属
       │                                               │  订阅这些主题
       │  ◀────────────────────  RESYNC（该主题）      │   ← 每个主题各一条
       │  GetDraft / ValidateDraft / PreviewDraft … ─▶
       │  ◀────────────────────  当前状态              │
       │                                               │
       │                                               │   ← 别处 push 了这个工程
       │  ◀────────────────────  （该主题变了）        │
       │  GetDraft / ValidateDraft / PreviewDraft … ─▶
       │  ◀────────────────────  新的状态              │
```

> 时序图（一次订阅与一次变更）。它省掉了重连、心跳与上限寿命，那些在下面几节。

**每个主题订阅成功后的第一条必须是该主题的 `RESYNC`，这不是礼节而是正确性的一部分。** 客户端在连接建立之前无法知道"我已经同步到哪一刻"——「上一次拉取完成」与「订阅建立」之间落下的那次改动，没有任何别的机会被补上。把第一条固定成"无条件重拉一次"，这个窗口就不存在了。

因此客户端在收到某个主题的 `RESYNC` 之前**不认为该主题已同步**，收到之后的动作与收到任何一条该主题的事件完全相同：重拉它。

### 交付语义：按主题合并——不漏、可重复、不重放

**一条主题上的连续变化会合并成一次提示**：对订阅者来说是同一件事——再拉一次。由此得到三条，它们一起构成这份契约：

1. **不漏**：只要还订着这条主题，它的变更**至少**会被报一次。合并意味着"还没被取走的那次变更"被后来的合并掉，而不是被丢掉；而待取集合的大小以**订阅的主题集合**为上限，所以订阅者再慢也不会积压到丢东西。
2. **可重复**：同一条主题可能被报到不止一次（先报到的那次你还没取走，又来了新的）。重复是无害的——重拉是幂等的。
3. **不重放**：断线期间发生的变更**不会补**。它由重连覆盖：重连之后服务端为每个主题各发一条 `RESYNC`（见上一节）。

**为什么不做重放缓冲。** 补一段"离线期间的变化"需要服务端维护一个可比对的序号加一段缓冲——那既加了常驻状态，又**仍然盖不住**离线时间超过缓冲的客户端；而要求客户端自己比对版本号，会引出"多久没对上算太旧"这个没有好答案的问题。补上来的收益只是**省一次幂等的重拉**。

**也不做去重。** 没有可比对的序号，因此重复的事件只会导致重复的幂等拉取；而拿到序号要付出的代价（服务端维护一个在重启与多副本下都有意义的单调值）远大于它省下的那几次拉取。

由此得到客户端契约，只有一条：**收到任何一条事件、以及任何一次（重）连接成功之后，都重拉一次受影响的主题。** 事件只带 `topic`，不带"变了什么"，因此"受影响的主题"就是事件上写的那一个。

### 事件里为什么没有"变更类别"

早期草案里每条事件还带一个类别（草稿变了 / 新版本 / 已发布…）。**去掉了**，理由是它换不来什么：

- 客户端要做的事与类别无关——不管变了什么，都是"重拉这条主题的现状"，而那条路是幂等的、廉价的（工作台的重拉本来就是一次整组读取）。
- 一旦留下它，它就要被所有消费方解释，于是**共享的信封里出现各业务的词表**：要么退化成字符串（前端拿不到 proto 生成的枚举），要么在共享包里放一个随业务增长的 oneof（每加一个业务都要改共享包，与衡量标准 7 相冲）。

极少数确实需要区分"变了什么"的消费方（例如将来命令行要打印"新增了 v3"），可以在自己的业务里比对两次读取的结果——那不需要协议承担。

### 主题：谁定义、谁判权

**主题类型由**它所属的那个业务**定义与注册**，通道（以及 events 模块）不认识任何具体业务：

| 谁 | 做什么 |
|----|--------|
| 属主模块（如 galaxy） | 注册一个主题类型：类型名、订阅它所需的权限码、以及"这个主体能不能看这个具体资源"的判定 |
| 通道 | 收到订阅时按类型名前缀找到注册项，先按权限码判权，再调属主的判定 |
| 属主模块 | 在写路径成功之后，往这个主题上发一条事件 |

**归属判定复用属主自己的读取入口**（galaxy 用 `GetProject`），因此"不是他的"与"不存在"返回同一个结论这条既有的反枚举约定，在订阅上同样成立。

**订阅的粒度是一次请求里的整个集合，判定失败即整条流被拒。** 不做"跳过订不上的那几条"：静默少订一个主题，客户端会以为自己是最新的——那正是这条通道要消灭的状态。

### 一条明确的例外：订阅的权限不写在方法注解上

本仓库的硬性约定是"**受控接口的权限声明写在 proto 的方法注解上**，不在拦截器里逐条硬编码"（见 [AGENTS.md](../../AGENTS.md)）。**这条约定在多路复用的通道上表达不了**：需要哪个权限取决于请求里订的是哪条主题，那是数据，而注解是静态的。

因此这里是一次**刻意的、有边界的例外**：

- 通道方法本身声明为**只需认证**——它没有任何一条能代表"所有这些主题"的权限码；
- 逐主题的权限码仍然取自[权限目录](../../api/permissions/catalog.yaml)（不得手写字符串字面量），判定的**唯一实现**仍然是 `rbac.Engine.Check`；
- "哪条主题需要哪个权限码、归属怎么判"由属主模块注册在一处，通道只查表，不自己维护任何业务到权限的映射；
- **代价如实写下**：文档（OpenAPI）与前端从此拿不到"订阅这条主题需要什么"这一事实——它只存在于属主的注册项与本文档里。前端的权限裁剪仍然按页面/动作走既有的权限码（见 [../rbac/frontend-permissions.md](../rbac/frontend-permissions.md)），不依赖这条。

### 谁能开流、流什么时候结束

**开一条流只要已认证**（见上：权限是逐主题的）。**鉴权在开流时做一次**（认证 + 逐主题判定），之后流是长连接，不会为每条事件再判一次——这是长连接与 unary 在安全上唯一的实质差别，因此需要一条明确的吊销策略：

- **流有上限寿命（半小时量级）。** 到点服务端主动结束，客户端重连时**重新鉴权**。因此"凭证在流开着时被吊销或过期"的暴露窗口不超过这个上限。
- **不做流内周期复验。** 那需要在每条流上多一条常驻的定时路径，而它换来的只是把窗口从"半小时"压到"更短"——对一个有效期以天计的会话来说，这个收益抵不过多一条常驻路径的代价。

**心跳。** 服务端周期性发一条控制事件，它有两个用处：让反向代理不把空闲连接判死（nginx 的 `proxy_read_timeout` 默认 60 秒，见 [../../deploy.md](../../deploy.md)），以及**给客户端一个可以判活的信号**（见下节）。**心跳不是一次变更**——它不引起任何重拉，但它证明这条连接还是通的。它按连接发，不带主题。

**进程退出时主动结束所有流。** 不这样做的话，每次停服都要等满在途请求的宽限时间。

### 订阅者跟不上时：合并，而不是丢弃，也不掐连接

**写路径永不因为订阅者而阻塞**——写入是别人正在等的操作，订阅者只是看客。它只往订阅者的**待取集合**里记一项（同一主题重复报到会被合并）并摇一次铃。

于是"订阅者慢"这件事没有失败模式可言：待取集合的大小以它订的主题数为上限，所以它既不会因为积压而丢变更（见"交付语义"的"不漏"），也不会因为积压而被断开。**它只是晚一点知道。**

### 页面隐藏时：保持订阅；连接死了客户端自己发现

**页面不可见时不退订。** 退订等于把本次要修的陈旧重新引回来，而换来的只是省下一条空闲连接。

**但"这条流还活着"不能由"对面没报错"推断。** 半开的连接——笔记本睡眠、NAT 表项过期、中途换网——**两边都不会报错**：服务端的心跳写不出去（它只是重传），客户端也永远读不到任何东西。**不报错就不会重连，不重连就没有 `RESYNC`**，于是这一页可以无限期停在旧状态上。浏览器冻结后台标签页只是触发这件事的一种方式，不是它的全部。

因此**客户端按心跳判活**：多久没从这条流上收到任何东西（心跳也算）就主动断开，走既有的重连路径——重连之后每个主题各一条 `RESYNC`，那段静默窗口就补齐了。

这比"回到前台再主动重拉一次"好在三点：

- **它判的是连接的死活**，而不是"用户有没有看向这一页"。后者与连接状态之间的相关性很弱：页内换一次焦点就会误触发一次全页重读（见 [../../debugging/records/2026-10-07-preview-reloads-on-page-internal-focus.md](../../debugging/records/2026-10-07-preview-reloads-on-page-internal-focus.md)）。
- **它覆盖"用户根本没离开过"的情形**：僵尸连接在有人一直盯着这一页时同样不会自己好。
- **被冻结的标签页不必单独照顾**：定时器在页面恢复时会立刻到点，重连与 `RESYNC` 照常发生。

于是**"重新可见 / 重新获得焦点时主动重拉一次"这条兜底取消了**——它原先要挡的每一档，都由"隐藏期间不退订（事件照常交付）"与"判活发现死连接（重连即 `RESYNC`）"覆盖。多留一条靠猜的路径，只是多一个它会猜错的场合。

## 边界与约束

- **只做服务端流，不做双向流。** 双向流要求**端到端 HTTP/2**（connect-go 在响应的协议版本上直接检查），而本仓库的部署形态在 nginx 那一跳是 HTTP/1.1 转发（`/aladdin.` 那一条，见 [deploy/nginx-aladdin-site.conf](../../deploy/nginx-aladdin-site.conf)）；nginx 的 `proxy_pass` 对上游只能发 HTTP/1.0/1.1，能发 h2 的 `grpc_pass` 只讲 gRPC，而浏览器那侧的 gRPC-Web 规范不支持双向流。**这不是"能不能改"的问题，是改它要动代理层与浏览器能力**，而它换来的只是"连接内改订阅"——那个动作另有代价更低的实现（重开一条）。
- **事件不得承载正文、文件字节、短时地址，也不得承载"变成了什么"**（见上文两节各自的理由）。
- **流式方法不得把作用域声明为从请求字段取。** 流式拦截器拿不到那一条请求消息（框架在它之后才读），因此"作用域从请求字段来"在流上不可表达。**这条由一个不变量测试固定**，而不是靠约定。
- **订阅的权限不写在方法注解上**，这是一条有明确边界的例外，理由与代价见上。
- **不持久化、不重放、不跨副本。** 事件通道不是审计日志：没有历史、不可查询、进程重启即丢失（P0 单机；多副本见"待定决策"）。
- **反向代理必须关闭响应缓冲**，否则事件被攒在代理里，表现是"事件不来"或晚来一大批；**心跳周期必须小于代理的读超时**。两条都是部署形态的硬要求，不是调优。
- **心跳也是客户端判活的唯一信号**（见"页面隐藏时"），因此心跳周期同时是"客户端多久才发现一条死连接"的下界——它调大，客户端发现得就晚。
- **通道不改变任何读取路径的契约**：它不缓存、不代理字节，客户端拿到事件后走的仍是既有入口。
- 订阅数没有按主体的配额（见"待定决策"）；单条订阅的资源占用由"待取集合以主题集合为上限"与上限寿命两条共同封住。

## 可验证性与长程执行

**非长程任务。** 推送与重拉都是即时的同步操作；一条订阅的寿命有上限，它是**连接的寿命**，不是一次需要推进与恢复的长程任务。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 事件不含内容 | 事件消息的字段只有主题与控制类别；任何一条都不带正文、字节、地址或"变成了什么"（代码审查 + proto 定义） |
| 订阅后每个主题各一条 RESYNC | 请求里订 N 个主题，收到的前 N 条是按主题各一条 RESYNC（`internal/server` 测试） |
| 一次连接承载多个主题 | 同一条流上收到的两条事件分属两个不同主题，且客户端只开了一条流（`internal/server` 测试 + 前端测试） |
| 每一次改变状态的写入各发一个事件 | 逐个写路径：成功后恰好一条、主题正确（`internal/galaxy` 测试） |
| 写失败不发事件 | 校验拒绝与存储故障都不产生事件（同上） |
| 同一主题的连续变化只交付一次 | 连发 N 次只取到一项，且订阅者不会被断开（`internal/watch` 测试） |
| 未知主题类型被拒 | 订阅一个没注册过的类型前缀即开流失败（`internal/server` 测试） |
| 没有该主题的权限就订阅不到 | 缺少 `galaxy.project.read` 的凭证订阅工程主题被拒（`test/e2e`，两条协议） |
| 不是你的主题与不存在同结论 | 订阅别人的工程返回与订阅不存在的工程相同的结论（`test/e2e`） |
| 没有凭证开不了流 | 匿名开流被拒（`test/e2e`） |
| 流有上限寿命 | 到点服务端主动结束该流（`internal/server` 测试） |
| 连接死了客户端自己发现 | 一条先发心跳、随后再也不发的假流上，超过判活阈值没有收到任何东西时客户端主动断开，重连之后依 `RESYNC` 重拉（前端测试） |
| 判活阈值远大于心跳周期 | 客户端的判活阈值与 `watchHeartbeat` 对照：至少容得下若干个心跳周期（代码审查） |
| 心跳周期小于代理读超时 | 心跳周期与部署模板里的读超时对照（代码审查 + [../../deploy.md](../../deploy.md)） |
| 关停即结束所有流 | 停服时在途的流被主动结束，不等满宽限时间（`internal/server` 测试） |
| 两条协议结论一致 | grpc-go 与 Connect 各开一条流，`push` 之后都能收到事件（`test/e2e`） |
| 新增一个资源不动通道 | 加一个主题类型只需要在属主模块注册 + 在写路径发事件；通道、信封、服务端循环、前端重连都不用改（代码审查） |
| 不刷新页面即更新 | 工作台开着时命令行 `push` 同一工程，状态条与预览在约定时间内更新（前端测试 + 部署后冒烟） |
| 前端不复写判定 | 事件到达后走既有 unary 入口取结论，不在前端推断内容对错（前端测试） |
| 流式方法不从请求字段取作用域 | 遍历方法描述符：任何流式方法声明该来源即失败（`internal/rbac` 测试） |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| galaxy 创作与发布 | **第一个消费方**：注册 `galaxy.project` 主题类型，写路径往它上面发事件（见 [galaxy/README.md](../galaxy/README.md)） |
| RBAC | 通道方法声明"只需认证"；**逐主题的权限码取自权限目录，判定仍只有 `rbac.Engine.Check` 一处实现**（见 [rbac/](../rbac/README.md)） |
| 身份认证 | 认证与逐主题判定在开流时完成一次；**流的寿命上限界定了凭证吊销的暴露窗口**（见 [identity/session-token.md](../identity/session-token.md)） |
| 持久化 | 不涉及：事件不落库 |
| 可观测性 | 一条流在请求日志里仍是一行（在结束时记持续时间）；事件不含内容（见 [../../observability.md](../../observability.md)） |
| 命令行 | 命令行是**写入方**（事件的产生者），当前不消费事件（它的客户端已能覆盖流式调用） |
| 部署 | 反向代理须关响应缓冲、读超时须大于心跳周期（见 [../../deploy.md](../../deploy.md)） |
| Web 界面 | 工作台按主题订阅它正在看的那个工程（见 [galaxy/authoring.md](../galaxy/authoring.md)） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 连接的生命周期 | 跟着页面走（页面挂载即开，卸载即关）。要跨页面常驻就把订阅集合提到应用层（**未定**） | 只动客户端：协议面不变（集合本来就在请求里） |
| 多副本 / 水平扩展 | 进程内总线，单副本。**多副本下同一主题的订阅者可能不在同一个进程**，届时要换成跨进程的投递（Redis pub/sub、NATS 一类）（**未定**） | 只换总线的实现；"事件不落库、不重放"这条语义不变 |
| 上限寿命与心跳的取值 | 上限 30 分钟、心跳 25 秒（前者界定吊销窗口；后者须小于代理默认的 60 秒读超时，同时决定客户端判活的精度）（**未定**） | 分别影响吊销窗口、代理兼容性与"客户端多久发现一条死连接"；两者都在代码里各有一处常量 |
| 双向流（连接内改订阅） | 暂不做，改订阅即重开一条（**未定**） | 要先把代理层换成能转发 h2c 的，再实测浏览器支不支持流式请求体；协议面变成双向 |
| 订阅的配额（按主体或按连接） | 暂不设（**未定**） | 属于资源保护：需要一个按主体或连接的计数与拒绝语义 |
| 其他资源的 Watch（设备码、资产库等） | 在属主模块注册主题类型即可，通道不动（**未定**） | 只影响属主模块与它的写路径 |
| 事件携带一个可比对的序号（跳过重复拉取） | 暂不做（**未定**） | 服务端要维护一个在重启与多副本下都有意义的单调值 |
