# skill — 目录、标签、收藏与统计

## 背景与目标

技能纳管进来之后，本子模块回答的是"**怎么找到它、怎么归类它、怎么知道有没有人在用**"。它管的是**说明层**——那一层不改变任何一份字节，却决定这个目录对读它的人是不是可用。

它要回答四个问题：

1. 一个技能对外展示的标题与简介**从哪里来**，管理员改了之后以谁为准；
2. 标签的规则是什么，筛选语义是什么；
3. 收藏是谁的属性，它改变什么、不改变什么；
4. "使用量"这个数字**到底是数的什么**——一个定义不清的计数会让它此后所有的解读都建立在猜测上。

成功的衡量标准：

1. 一个从没有说明层覆盖的技能，展示出来的标题与简介取自它自己的 `SKILL.md`——纳管之后不需要管理员再填一遍。
2. 管理员改了标题、简介或标签，**任何一份字节都不变**，当前版本、正文与取用结果逐字不变。
3. 按关键词与标签能搜到它，且**同样的筛选条件在任何一端、任何一次都返回同样的顺序**。
4. 收藏只影响收藏者自己看到的东西。
5. 使用量是一个**任何人看了都不会误解**的数字：它不因同一个 agent 多取几个文件而虚高，也不暴露是谁在用。

## 功能行为

### 两层：说明层与内容层

一个技能对外有两层，它们的可变性完全不同。不分开谈，"技能不可变"就会变成一句含糊的话：

| 层 | 内容 | 可变性 | 谁决定 |
|----|------|--------|--------|
| 内容层 | 文件树、版本、当前指针 | **不可变**（版本）/ 只由同步与回滚改变（指针） | 远端仓库 |
| 说明层 | 标题、简介、标签、展示图集 | **可变**。纳管之后随时可改 | 平台管理员 |
| 关系层 | 收藏、使用量 | 只随读的人的动作变化 | 读的人 |

**说明层永远不改内容层任何一项。** 改标题（或加一张展示图）不产生新版本、不动指针、不改任何一个字节——因此"这个技能的正文变了吗"这个问题永远只有一个答案来源：版本。

### 有效标题与有效简介

说明层的两个字段**可以留空，留空时回退到当前版本 `SKILL.md` 里的那一项**：

| 对外取值 | 从哪来 | 回退到 |
|---------|-------|-------|
| 有效标题 | 技能行上的标题 | `SKILL.md` 的 `name` |
| 有效简介 | 技能行上的简介 | `SKILL.md` 的 `description` |

这条回退的取向与 galaxy 资产"展示标题为空时回退到文件名"完全相同（见 [../galaxy/asset-library.md](../galaxy/asset-library.md)）：**空是一个判据，不是"内容是一个空字符串"**。由此得到三条：

- 纳管之后不需要管理员补一遍——远端已经写好了它自己的名字与用途；
- 要改就整体覆盖，**没有"部分清空到一半"**：写入表达的是**期望的完整状态**，空值表示"清空，回到回退";
- **回退取的是当前版本的那一项**。同步换了一个 `name` 不同的版本，没有覆盖过标题的技能展示名会跟着变——它是"这一份内容的自我描述"，内容换了它就换了。

**简介的长度上限是 1024 字符**（与 `description` 的上限相同），标题是 128 字符。都按**字符数**而不是字节数计，与工程名称、简介同一条理由：用户感知的长度是字数，按字节算会让"一段中文写到十几个字就被拒"成为一条需要解释的规则。

**关键词检索匹配的是有效标题与有效简介**，不是原始字段。两个字段都要能被搜到，因此"管理员改过一个更好懂的名字"这件事，搜索侧不需要知道。

### 展示图集（首图即封面）

技能有一组**展示图**：**第一张是封面**，用在目录的卡片上；整组用在详情页的画廊上（"它做出来是什么样"）。

它**属于说明层**：可改、不进版本、与内容层正交——加图、删图、换图、排序都不产生版本、不动指针、不改 `skipped_files`，与改标题同一条取向。

**它不是包的内容。** 技能包只收文本（见 [onboarding.md](onboarding.md)），展示图走的是另一条路；因此"包里的二进制被跳过"与"技能有一组展示图"是两件互不影响的事。这一点必须写清楚，否则很容易被读成"平台其实收二进制了"。

#### 列表只给首图，详情给全部

卡片是"一眼认出这是哪个技能"的场景（见"检索"），塞多图只会把卡片变成轮播；而"它做出来是什么样"是详情页的问题。因此：

- **列表**只下发首图那一个地址，不因为没有第二张而少给什么，也不因为图集有十张而多签九次；
- **详情**下发整个图集，顺序与管理员设定的一致。

一条技能的"当前展示图集"只有一处答案：挂在它下面的那组图。没有图时保持占位行为（标题首字 + 中性底），不引入默认图。

#### 两个来源，同一组落点

| 来源 | 怎么走 | 谁写字节 |
|------|-------|---------|
| 纳管时指定（`--image <包内路径>`，可重复） | 服务端从**已经取回的那棵树**里逐张取回，顺序即给定顺序 | 服务端 |
| 界面/客户端直传 | 直传三步：签发 → 直传 → 提交，**逐张一次** | 客户端直传（服务端不碰字节） |

两条来源落到**同一组图**上，因此"这个技能有哪些展示图"也只有一处答案。

#### 图标识、顺序与键

- **一个技能最多 12 张**，每张有一个**图标识**：由服务端分配、不可猜、不可改、不复用。
- **对象键按图标识走**（`<技能标识>/<图标识>`），一张一个键。它与内容对象（按内容摘要寻址、跨技能共享、不删）是两回事——展示图是"这个技能当前展示的这几张"，不是要被版本钉住的事实。
- **顺序与地址无关。** 图集有确定顺序，顺序是它自己的一个事实，不是对象键的一部分。由此得到四条：
  - **重排不改任何一张的地址**；
  - **删中间一张不改其余任何一张的地址**：删的是那一条记录与它那一个对象；
  - **换图（同一张换字节）就地覆盖**：键不变，不产生孤儿对象；
  - **删技能时图集的对象一起删**（每个键都由这一个技能独占，不像内容对象那样可能被别处引用）。
- **"设为首图"就是把某一张排到第一位**——它是决定卡片显示哪一张的唯一入口，没有第二个开关。
- 换图的取图地址在有效期内指向的**可能已经是新那一张**（与头像同一个代价，也同一个理由：换的是"当前"）。

#### 类型与上限

**单张的类型与大小沿用与头像共用的那一份白名单**（PNG / JPEG / GIF，2 MiB，不含 SVG）：它们问的是同一个问题——一张会下发给浏览器的展示小图，收哪些格式。实现只有一处，见 [../../ssot-registry.md](../../ssot-registry.md)。

本模块只新增一组**"张数 + 合计字节"**的上限（12 张 / 合计 12 MiB），且**只在服务端一处判**：

- 纳管时超限 → **拒绝整次写入**，与别的校验同一条：不留"进来一半"的状态；
- 直传时超限 → **签发就拒**（按声明早退），**提交时再按真实字节数复核一次**——声明可以撒谎，而服务端在提交那一步做了 Head，看得见真实的字节数。

这组上限与包契约那几项一样**随能力下发点给出**（界面据此把"最多几张、一张多大"讲在管理员动手之前，客户端不猜），但判定仍然只在服务端一处：前端拿到的是一个用来写文案的取值，不是一道闸门。

**两条来源的校验强度不同，这是直传的已知代价**：

| 来源 | 服务端看得见字节吗 | 校验 |
|------|------------------|------|
| 直传 | 否（直传） | 只看**声明的**类型在白名单内、声明的大小在上限内，真正的边界由存储侧按策略执行——与头像完全一致 |
| 纳管时指定 | **是**（服务端自己取回） | 扩展名看着是图 + 大小在上限内 + **核对文件头**（PNG / JPEG / GIF 的魔数） |

**看得见就验一次，看不见就只信声明。** 这条对照是刻意的，不是一处疏漏：把"看不到字节"说成"验证过了"才是问题。核对魔数换来的是——一张扩展名是 `.png` 而内容不是图的字节，进不了平台。

#### 逐张独立，不做整组原子

一次加好几张图时，每一张各自走完"签发 → 直传 → 提交"：**提交第 3 张失败时，前两张已经在图集里可见**。这是刻意的，不是一致性上的疏漏——一次上传好几张要浏览器连着传，任何一张失败都回滚全部，等于让一次网络抖动把已经传好的字节也丢掉。

由此得到三条失败语义：

- **提交时对象不在**（没传完、没传）即失败，图集不变。那次失败唯一的残留物是桶上一个无引用的对象（与"行写失败留下一份无引用的内容对象"同一种残留）；
- **换图没有"先检查后写入"的余地**：它是就地覆盖，字节落上去就回不去。因此合计超限时服务端**先把真实字节数记下来**（库里的那一行必须与桶上一致），再报"超出多少、请先删掉别的一张"——报错的那一次已经生效，这一点写在错误信息里，不让管理员以为它被回滚了；
- **重排是整体替换**：请求给出的是期望的完整顺序，给出的不是当前图集的一个排列时整个拒绝（少了、多了、重复、别人的都算）。它一次写入，不存在"排到一半"。

#### 下发

- 每张图的地址是**短时有效的预签名地址**（与头像同一条模型、同一个有效期）。**详情给全部，列表只签首图那一张**——签名是本地计算、不发网络请求，因此签名量不随图集张数增长。
- **空图集表示没有封面**，界面据此渲染占位，不引入"默认图"这类二进制资源。
- 未配置对象存储时图集整体不可用——与目录同一条降级取向。

### 标签

标签是**平台级的自由字符串**，供检索与归类。

| 约束 | 取值 |
|------|------|
| 单个标签长度 | ≤ 32 个字符 |
| 每个技能的标签数 | ≤ 16 个 |
| 归一化 | 去首尾空白、统一小写、去重、按字典序排 |

**归一化的实现只有一个入口**，与 galaxy 资产的标签是同一处（见 [../galaxy/asset-library.md](../galaxy/asset-library.md) 的"可编辑元数据"）。同一串标签在两处被归一化成不同的样子，表现是"这个标签看着对、就是筛不出来"——这正是 SSOT 原则要挡住的那类问题。

**标签不是一个全局字典。** 平台不维护"合法标签清单"，不提供"标签管理"页面，也不把标签做成权限资源：它是给人和检索用的词，不是一套需要治理的对象。因此**候选标签来自目录本身**（现有哪些技能带了哪些标签），不来自某个配置。

**不支持"未打标签"这类否定筛选。**

### 收藏

收藏是**主体对技能**的一个标记，等价于"我把它放进我的常用里"。

- **任何能读目录的主体都能收藏**（不发单独的权限码）。它不改变目录内容、不影响别人、不放大任何能力——一个只有读权限的人能做的事，收藏没有超出它。
- 入口表达的是**期望的完整状态**：给出目标值，为真表示收藏（已收藏时是空操作），为假表示取消（未收藏时是空操作）。两个方向都不需要"先查一下现在是什么"，也因此没有"收藏两次变成取消"这类要靠调用方小心的形状。
- **列表返回调用者自己的收藏状态**，`favorited_only` 只看自己收藏的那些。
- **收藏不改变排序。** 排序必须确定（见下），而"我收藏的排在前面"会让每个人看到的顺序都不一样——那正是"同样的筛选条件返回同样的顺序"这条要挡住的东西。要只看收藏的就用筛选。
- **收藏不改变目录里有什么。** 它是读的人与技能之间的记号，不是对技能的编辑，因此不需要 `skill.catalog.write`。

### 使用量

**一次取用 = 一次成功的正文下发**（见 [agent-access.md](agent-access.md)）。计量点是那一个动作，且只有一个。

计数**按（技能，主体，日期）归并成一条日次**：

| 取值 | 含义 |
|------|------|
| 使用日次（最近 30 天） | 有几天、有几个人用过这个技能：同一个人在同一天里取几次都算一次 |
| 使用人数（最近 30 天） | 同期去重之后的主体数 |

**为什么按"人日"而不是按"次数"。** 一次取用会连着取好几个文件——正文是 `SKILL.md`，而它通常还会引用同目录下的别的说明。按次记的数字因此主要由"这个包有几个文件"决定，与"有没有人在用"无关；而按人日记的数字有两条它没有的性质：

- **它有天然上界**：一个主体对一个技能一天最多贡献 1。想把这个数字刷上去，唯一的方式是换更多的主体或等更多天——而不是写一个循环；
- **它与"多少个文件"无关**：包大小变了，同一个使用强度不会让数字跳一下。

**明细保留 30 天**，过期行在服务端启动路径上回收（与过期会话、客户端事件同一时机、同一条理由：回收发生在监听之前，早于任何请求）。因此读侧给的永远是 30 天口径的一个数，而不是"从有史以来"——后者要留着全部明细，而它换来的只是一个人越来越难解读的数字。

**读侧不返回"谁用过"。** 只返回上面两个计数与最近一次使用时间。使用明细**不是审计数据**：它不回答"谁在什么时候做了什么"，那是审计日志与客户端事件的事（见 [../../observability.md](../../observability.md)）。把它当审计数据读，会读出一个它本来就不打算回答的结论。

**计数失败不影响取用。** 计一次数失败了，正文照常返回——"统计不准"与"我拿不到技能"是两件事，前者不该让后者发生。

### 检索

**目录以卡片呈现**，不是一列条目：技能之间的差别首先在"看起来是什么样"，而这件事一排排读文字读不出来。**首图（封面）因此是检索界面的一半**——它让人一眼认出"我要的是那个出图的"，而标题与标签负责说清"它是干什么的"。没有图时渲染占位（标题首字 + 中性底），不引入默认图。

| 参数 | 语义 |
|------|------|
| 关键词 | 大小写不敏感的子串匹配，匹配**有效标题**与**有效简介**。去首尾空白；空表示不筛 |
| 标签 | 多值**取交集**：只列出同时带这些标签的技能。精确匹配（按归一化后的取值比较） |
| 只看收藏 | 只看当前主体收藏过的 |

**排序是确定的**：按**有效标题的字典序**，标题相同时按技能标识。没有"按相关度""按热度"这类排序——它们要么依赖一套只有搜索引擎才有的相关性模型，要么让列表随使用量变动而变动，而两者都会让"我上次看到的第三条"变成一个无法复现的位置。

**标签筛选在服务端做**，因此列表返回的标签候选是**整个目录已有**的标签，不随当前筛选收窄（与 galaxy 资产筛选同一条）。

**一次返回有上限（200 条），超出时置"还有更多"并由界面提示用关键词缩小范围。** 不做游标翻页：目录由管理员维护，规模有天然上界，而"翻到第几页"这件事在一个人维护的目录里没有用途。上限存在的意义只是让响应有界。

## 边界与约束

- **说明层不进内容层。** 改标题、简介、标签不产生版本、不动指针、不改任何一个字节。
- **检索不匹配正文。** 关键词只匹配有效标题与有效简介：正文是给取用者读的，把它拉进检索会让"这个技能是干什么的"淹没在"它提到了多少次某个词"里。要搜正文，取下来自己搜。
- **检索不匹配来源。** 仓库地址、引用与子路径不是目录的一部分，它们出现在详情里（见下），但不参与筛选。
- **只读侧不放大字段面。** 列表给的是"这一条是什么"，不含文件清单与正文；正文只有取用那一个入口能拿到。
- **不返回主体的使用明细**（见上）。
- **不做标签的重命名 / 合并 / 删除。** 标签只在技能的说明层里存在，改它就走改说明层；"平台级标签管理"是一套独立的对象治理，不在第一版。

## 可验证性与长程执行

**非长程任务。** 本子模块的每一个动作都是一次请求一次结论。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 回退取到位 | 没有覆盖过说明层的技能，列表里的标题与简介等于当前版本 `SKILL.md` 的 `name` 与 `description`（`internal/skill` 测试） |
| 回退跟随版本 | 同步到一个 `name` 不同的版本后，未覆盖过标题的展示名跟着变（`internal/skill` 测试） |
| 覆盖是完整状态 | 清空标题后展示名回到回退值；只给标签不给标题时标题不被清空（`internal/skill` 测试） |
| 说明层不动内容 | 改标题、简介、标签之后，当前版本、文件清单与所有字节逐字不变（`internal/skill` 测试 + 端到端测试） |
| 图集不进内容层 | 加图、删图、换图、重排之后，当前版本、文件清单与 `skipped_files` 逐字不变（`internal/skill` 测试 + 端到端测试） |
| 图集不在包的内容里 | 纳管时取自包的图进图集，但**不在文件清单里**、不改 `skipped_files`（`internal/skill` 测试） |
| 顺序与地址无关 | 删中间一张、重排之后，其余每一张的对象键逐字不变，且桶上不留无引用的对象（`internal/skill` 测试 + 存储契约测试） |
| 列表只签首图 | 列表返回的每条技能只有首图那一个地址；图集张数不改变列表的签名次数（`internal/skill` 测试 + 端到端测试） |
| 首图唯一 | 没有图时首图为空；有图时首图恒为顺序里的第一张（`internal/skill` 测试） |
| 存量封面被接住 | 升级之前只有一张封面的技能，升级之后那一张就是它的首图：图不变、地址不变，也不多出一条空图集（`internal/database/migrate` 测试） |
| 张数与合计有上限 | 超过 12 张、或合计超过 12 MiB 时纳管被拒、签发被拒；提交时按真实字节数复核（`internal/skill` 测试 + 端到端测试） |
| 重排是整体替换 | 给出的标识不是当前图集的一个排列时整个拒绝，顺序不变（`internal/skill` 测试 + 存储契约测试） |
| 删技能带走图集 | 技能删除后，它图集里每一个对象都不再存在；内容对象一个都不删（`internal/skill` 测试） |
| 失败与"没配置"分开 | 对象存储这一次失败时报"对象存储暂时不可用"、并在服务端留下原因；它与"这个部署没有配置对象存储"是两句话、两种结论（`internal/skill` 与 `internal/server` 测试） |
| 标签归一化同源 | 同一串标签在技能与 galaxy 资产上得到逐字相同的归一化结果（`internal/skill` 测试 + `internal/galaxy` 测试） |
| 标签超限被拒 | 长度、数量、空串、控制字符、路径分隔符各有一条用例（`internal/skill` 测试） |
| 标签筛选取交集 | 用两个标签筛选只得到同时带这两个标签的技能；候选标签是整个目录的而非当前结果集的（`internal/skill` 测试 + 端到端测试） |
| 收藏是私人的 | 一个主体收藏之后，另一个主体读到的该技能未被收藏（端到端测试） |
| 收藏幂等 | 连续两次收藏只留一条，连续两次取消不报错（存储契约测试） |
| 收藏不改排序 | 收藏之后列表顺序逐项不变（`internal/skill` 测试） |
| 关键词大小写不敏感 | 用与标题不同的大小写搜索能命中原条目（`internal/skill` 测试） |
| 关键词不匹配正文 | 只在正文里出现的词搜不到该技能（`internal/skill` 测试） |
| 排序确定 | 同一份数据反复查询、两个存储实现分别查询，得到逐项相同的顺序（存储契约测试） |
| 上限有界 | 目录超过上限时返回条数等于上限且置"还有更多"（`internal/skill` 测试） |
| 计数按人日 | 同一主体同一天连取多个文件，使用日次只增一次（`internal/skill` 测试） |
| 计数不漏主体 | 两个主体各取一次，使用人数为二（`internal/skill` 测试） |
| 计数失败不挡取用 | 计数写入失败时正文照常返回（`internal/skill` 测试） |
| 明细不回主体 | 列表与详情的返回体里不出现主体标识（`internal/server` 测试） |
| 过期明细被回收 | 超过保留期的日次行在启动回收之后不再存在（存储契约测试 + 服务端测试） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 按使用量排序 / "热门" | 暂不做（**已定**）。排序必须确定 | 需要一个稳定的热度定义与一套"热度变了列表就变"的界面说明 |
| 全文检索 | 暂不做（**已定**，见 [README.md](README.md)） | 引入索引与相关性排序 |
| 谁在用（审计视图） | 暂不做（**未定**，见 [README.md](README.md)） | 一个新的管理面方法与一条"使用明细算不算审计数据"的边界 |
| 标签字典化（别名、合并、受控词表） | 暂不做（**未定**） | 标签从"自由字符串"变成"一种要治理的对象"，随之而来的是它与权限、与检索的关系 |
| 收藏的分组 / 备注 | 暂不做（**未定**） | 收藏从一个标记变成一个小型收藏夹，需要自己的界面与上限 |
| 使用明细的保留期可配 | 不做，固定 30 天（**已定**） | 会让"这个部署的使用量口径是几天"变成一个要在别处解释的事实 |
