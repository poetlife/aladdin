# skill 模块总览

> 本目录是 aladdin **"平台提供一组辅助创作的技能，由管理员从 GitHub 纳管，创作者与 agent 检索并取用"** 这一能力的唯一信源。

## 背景与目标

aladdin 已有的四块能力各自回答一个问题：认人（[../identity/](../identity/README.md)）、判权（[../rbac/](../rbac/README.md)）、记这个人长什么样（[../profile/README.md](../profile/README.md)）、让用户做出东西并发出去（[../galaxy/](../galaxy/README.md)）。没有任何一块回答"**创作时用什么**"。

社区里已经有一批形态成熟的 skill（SKILL.md 加附属文件的目录，`description` 说明它什么时候该被用上）。把它们直接装进每个 agent 的本机 skill 目录（`~/.claude/skills`、Cursor skills 等）有三个问题：

| 问题 | 后果 |
|------|------|
| 真相源被复制成 N 份 | 平台想统一更新一处，得挨个机器去改；改没改到没人说得清 |
| 没有准入 | 谁往目录里丢一份都会被 agent 当作指令读进去 |
| 没有归属与计量 | "平台提供了哪些""哪些真的在被用"两个问题都答不出来 |

skill 模块补上这一块：**真相源在平台**，管理员从远端仓库纳管，创作者与 agent 按需检索与取用，**平台从不往任何一台机器写文件**。

它要回答四个问题：

| 问题 | 归属 |
|------|------|
| 一个技能是什么、由哪些字节组成 | **技能包与快照**（[onboarding.md](onboarding.md)） |
| 怎么把远端的一份拿进来、怎么更新、怎么退回去 | **纳管与同步**（[onboarding.md](onboarding.md)） |
| 怎么找到它、怎么标它、怎么知道有没有人在用 | **目录、标签、收藏与统计**（[catalog.md](catalog.md)） |
| agent 怎么用它、为什么不会污染本机 | **取用面**（[agent-access.md](agent-access.md)） |

成功的衡量标准：

1. 管理员给一个 `github.com/<owner>/<repo>`（可选引用、可选子路径），平台把它变成一条可检索的技能；**校验失败时库里不留任何痕迹**。
2. 一个技能的内容是**不可变快照**：更新产生新快照，回滚是切指针，老快照读回来逐字不变。
3. 持有读权限的主体能按关键词与标签搜到它、读到它的正文、收藏它、看到它有没有人在用。
4. **agent 能靠一条命令行把它取到自己的会话里，而调用方的文件系统上不会出现任何技能目录**——这一条是硬约束，见 [agent-access.md](agent-access.md)。
5. 技能正文**不被服务端执行**，也不被服务端解释：平台分发的是**文本字节**，纳管与取用两条路径上都不存在任何执行入口。
6. 未配置对象存储时技能目录整体不可用，而其余模块照常——与 galaxy 的资产同一条降级取向。

## 概念模型

| 概念 | 含义 | 关键性质 |
|------|------|---------|
| 技能（Skill） | 平台纳管的一个创作辅助包 | 标识 `skl_…` 由平台分配、不可猜、不改、不复用；**说明层**（标题、简介、标签）可改 |
| 技能版本（Version） | 从远端某一个提交取回的一棵文件树 | **不可变**。字节在对象存储，库内只有清单 |
| 来源（Source） | 仓库 + 引用（`ref`）+ 子路径 + 上次同步到的提交 | 同步的输入。**不可改**：要换源就重新纳管 |
| 当前版本（指针） | 目录对外服务的那一份 | 唯一决定"别人读到的是哪一份" |
| 标签（Tag） | 管理员给的归类词 | 平台级自由字符串，**不是全局字典，也不做成权限资源** |
| 收藏（Favorite） | 主体级的个人标记 | 只影响自己看到的列表，不影响别人、不影响目录内容 |
| 取用（Use） | 一次成功的正文下发 | 使用统计的**唯一计量点** |

它们的关系**单向**：技能拥有版本与标签，一个版本是一棵不可变的文件树；当前指针指向其中一个版本。收藏与取用是**主体与技能之间的关系**，挂在技能上而不是版本上——"谁用过这个技能"与"用的是哪一版"是两个问题，后者由取用时的指针间接确定。

**技能之间没有关系。** 没有依赖、没有继承、没有组合：一个技能是一棵自足的树，它需要另一个技能的内容时，那是**它的作者**在远端仓库里组织的事（子目录、复制一份），平台不解释、也不解析。

## 状态流转

一个技能对外只有一个状态维度：**当前指针指向哪一份快照**。它没有"草稿"这一层——纳管拿到什么就是什么，管理员不像 galaxy 那样在平台里编辑正文（见"模块边界"）。

```
                        纳管                     再纳管（换源）
   （不存在）  ────────────────▶  ① 已纳管   ──────────────────▶  仍是 ①，但来源换了

  ① 已纳管 ──同步（远端有新提交）──▶ ① 新版本生效（指针前移）
           ──同步（远端无变化）────▶ ① 不动
           ──回滚─────────────────▶ ① 指针后移
           ──删除技能────────────▶ 终态：技能、版本、标签、收藏与使用记录一起消失
```

**"指针指向哪一份"是判断"现在对外是什么"的唯一依据**；**"有没有版本引用它"不是本模块的问题**——版本不可变，且没有删除单个版本的动作（见"模块边界"）。

**删除只删库里的行，桶上的字节不删。** 同一份字节可能被别的技能、别的版本引用（按内容摘要寻址，键上不带技能标识），而"哪些对象还在被引用"要一次全量对账才答得上来——那正是 galaxy 那边把孤儿对象回收列为待定决策的同一条理由（见 [../galaxy/publication.md](../galaxy/publication.md)）。

**没有"下线一个技能"这个中间状态。** 要让它不可见就删除，要让一部分人看不见就用权限——一个"停用但保留数据"的状态会立刻引出"停用的技能还能不能取用旧版本""已收藏的人看到什么"这些没有好答案的问题。

## 存储分层

**库只回答"有哪些、是什么"，字节一律在对象存储**——与 galaxy 同一条规则，理由是同一个（[../galaxy/README.md](../galaxy/README.md)）。

```
关系库（不含任何字节）
  ├─ 技能：标题 · 简介 · 来源（仓库 / 引用 / 子路径 / 已同步到的提交） · 【当前版本指针】
  ├─ 版本：提交标识 · 文件清单（路径 → 内容摘要 + 字节数） · 文件数 · 总字节数
  ├─ 标签：技能 ↔ 归一化后的标签串
  ├─ 收藏：技能 ↔ 主体
  └─ 使用日次：技能 ↔ 主体 ↔ 日期（计数与首末时间）
        │
        │ 纳管：服务端拉取远端 → 按内容摘要写字节
        ▼
桶 · 私有区
  └─ skills/text/<内容摘要>        中性类型，只有服务端读得到（逐对象私有）
```

| 层 | 存什么 | 键 / 位置 |
|----|-------|----------|
| 关系库 | 技能的说明层与来源 | 技能行。**没有内容** |
| 关系库 | **当前版本指针** | 技能行上的一列 |
| 关系库 | 版本的文件清单 | 版本行上的一列（JSON）。它从来是整份读写 |
| 桶 · 私有区 | 每个文本文件对象的字节 | `skills/text/<内容摘要>`，按内容摘要全局去重 |

**键上不带技能标识、也不带版本标识。** 内容寻址的键只回答"这份字节是什么"，不回答"它属于谁、给谁用"——同一个 `LICENSE` 出现在十个技能里就是一个对象。代价是**跨技能共享**：删除一个技能不能顺着键去删字节（那会删掉别人还在用的），因此删除只删行（见上）。

**对象用中性类型存放**，与 galaxy 的内容对象同一条理由：下发时的内容类型由**请求的路径扩展名**决定，对象本身不承担类型语义，顺带消掉"预签名地址被直接打开时按 HTML 渲染"这条隐患。

**这个桶与头像、galaxy 资产是同一个桶**，靠 `skills/` 这一段前缀并排（见 [../config/server-config.md](../config/server-config.md)）。前缀是**常量，不是配置项**：做成配置项只会多出一种失败方式——改了前缀，存量对象在一瞬间全部变成孤儿。

## 模块边界

本模块**明确不做**：

| 不做的事 | 理由 |
|---------|------|
| 任意用户上传任意包 | 目录由平台维护。开放上传要的是审核、隔离、滥用处置三整套东西，而那与"平台提供一组可信的辅助能力"是两件事（见"待定决策"） |
| 在平台里编辑技能正文 | 真源是远端仓库。平台若允许就地改，就必须回答"下一次同步谁的改动赢"——那是一个合并问题，而合并的正确答案只有仓库自己知道 |
| **执行技能里的任何内容** | 平台分发的是文本。技能里可能引用脚本、可能写着"请运行以下命令"，但那是**读它的人**的判断，不是平台的行为。服务端不执行、不解析、不校验它 |
| 依赖解析与组合 | 一个技能是一棵自足的树。技能之间没有关系（见"概念模型"） |
| 定时同步 | 见 [onboarding.md](onboarding.md)：自动把远端变更带进来，等于把远端仓库的写权限变成平台内容的写权限 |
| 删除单个版本 | 版本是快照，删它换不到任何东西：存储不因此回收，可见性由指针决定。真要变小就删掉整个技能 |
| 二进制 | 平台分发的字节是**文本**：含 NUL 或不是合法 UTF-8 的文件在纳管时被拒并点名（见 [onboarding.md](onboarding.md)）。**脚本类文本照收**——收不收得下由"它是不是文本"决定，不由"它像不像会被执行"决定，因为平台从不执行它 |
| 把技能打进 galaxy 发布物 | 技能是**创作时的输入**，不是作品的一部分（见"待定决策"） |
| 全文检索、语义检索 | 关键词是大小写不敏感的子串匹配，匹配标题与简介。目录规模由管理员的维护成本决定，语料远没到需要索引的量级 |

## 归属与权限

### 两把闸门

| 闸门 | 管什么 | 唯一入口 |
|------|-------|---------|
| RBAC 权限码 | 这个主体**能不能读 / 能不能维护**目录 | [../../../api/permissions/catalog.yaml](../../../api/permissions/catalog.yaml) |
| 归属 | **不适用** | 目录是**部署级**的：技能不属于任何主体 |

**这是本模块与 galaxy 最大的不同，也是它不需要第二把闸门的原因。** galaxy 的每一个方法都以"调用者自己的工程"为目标，因此"是不是他的"必须单独判一次；而技能目录全库只有一份，谁能看见、谁不能，**全部由权限码表达**——没有一个"这个技能是你的"的分支。

由此得到两条：

- **不存在"按拥有者列出技能"的形状**，也没有"技能属于谁"这个字段。纳管是谁做的只进审计留痕（见 [../../observability.md](../../observability.md)），不进数据模型。
- **作用域一律取自凭证**，请求里没有作用域字段（见"依赖关系"）。目录不由作用域切分：`skill.catalog.read` 在某个范围上被授予，就在那个范围上生效，这是 RBAC 的事，不是本模块的事。

### 权限码

| 权限码 | 含义 |
|--------|------|
| `skill.catalog.read` | 检索目录、读技能正文、收藏与取消收藏 |
| `skill.catalog.write` | 纳管、同步、回滚、改说明层与标签、删除技能 |

**读与写分成两码**，因为它们对应两类完全不同的人：读是**每一个要创作的人与每一个 agent**（他们只需要找到并用上），写是**平台管理员**（他们决定目录里有什么）。合成一码会让"让创作者用上技能"必然连带"让创作者能往目录里塞东西"。

权限码落在新建的内置角色 **`skill.curator`（技能管理员）** 上；`skill.catalog.read` 同时落在 `galaxy.author`（创作者）上——创作者要能选用，否则这个目录对他不存在。**`skill.catalog.read` 不落在 `viewer` 上**：只读用户看的是权限体系（角色、范围、绑定），技能目录对他不是"只读该看的东西"，加进去只会让"只读用户"这个角色名越来越不像它自己。

**取消收藏不需要单独的权限**，它与收藏是同一个动作的两个方向（与"撤回发布用发布那一码"同一条理由：只授一半的能力只会让"能收藏、收不回来"变成一个可以造出来的状态）。

### 管理面与读面分成两个服务

`SkillService`（读）与 `SkillAdminService`（管）在 proto 上就是两个服务。理由与 `TelemetryService` / `TelemetryAdminService` 逐字相同（见 [../rbac/server-permissions.md](../rbac/server-permissions.md)）：两侧的准入条件不同，写在同一份接口里会让"这个服务要不要认证"变成一个需要逐方法去看的问题——那正是注解漏写的温床。

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| RBAC | 消费两个权限码判定结论；**没有归属判定**（见"归属与权限"） |
| 身份认证 | 只消费"已确认的主体标识"，用在收藏与使用统计上 |
| 对象存储 | 字节按内容摘要写进私有区、由服务端读回。**走的是galaxy 内容对象同一条规则**（内容寻址、仅当不存在时写入、写后核对摘要），见 [../objectstore/README.md](../objectstore/README.md) |
| 持久化 | 五张表由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)） |
| 服务端配置 | 远端拉取的凭据只从环境变量读（`ALADDIN_GITHUB_TOKEN`，可空）；各项上限是**常量，不是配置项** |
| 命令行 | 取用面与维护面各有一条命令，见 [agent-access.md](agent-access.md) |
| Web 界面 | 目录页与详情页；呈现机制见 [../web/README.md](../web/README.md)，取舍见 [../uiux/README.md](../uiux/README.md) |
| galaxy | **无数据交互**。第一版技能不进文件组、不进产物（见"待定决策"） |
| proto | 方法与权限码在 `api/proto/aladdin/skill/v1/` 中声明，经 `buf generate` 派生两端代码 |
| 可观测性 | 纳管、同步、回滚与删除的留痕（**不含正文**），见 [../../observability.md](../../observability.md) |

**远端拉取不出现在这张表里**，因为它不是"另一个模块"：它是本模块的一个**出口**，藏在接口后面，测试注入假实现（见 [onboarding.md](onboarding.md) 的"可验证性"）。

## 可验证性与长程执行

**非长程任务。** 纳管与同步是一次请求一次结论的同步操作，不做多阶段推进、不需要检查点。代价是**一次纳管请求的时长由远端决定**（见 [onboarding.md](onboarding.md) 的"超时与失败"）。

跨子模块的约束：

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 校验失败不留痕迹 | 一次被拒的纳管之后，库里没有新的技能行、版本行，桶上也没有新的对象（`internal/skill` 测试 + 端到端测试） |
| 版本不可变 | 同步产生新版本之后，旧版本读回来逐字不变（`internal/skill` 测试） |
| 指针是唯一可见性依据 | 回滚之后读到的正文是旧版本那一份；同一个技能在同一时刻只有一个当前版本（`internal/skill` 测试 + 端到端测试） |
| 同步无变化时不动 | 远端提交与已记录的一致时，不产生新版本、不留痕（`internal/skill` 测试） |
| 来源不可改 | 接口面上不存在"改来源"的方法；技能来源在纳管之后逐字不变（`internal/server` 测试：遍历 method descriptor） |
| 平台不写调用方文件系统 | 取用之后调用方的 HOME 下不出现任何技能目录/文件（端到端测试） |
| 正文不被执行 | 纳管与取用不产生任何进程：一份含 `#!/bin/sh` 与别的脚本的文件被当作字节处理，读回来逐字不变（`internal/skill` 测试）；模块内不出现执行入口（导入清单测试） |
| 二进制被拒 | 一份带 PNG 的包被拒，错误点名那个路径（`internal/skill` 测试） |
| 只认 github.com | 形状不是 `https://github.com/<owner>/<repo>` 的地址在**解析阶段**被拒，不发生任何出站请求（`internal/skill` 测试 + 端到端测试） |
| 目录不由主体切分 | 接口面上不存在"按拥有者"的形状；任意两个持读权限的主体读到同一份目录（端到端测试） |
| 收藏是私人的 | 一个主体收藏之后，另一个主体读到的该技能未被收藏（端到端测试） |
| 使用量不外泄主体 | 读侧只返回计数，返回体里不含主体标识（`internal/server` 测试） |
| 未配置时降级正确 | 桶未配置时目录整体不可用（检索与取用都被拒），其余模块照常（`internal/config` 与 `internal/skill` 测试） |
| 不联网即可测 | 远端拉取藏在接口后面，测试注入假实现；另有一条默认跳过的真实 GitHub 冒烟（`internal/skill` 测试） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 创作者自助上传 | 暂不做。要开放要的是审核流、滥用处置与配额三件套（**未定**） | 归属、权限模型与生命周期都要重新设计：现在"技能不属于谁"是整套设计的地基 |
