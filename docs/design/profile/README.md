# 个人档案 模块总览

> 本目录是 aladdin **"这个主体叫什么、长什么样"** 这一问题的功能行为唯一信源。

## 背景与目标

另外两个模块各自回答了一个问题：[../identity/](../identity/README.md) 回答"你是谁"，[../rbac/](../rbac/README.md) 回答"你能做什么"。没有谁回答"这个主体在界面上叫什么名字"。

于是最接近用户名的东西变成了主体标识本身——一个分配即冻结的内部标识，界面上直接把它当用户名显示，等于把内部标识当成了名字。

渠道确实给出了可读标识（Google 是邮箱），但它落在**身份**这一层（见 [../persistence/schema.md](../persistence/schema.md) 的身份别名表），因为一个主体可以有多个渠道、因而有多个邮箱。拿它当用户名等于替主体选定唯一一个，而"哪个才是他的名字"这个问题没有正确答案——它在渠道侧随时可以被改名。

本模块补上"主体自己的展示信息"这一层。它**与权限完全无关**：档案字段不进任何一次判定，也不构成一条新的身份路径。

成功的衡量标准：

1. 一个主体可以设置自己的昵称、头像、简介，三者彼此独立——设昵称不必先有头像。
2. 昵称**不是**身份：两个主体可以同名，且任何一次判定、任何一次身份归属的确定都不读昵称。
3. 未设置昵称时，界面显示的仍是一个**可读的名字**而不是内部标识——回退规则只有一处实现。
4. 每个方法只作用于调用者自己，接口面上不存在以他人为目标的形状。
5. 首次登录、零角色的主体**能**设置自己的档案。这不是边界情况，而是本模块的主要使用者（见 [../identity/README.md](../identity/README.md) 第 4 条成功标准）。

## 模块边界

| 问题 | 归属 |
|------|------|
| 你是谁 | [../identity/](../identity/README.md) |
| 你叫什么、长什么样 | **本模块** |
| 你能做什么 | [../rbac/](../rbac/README.md) |
| 档案存在哪 | [../persistence/](../persistence/README.md) |
| 头像字节存在哪、桶怎么配 | [avatar-storage.md](avatar-storage.md) |

两个方向上的边界都要守住：

- **不参与判定。** 本模块不读角色、不算权限，产出的是一份展示信息。它既不能决定放行，也不能决定"这个人是谁"。
- **不成为身份路径。** 昵称不是键：不可按它查询、不给它唯一约束、不参与登录与绑定。身份归属的唯一入口仍在 [../identity/identity-linking.md](../identity/identity-linking.md)。

## 功能行为

### 三个字段

| 字段 | 语义 | 为空时 |
|------|------|--------|
| 昵称 | 主体自己定的短名字 | 表示未设置，展示时回退 |
| 简介 | 一段自由文本 | 表示未填写 |
| 头像 | 一张图片，字节存于对象存储（见 [avatar-storage.md](avatar-storage.md)） | 表示没有头像 |

- 三者彼此独立：可以只设昵称，也可以只传头像。
- 空值就是"未设置"，不区分"从没设过"与"设成了空"。
- 写入前做长度上限校验，超限拒绝并指出是哪一项。
- 头像**未配置时**（见 [../config/server-config.md](../config/server-config.md)）昵称与简介照常可用，档案响应里明确标出该功能未启用。

**档案行是惰性创建的**：主体登记时不建档案行，本人第一次保存才创建。认证流程因此完全不依赖本模块，依赖方向单向。

### 展示名：回退规则

界面要显示的不是三个字段，而是**一个**展示名。规则：

1. 昵称非空 → 昵称
2. 否则 → 该主体身份列表中第一条非空的渠道可读标识
3. 否则 → 主体标识

**规则只有一处实现，在服务端**，随档案一起下发。理由是这是一次**判断**：两端各写一份必然漂移（前端容易只看第一个渠道，或忘记排序），而漂移的表现是"页头显示的名字与服务端日志里的不是同一个"。

第二步需要一个确定的顺序——一个主体可能有多个渠道、多个邮箱。顺序沿用身份模块既有的排序，本模块不另定一份。

### 自服务：每个方法只作用于调用者自己

四个动作：读自己的档案、改昵称与简介、设头像、删头像。

**接口面上不存在"以某个指定主体为目标的档案方法"**，因此不存在"改他人档案"这个入口。目标由凭证决定，不由请求里的任何字段决定。

由此得到准入结论：**准入门槛是"已认证"，不是一个权限码。** 要拿到和改动的都是**自己**主体的展示信息，而这个动作没有任何以他人为目标的形状，因此不存在可被滥用的授权面。它与"把受自己控制的渠道绑到自己身上"同类（见 [../identity/identity-linking.md](../identity/identity-linking.md) 的"边界与约束"）。

反过来说：一旦将来出现"管理员查看或编辑他人档案"的入口，它就是一个以他人为目标的动作，**必须单独设计并带权限码**，不能与本模块的入口混为一谈。见"待定决策"。

### 留痕

档案变更各留一条记录：主体标识、改了哪一项、时间。

**不含头像字节**——与令牌、口令同级地不进日志。简介是自由文本，全文进日志既无必要也可能含隐私，因此只记"简介被修改"这一事实，不记内容。

## 边界与约束

本模块**明确不处理**：

- 头像字节的存放与桶的配置：[avatar-storage.md](avatar-storage.md)。
- 主体是否存在：由认证流程的登记动作决定（见 [../persistence/schema.md](../persistence/schema.md)）。
- 档案的任何权限含义：没有。档案不进任何一次判定。

约束：

- **档案字段不得成为判定的输入。** 新增任何读昵称 / 简介 / 头像来决定"放行或不放行""这个人是谁"的逻辑，都是对本模块的违反。这条与邮箱的约束同源，理由也相同：展示信息在别处可以被改名，把判定建在它上面等于把一次改名变成一次提权。
- **昵称不得获得唯一性。** 唯一约束会把它变成一个查找键，也就是第二条身份路径；一旦有了唯一性，"按昵称查人"的需求就会跟着出现——而那正是邮箱这条路已经踩过的坑。
- **展示名的回退规则只有一处实现**（服务端）。
- **本模块不提供"删档案"的入口。** 档案随主体存在，而主体的生命周期不由本模块管。

## 可验证性与长程执行

**非长程任务。** 档案的读写都是即时的同步操作，不跨阶段推进。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 档案不参与判定 | 改昵称、改简介、换头像前后，同一份会话的权限集合逐字相同（端到端测试） |
| 昵称不是身份 | 两个主体设同一昵称都成功；此后各自登录仍解析到各自原本的主体（端到端测试） |
| 没有按昵称查询的入口 | 接口面上不存在以昵称为条件的查询方法（`internal/server` 测试：遍历 method descriptor） |
| 没有以他人为目标的入口 | 接口面上不存在带目标主体标识的档案方法（`internal/server` 测试：遍历 method descriptor） |
| 回退规则确定性 | 未设昵称且有多渠道时，反复读取得到同一个展示名（`internal/profile` 测试） |
| 回退规则只有一处 | 展示名由服务端算好下发，客户端只渲染：端到端测试钉住三种情形（昵称 / 渠道标识 / 主体标识）都由服务端给出 |
| 三个字段彼此独立 | 只设昵称、只设头像、只设简介各自都成功（`internal/profile` 测试） |
| 空值即未设置 | 把昵称设为空后再读，回退生效且不报错（`internal/profile` 测试） |
| 超限即拒绝 | 超过长度上限的昵称 / 简介被拒，错误信息指出是哪一项（`internal/profile` 测试 + `internal/server` 的错误映射测试） |
| 档案行惰性创建 | 写入之前读该主体返回"档案不存在"，写入之后才出现（`internal/profile/gormstore` 契约测试） |
| 未登记主体不产生档案行 | 对未登记主体发起档案写入失败，且档案表无新行（`internal/profile` 测试） |
| 两份实现同结果 | 同一套档案用例在内存实现与 SQL 实现上结论与错误类别相同（`internal/profile/gormstore` 契约测试） |
| 变更留痕不含字节 | 走完一次头像上传后，所有日志字段里都没有承载二进制内容的那一个（端到端测试） |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 身份认证 | **只读**：取该主体的渠道列表，供展示名回退的第一步使用；不写身份别名、不参与归属（见 [../identity/identity-linking.md](../identity/identity-linking.md)） |
| RBAC | 无交互。档案不读角色、不参与判定 |
| 持久化 | 档案表与迁移由持久化模块统一管（见 [../persistence/schema.md](../persistence/schema.md)） |
| 头像存储 | 头像字节、对象键与下发规则见 [avatar-storage.md](avatar-storage.md) |
| 服务端配置 | 头像存储是否启用由配置决定；密钥只走环境变量（见 [../config/server-config.md](../config/server-config.md)） |
| 可观测性 | 档案变更留痕，含主体标识与改了哪一项，**不含头像字节与简介全文**（见 [../../observability.md](../../observability.md)） |

依赖方向单向：本模块依赖身份模块的只读查询，身份模块不感知本模块。

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 管理员查看 / 编辑他人档案 | 暂不做。真出现时单独设计（**未定**） | 以他人为目标，必须带权限码；且要重新审视"谁能替谁改展示名" |
| 档案字段进审计日志 | 暂不做，先按结构日志留痕（**未定**） | 依赖审计模块本身；档案不是权限事实，是否值得进审计需单独判断 |
| 昵称的内容策略（敏感词、控制字符） | 只做长度上限与去首尾空白（**未定**） | 只影响写入校验，不影响回退与判定 |
| CLI 侧的档案命令 | 暂不做。档案面向人类，CLI 以机器凭证为主（**未定**） | 新增一条 CLI 命令；档案语义不受影响 |
