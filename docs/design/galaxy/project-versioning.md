# galaxy — 工程与版本

## 背景与目标

用户在 galaxy 里做的不是"一次编辑"，而是一个会持续改的东西。没有版本，就只有两种选择：每次保存覆盖掉上一版（改坏了退不回去），或者把历史全塞进当前内容里（内容变成垃圾场）。

本子模块定义这个作品单元的形状：**工程**作为容器，**草稿**作为当前编辑态，**版本**作为不可变的历史点。

成功的衡量标准：

1. 用户能创建工程、改元数据、反复保存版本，并能回到任何一个已保存的版本。
2. 一个版本一旦保存，它读回的内容**逐字不变**——清单被冻结，而清单指向的字节按内容摘要寻址、不可能被改写。改草稿、改元数据、删资产都不改变它。
3. 一个版本引用了哪些资产，可以从这个版本的**文件清单**单独确定，不需要查任何别的记录。
4. 一个工程的内容槽**彼此独立**：在一个槽上改草稿、存版本、发布或撤回，都不改变另一个槽读回的任何东西。
5. 删除工程这一件事有确定的边界：删掉什么、不删掉什么、已发布的地址变成什么，都不需要猜。
6. **推草稿推掉的那一份找得回来**：每一次替换草稿都留下一条草稿快照，因此"只推不存版本"不会让中间过程消失——那正是这套东西最容易被用错的地方（见"草稿快照"）。

## 功能行为

### 工程元数据

| 内容 | 说明 |
|------|------|
| 工程标识 | 由 aladdin 分配，不可猜、不可改、不复用 |
| 拥有者主体标识 | 创建它的主体。**不可转移** |
| 名称 | 可改。**仅用于本人识别，不作为地址、不需要唯一** |
| 简介 | 可改，可空 |
| 内容槽 | 一组（1–2 个）：`site` 与 `docs`。**创建时至少选一个，此后只增不删**（见 [site-model.md](site-model.md)）。**每个槽各有自己的草稿、版本、发布指针与地址**，一个槽上的任何动作都不改变另一个槽 |
| 创建时间 / 更新时间 | 展示与排障用，不参与判定 |

**工程标识不可猜**是发布语义的要求，不是防重复写入的优化：它是发布地址的一部分，而发布态是公开匿名的（见 [README.md](README.md) 的"发布即公开"）。它由 aladdin 分配、分配即冻结、永不复用——与主体标识同一条约定。

**名称不参与任何查找。** 不按名称查工程、不给它唯一约束、不把它放进发布地址。理由与昵称不得获得唯一性完全相同（见 [../profile/README.md](../profile/README.md)）：一旦名称成为查找键，它就成了一条可以被改名或抢注改写的路径。发布地址用不可猜标识，用不着名字。

**拥有者不可转移。** 转移是"把一整个工程连同它的发布地址交给另一个人"，属于资源所有权的变更，首版不做（见"待定决策"）。

### 草稿

**工程的每一个内容槽有且只有一份草稿**：该槽当前正在编辑的文件组。

- 草稿随时可改，改它**不产生版本**。
- 草稿**不参与发布**。发布只能发布版本。
- 草稿不保证可退回：它是工作区，不是历史。

**改草稿 = 写入新的内容对象，再把清单换掉。** 被换掉的那些对象不因此消失——它们可能仍被某个版本引用。至于"还有没有人在用它"，库里没有引用计数，只能拿清单去回答（见 [asset-library.md](asset-library.md) 的待定决策）。

**草稿与版本是同一份内容类型**（一组具名文件，见 [site-model.md](site-model.md)）。保存版本就是把草稿的当前**文件清单**冻结成一条不可变记录——字节本来就是按内容摘要寻址的不可变对象，因此这一次冻结不搬运任何字节。此后两者各自演进。

**每一次替换草稿都留下一条草稿快照**（见下）。这是"草稿不保证可退回"这句话的边界：退回仍然不是草稿的语义，但**被覆盖掉的那一份还找得回来**。

### 草稿快照：被替换掉的清单

**替换草稿时，被换掉的那份旧清单会留成一条草稿快照**：清单 + 时间 + 来源（`web` / `cli`，与遥测的上报端标识同源）+ 操作者。

| 内容 | 说明 |
|------|------|
| 快照标识 | 由 aladdin 分配。**前缀与版本不同**（`snp_` 对 `ver_`）：拿一条快照的标识去发布必须失败，而标识一眼看得出拿错了哪一种 |
| 所属工程 / 内容槽 | 一条快照属于一个槽 |
| 序号 | 在**槽内**递增，**仅用于排序**（理由见下） |
| 文件清单 | 被替换掉的那份旧清单。**字节不搬运**：它们本来就是按内容摘要寻址的不可变对象 |
| 来源 | 替换它的那一端（`web` / `cli`）。没带上报端标识时为空 |
| 操作者主体标识 | 留痕用 |
| 时间 | 它被替换掉的时刻 |

**排序按序号，不按时间。** 两次替换可能落在同一个时间刻上（库的时间列精度有限，而一次密集的构建循环本来就可能在同几秒里推好几次），那时"哪一条是最近的"会变成一个由标识的随机性决定的答案——而历史列表要回答的第一件事就是"最近那一条是什么"。序号在写入它的那个事务里分配，因此这个答案永远确定。它与版本表的序号是同一条取向：**删除与清理会留下空洞，这不是错误**。

四条边界，每一条都对应一次误用：

- **快照不是版本。** 它没有序号、**不能发布**、也不进 `version list`。发布只发布版本（见 [publication.md](publication.md)），这条不因快照而松动——"发布一个自动记下来的东西"没有意义。
- **相同清单不产生新快照。** 连续多次推同一份清单只留一条。这与"版本不去重"不冲突：版本的两次保存是用户**显式**的两次动作，而快照是服务端顺手记的——把两次相同的结果记两遍，只会让历史里全是同一份东西。
- **保留有上限**：每个槽保留最近 **50** 条、且不超过 **14 天**，超出按时间清理。清理挂在写入那一处（与预览凭证同一条做法），因此表的大小只由"还有多少条活的快照"决定，读的那条路是只读的。
- **恢复本身也留快照。** 恢复到某一条快照是一次草稿替换，所以它照样先把当前清单留成快照——**恢复不会让你丢掉恢复前的内容**。

**它不进发布产物，也不参与引用完整性。** 一张快照里的资产条目就是它当时的那些条目；一份资产若只被快照引用（没有任何版本引用它），它**照常可以删**。快照会过期，让一段会自动消失的历史去拦住一次删除，只会让"想删一个不再用的素材"变成一件要看运气的事。

由此得到一条**恢复的前置条件**：一条引用了已删除资产的快照**不能被恢复**，也不能升级成版本，服务端如实拒绝并指出那一处。不这样做的话，恢复出来的是一份必然在校验阶段失败的草稿，而用户从"恢复成功"这句话里看不出问题在哪——与"被引用的资产不许删"要挡的是同一类结果（见下）。

### 版本：保存即冻结

版本是内容的一次**不可变快照**。

| 内容 | 说明 |
|------|------|
| 版本标识 | 由 aladdin 分配 |
| 所属工程 | 一个版本属于唯一一个工程 |
| 所属内容槽 | 一个版本属于该工程的一个内容槽。**版本只在自己的槽里被列出、发布与撤回** |
| 序号 | 在**槽内**递增，仅用于展示与排序，**不是标识** |
| 文件清单 | 保存那一刻草稿的清单（路径 → 内容摘要与条目类别），此后不可改。**字节不随清单走**：它们是按内容摘要寻址的不可变对象，由多个版本共享 |
| 说明 | 可选的一句短文本（≤ 280 字），**可事后补写或修改**（见下）。空表示没有 |
| 渲染规则版本 | 保存时所处的渲染规则版本。**仅 `docs` 槽有**，重新发布时用它而不是用当前最新的（见 [site-model.md](site-model.md)） |
| 保存时间 | 排障与展示用 |

三条不可变性约定：

1. **版本的文件清单不可修改。** 没有"编辑某个版本"这个动作——要改就改草稿、再保存一个新版本。
2. **版本不因别的记录变化而变化。** 改工程名称、改简介、删资产、删别的版本，都不改变一个已保存版本读回的内容。
3. **版本不可覆盖。** 保存两次相同的内容产生两个版本，而不是"检测到重复就不新增"。判断"内容一样"需要比较文件组，而两份看起来一样的文件组对用户是两次不同的保存动作——把它们合成一个会让"我明明保存了两次"变成一个需要解释的问题。

**序号不是标识。** 删除一个版本会让后续版本的序号出现空洞，这是可接受的；把序号当标识意味着删除会波及所有更大的序号，而标识别名化正是所有这类 bug 的来源。

### 版本说明：可改的是那一句，不是内容

**说明是元数据层的一层，与"版本不可变"不冲突。** 与资产的标题 / 标签 / 备注同一条：不可变说的是**内容**（文件清单、渲染规则版本），而说明回答的是"这一版是干什么的"，它不进产物、不参与任何判定。

- **它随保存写入**（`version save --description`），也可以事后补写或修改——**两端都能改**，命令行与网页端对等。
- **改它不碰内容**：清单、序号、保存时间与渲染规则版本在改动前后逐字不变，已经发出去的页面也不受影响（产物与说明无关）。
- 空串表示没有说明。长度按**字符数**计，与工程简介同一条理由。

**为什么它是可改的而清单不是**：写错一句话与"把这一版的内容改掉"是两件事，而前者在"只能再存一版"的规则下要付出一整个版本的代价——那会让人宁可不写说明。

### 版本引用了哪些资产：文件组的条目

**一个版本引用了哪些资产，由该版本文件组的资产条目决定，不另存一份集合。**

**它不需要解析文本。** 条目是发布态分派的唯一依据，也是这件事的直接答案；文本里那一处的写法（构建产物的路径，或手写的 `asset://` 记号）与条目由**写入校验**绑在一起：每一处取字节的引用都必须落在一条资产条目上，落不上就拒绝写入（见 [site-model.md](site-model.md) 与 [publication.md](publication.md)）。

由此得到两条直接结论：

- **资产被删除的拦阻是"查文件组"**：一个资产若仍被某个版本引用，就不能删（见"删除语义"）。这个判断的输入只有版本的文件组，没有第二份数据。**草稿快照不在这个判断里**（理由见上）。
- **版本不需要"资产集合"这个方法**。调用方要这个结论时读文件组（唯一入口见 [README.md](README.md) 的"引用完整性的唯一入口"）。

### 发布指针

**每一个内容槽各记录自己的发布指针**：它指向该槽当前发布的版本，或为空表示该槽未发布。

- 发布把一个版本指为**它所属槽的**当前发布版本（见 [publication.md](publication.md)）。指针因此指向的是（槽，版本）这一对。
- 撤回发布把该槽的指针置空，该槽回到未发布；**另一个槽的指针不动**。
- **指针指向的是版本，不是发布记录本身**——但发布记录里存着当时改写好的产物，对外地址返回的是那份产物（理由见 [publication.md](publication.md)）。

### 删除语义

| 删除什么 | 影响 |
|---------|------|
| 一个版本 | 草稿与其它版本不受影响。**被它所属槽的发布指向的版本不可删**——那会让那条发布地址指向一个不存在的版本 |
| 一个资产 | 被任一版本引用时**拒绝删除**，错误信息指出被哪些版本引用。未被引用时删除，字节与元数据一并清掉 |
| 一个草稿快照 | 接口面上没有"删一条快照"这个动作。快照会按保留策略过期，那就是它唯一的清理方式——多一条删除入口只会多一条能删掉历史的路（见"待定决策"） |
| 一个工程 | 连同它的全部内容槽、版本、草稿快照、资产与发布记录一并删除；**每一个槽的**发布地址都变成"不存在" |

**为什么被引用的资产不许删。** 版本不可变的含义包括"它此后永远可以发布"。一个引用了已删除资产的版本，发布时必然在校验阶段失败，而那时用户看到的是一句"资产不存在"，却无法从版本内容里知道该怎么做——引用是可以看见的，资产已经没有入口了。拒绝删除把这个问题挡在它产生的地方，并明确告诉你先改哪一步。

代价是清理麻烦：想删一个被旧版本引用的资产，得先删那些版本。这是刻意的（见"待定决策"的备选）。

**删工程会连带删掉发布记录，因此已发布地址立刻不可达。** 这是"删除"应有的语义：工程都不存在了，页面还在是更难解释的那个结果。

### 归属

工程的每个读写动作都要求**调用者是该工程的拥有者**。

- 接口面上不存在"指定拥有者"的形状；拥有者由凭证决定，不由请求里的字段决定。
- 用一个主体的凭证去读、改、发布另一个主体的工程，一律拒绝，且拒绝类别与"工程不存在"一致（见下）。

**"不是你的" 与 "不存在" 返回同一个结论。** 区分它们等于提供一个工程枚举接口：拿着别人的工程标识反复调用，"不存在"与"无权访问"的差异就能把一个不可猜标识试出来。这与发布态的"地址即凭据"是同一条取向——**地址的可猜性是唯一防线，那就不能有任何东西帮人猜。**

## 边界与约束

- **不做分支、标签、合并。** 版本的演进是线性的。分支是一整套并发模型（怎么比较、怎么合、冲突了怎么办），不是"多个指针"。
- **不做版本之间的差异比较。** 比较两组文件的差异是一件事，但它的价值取决于用户真的会用它来 review——首版没有这个场景。
- **不做自动保存为版本。** 保存为版本是显式动作（见 [README.md](README.md)），因此不存在"历史里多了一堆没意义的版本"这个问题。
- **工程不参与权限判定。** 工程是资源归属的载体，不是权限来源；`galaxy.*` 权限码来自权限目录，工程的任何字段都不改变任何一次判定。
- **元数据不得成为判定的输入**，与档案字段同源的理由：名称与简介都是可改的自由文本，把判定建在它上面等于把一次改名变成一次授权变更。

## 可验证性与长程执行

**非长程任务。** 工程、草稿与版本的读写都是即时的同步操作，不跨阶段推进。发布才是长程的，见 [publication.md](publication.md)。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 工程标识不可猜 | 标识由服务端分配且不含可控成分（`internal/galaxy` 测试） |
| 名称不是查找键 | 接口面上不存在按名称查工程的方法；两个工程可同名（`internal/server` 测试 + `internal/galaxy` 测试） |
| 版本不可变 | 保存版本 → 改草稿 → 读回该版本，内容逐字不变（`internal/galaxy` 测试） |
| 清单不随字节走 | 版本行与草稿行不含内容本身；两份清单指向同一个对象键时不产生第二份字节（`internal/galaxy` 测试） |
| 版本不因别处变化而变 | 改工程名称、删其它版本之后，该版本读回内容不变（`internal/galaxy` 测试） |
| 草稿不可发布 | 只有草稿没有版本时发布被拒；保存版本后发布成功，且产物对应保存时那一刻的文件组（端到端测试） |
| 版本不覆盖 | 连续保存两次相同文件组产生两个版本（`internal/galaxy` 测试） |
| 序号不是标识 | 删除中间一个版本后，其余版本仍可按各自标识读回（`internal/galaxy` 测试） |
| 引用集合由清单决定 | 同一清单里的资产条目集合，在草稿与各版本上一致（`internal/galaxy` 测试） |
| 替换草稿留快照 | 连续三次推**不同**清单之后，草稿历史里能读出前两份旧清单（`internal/galaxy` 测试） |
| 相同清单不留快照 | 连续两次推**相同**清单只留一条快照（`internal/galaxy` 测试） |
| 快照不是版本 | 快照不出现在 `version list` 里，也没有序号；用它的标识发起发布被拒（`internal/galaxy` 测试 + 端到端测试） |
| 恢复也留快照 | 恢复到某一条快照之后，恢复前的那份清单成为一条新快照（`internal/galaxy` 测试） |
| 快照过期被清理 | 超过保留条数或保留期的快照在写入时被清掉（`internal/galaxy` 与存储契约测试） |
| 历史顺序确定 | 同一时间刻写下的两条快照，按序号能定出哪一条最近（两个存储实现给出同一个顺序）（`internal/galaxy` 与存储契约测试） |
| 只被快照引用的资产可删 | 一份资产没有任何版本引用、只被快照引用时可以删除（`internal/galaxy` 测试） |
| 坏快照不能恢复 | 快照引用的资产已删除时恢复被拒，且拒绝信息指出那一处；草稿保持不变（`internal/galaxy` 测试） |
| 快照可以升级成版本 | 用一条快照保存出的版本，清单与那条快照逐字相同（`internal/galaxy` 测试） |
| 版本说明可改而不动内容 | 改说明之后清单、序号、保存时间与渲染规则版本逐字不变；重新发布产物不变（`internal/galaxy` 测试 + 端到端测试） |
| 说明不进产物 | 带说明的版本发布出来的产物与不带说明时逐字相同（端到端测试） |
| 渲染规则随版本冻结 | 以旧渲染规则保存的版本，重新发布得到旧规则下的产物（`internal/galaxy` 测试） |
| 被引用的资产不可删 | 资产被某版本引用时删除失败，错误信息含引用它的版本（`internal/galaxy` 测试） |
| 未被引用的资产可删 | 删掉引用它的所有版本后，该资产可以删除且元数据与字节一并消失（`internal/galaxy` 测试） |
| 当前发布的版本不可删 | 被所属槽发布指向的版本删除失败；另一个槽的发布指针不影响这个判定（`internal/galaxy` 测试） |
| 内容槽只增不删 | 接口面上不存在"删除内容槽"的方法；加入一个槽后，另一个槽的版本、草稿与发布指针原样（`internal/server` 测试 + `internal/galaxy` 测试） |
| 两槽的发布各归各 | 发布站点槽不改变文档槽的指针；撤回一个槽不影响另一个槽（`internal/galaxy` 测试 + 端到端测试） |
| 归属不可绕过 | 另一个主体的凭证读 / 改 / 发布该工程一律被拒（端到端测试） |
| 不区分"不是你的"与"不存在" | 对他人工程与对不存在标识的调用返回相同的错误类别（`internal/galaxy` 测试 + 端到端测试） |
| 接口面上无以他人工程为目标的形状 | 方法描述符里不存在拥有者参数（`internal/server` 测试） |
| 删工程即撤下页面 | 删除工程后其发布地址返回"不存在"（端到端测试） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 多人协作同一个工程 | 暂不做，一个工程一个拥有者（**未定**） | 需要显式的成员表或把工程挂到作用域上；归属校验与"不是你的与不存在同结论"都要重新论证 |
| 工程所有权转移 | 暂不做，不可转移（**未定**） | 转移连发布地址一起交出去；需要一条留痕的、不可静默完成的路径 |
| 允许"删除并让引用它的版本失效" | 暂不做，保持"先删版本"（**未定**） | 省去清理步骤，但引入了"版本可能不可发布"这个新状态，而它必须对用户可见 |
| 版本之间做差异比较 | 暂不做（**未定**） | 只影响界面，不影响数据模型与发布语义 |
| 草稿的并发修改检测 | 暂不做，后写覆盖（**未定**） | 单拥有者下两个人同时编辑的窗口很小；协作落地时必须一起解决。**草稿快照把它从"丢内容"降成"能取回"**，但基线校验仍是协作要解决的那件事 |
| 草稿快照的保留条数与天数 | 暂取 50 条 / 14 天（**已定**，取值是实现里的常量） | 它是常量而不是配置项：做成配置项等于让"历史有多长"随部署变化，而界面上的说法（"最近 N 条"）会跟着变成一个查配置才知道的数 |
| 手工删除单条草稿快照 | 暂不做（**未定**） | 多一条能删掉历史的路；先看"自动过期"够不够 |
| 草稿快照的差异比较（哪几个文件变了） | 暂不做（**未定**） | 与版本之间的差异比较是同一件事，要做一起做 |
