# galaxy — 编写与预览

> 内容是什么形状、有哪两种形态、地址怎么给见 [site-model.md](site-model.md)。本文件只管两件事：**内容怎么写**，以及**这一页看到什么**。

## 背景与目标

创作路径在命令行，不在浏览器。命令行覆盖全部原子能力（把目录送上送下、存版本、传素材、发布，见 [cli.md](cli.md)），内容由本地工具或生成器产出来再送上去；在网页里逐行敲一份完整站点是低效的那一端。因此网页这一页**不是编辑器优先**的界面，它的职责是另外三件：**看草稿渲染成了什么样**（发布地址只反映已发布的那一版，草稿的渲染结果只有这里能看到）、**看清现在处于哪一步**、**把它推出去**。**网页端不改内容**——内容的写入只有命令行一条路，因此源码视图退化为**只读**的逐份查看：它回答的是"这一页对应哪一份文件、它写了什么"，不是"我要改哪一句"。

成功的衡量标准：

1. 打开这一页，一眼看到三件事：草稿渲染出来是什么样、这份草稿能不能发布、下一步该做什么。
2. 预览始终是草稿的当前内容：命令行改完草稿，打开这一页看到的就是刚改的那一份；**这一页已经开着时，别处的改动会推过来并立刻更新**（订阅见 [../events/README.md](../events/README.md)），窗口重新获得焦点或页面重新可见时还会兜底重读一次，不需要再整页刷新。
3. 素材通过一个**可粘贴、可读、可替换**的记号被引用，用户不需要记任何地址。
4. 预览渲染的内容里有脚本时，**它读不到这一页的任何数据**。
5. 这一页不自己判断内容对不对——它问服务端，与服务端发布时**同一句回答**，且这个回答不需要用户主动索取。

## 功能行为

### 这一页的形态：预览与状态是主体

页面由一个固定的分区骨架构成，而不是一串自上而下阅读的卡片。骨架回答的问题各自固定在一个位置：

| 分区 | 回答什么 |
|------|---------|
| 顶栏 | 去哪里（返回、工程信息），有哪些集合可以打开（资产、版本），以及推进流程的两个动作（存版本、发布） |
| 状态条 | 这份草稿能不能发布、发布出去的是什么（尚未发布 / 已发布 + 地址 + 撤回） |
| 主区 | 草稿现在渲染成什么样；需要看某一页的源文件时切到只读的源码视图。两者共用同一块面积 |

五条约束：

- **主区铺满，集合进弹层。** 资产与版本是"一批东西"，不是"此刻正在看的东西"——与主区并排，代价是主区**长期**窄掉一截，换来的却是一个多数时候不看的列表。改成从顶栏打开、以弹层承载。代价是看集合时看不到渲染结果，而复制引用是把记号复制到剪贴板、不需要同时看着主区。弹层的内容区**自己滚动**，不把父页面撑长。
- **状态条上只放驱动决定的信息。** 常驻的那一行回答两件事：这份草稿能不能发布，以及发布出去的是什么。草稿与版本的**保存时间不在那里**——它不改变任何一次决定。命令行改过草稿之后，这一页收到事件就会重新问服务端（页面在后台时靠重新可见兜底，见 [../events/README.md](../events/README.md)）；版本的时间在版本面板里点一下就有。因此它是一行无框的两段，而不是几个带时间戳的方块。网页端不改内容，因此没有「本地改过、结论过期」这一档。
- **预览与源码是两种模式，在同一块面积上切换。** 并排会让两者争夺同一块面积——"看渲染结果"是这一页的主体动作，而"查一份文件写了什么"是偶尔的；把源码收成一块常驻的折叠面板则是另一种失手：它每次都要多滚一段，还永久占着一行。
- **预览可以单独打开成一个页面。** 它是"要同时看渲染结果与别处"时的出口——改与看不必挤在同一个屏幕里。它读的是同一份草稿；地址过期后刷新即得到新地址（与"重新读取即得到新地址"同源）。
- **主操作随流程位置变化，但任何时刻只有一个。** 缺版本时主操作是存版本，有版本未发布时是发布；其余动作降为次要按钮。这与"一页只有一个主操作"是同一条，只是"哪一个"由状态决定。
- **推进流程的动作只有一个入口，而"撤回"紧挨着它撤销的那个状态。** 发布与更新发布在顶栏一处（决定哪一版发出去）；撤回放在状态条上、它要作废的那个地址旁边——它不是第二个发布入口，而是那一处状态的逆操作。撤回要把地址一并带出来，因为"撤回哪一个地址"是做起这个决定唯一需要知道的事。

状态条呈现的就是 [README.md](README.md) 的"状态流转"里那个机器当前所处的位置（① 无版本 / ② 有版本未发布 / ③ 已发布），再加上"这份草稿能不能发布"这个与草稿绑定的结论。**两者都不是这张表新增的状态**：草稿的结论不改变工程的状态，工程的状态也不告诉你草稿改过没有——这是它们必须分成两段显示的原因。

工程元数据（名称、简介）与形态、工程标识都不占常驻版面：它们不参与创作循环，收进点工程名打开的那个入口。工程标识、形态与入口路径作为只读信息也出现在那里。

### 源码视图：文件列表 + 选中的那一份（只读）

它不是"一份正文"，而是**文件列表 + 选中的那一份**（见 [site-model.md](site-model.md)）。内容本来就是一组具名文件，把它伪装成一份文本会立刻引出"我改的到底是哪一份"这个无法回答的问题。

**它是只读的，网页端不改内容。** 理由不是保守，是形状：写入要么是"整组表达期望状态"、要么是"单条替换"，而两者并存会引出"网页上刚改的一句被一次命令行 push 静默盖掉"这类**只在两个入口之间发生**的冲突。收成一条写入路径，这份冲突连同它需要的基线校验一起消失。

**读一份文件的原文与读一份资产是同一种下发**：服务端给一个短时地址，客户端直连取，服务端不代理字节（见 [asset-library.md](asset-library.md)）。查看也一样——它不经过服务端转发。读正文是浏览器对这条短时地址的跨域读取，因此桶的跨域规则必须允许主应用源发起 `GET` 并让脚本读到响应体；只放行上传用的 `PUT` 时，源码视图拿不到正文（见 [../../deploy.md](../../deploy.md)）。

**整组文件的读写只有命令行一条路**（见 [cli.md](cli.md)）。

### 源侧的记号

两条记号都是**源侧写法**——服务端只认文件组（见 [site-model.md](site-model.md)）：`asset://` 在进入文件组时被**登记**成一条资产条目、发布时被**替换**成该条目在站点内的路径；文档间链接在发布时被解析成站点内的绝对地址。

**一、素材：`asset://<资产标识>`**

例如 `<img src="asset://a1b2c3">`，或 `<style>body{background:url(asset://a1b2c3)}</style>`。

三条理由，缺一条这个设计就不成立：

1. **记号是一个可被逐字替换的文本。** 因此替换不需要解析 HTML——出现在元素属性里、在 `<style>` 里的 CSS `url()` 里、在 `srcset` 里，都只是把这段文本换掉。**依赖"枚举哪些属性算引用"的做法必然会漏**（`srcset`、内联 CSS、未来新增的属性），而逐字替换不会漏。
2. **编辑态与发布态的地址本来就不同**（一个短时预签名、一个稳定公开地址，见 [asset-library.md](asset-library.md) 与 [publication.md](publication.md)）。把真实地址写进源，等于让源里存着一个**会过期**或**与发布态不一致**的字符串。记号让源与两套地址都解耦，也让源里不必出现工程标识。
3. **"这个引用是不是本工程的资产"成了一个可判定的问题。** 写成真实地址时，判断它属不属于本工程要靠比对地址前缀——一个可以被相似域名、被重定向、被大小写绕过的问题。记号把问题变成"这个标识在不在本工程的资产里"，没有歧义。

**用 `asset://` 这个协议形状**，而不是某种模板标记：它不是一个浏览器能解析的协议，所以**任何一次漏掉解析的场合都是显式失败**（图片裂开、链接点不动），而不是静默指向某个看起来合法的地方。静默失败的内容发布是最糟的失败方式——它不会被人发现，直到有人看懂了页面上的错。

**素材库提供"复制引用"**，用户拿到的是这段文本，不需要打开存储或拼地址。

**二、文档间链接：相对 `.md` 路径**（仅 `docs` 形态）

```
[标题](guide/intro.md)
![图](images/x.png)
```

发布时解析成站点内的绝对地址；指向文件组里不存在的位置即拒绝，并指出是哪一份文件的哪一处。

**外部导航链接不受限制**：`<a href="https://example.com">` 可以是任意地址——用户链到外部网站是他的意图，不是资源引用。

**构建产物里的路径引用不需要任何记号。** 产物里写的 `/assets/index-abc.js` 原样保留，由命令行的发布根注入让它成立（见 [cli.md](cli.md)）。

### 预览

预览在浏览器里的一个**沙箱 iframe** 中渲染。

**沙箱的关键是它落在不透明源上（即不给它 `allow-same-origin`）。** 这样即使内容里有脚本，它也读不到这一页的 DOM、会话与本地存储——它连自己的源都没有。**"同源 + 沙箱"不是一个可接受的替代**：同源意味着脚本与这一页共享 origin，浏览器给的隔离就只剩一层属性开关，任何一次属性调整都会变成一次真实的数据泄露。

**代价是站内引用在预览里解析不到**（沙箱文档没有自己的源）。因此：

| 形态 | 预览里能做什么 |
|------|--------------|
| `docs` | 整站拼成一份、用文内锚点导航，页间跳转可用 |
| `static` | 逐页预览；页内的站内导航在预览里不可用 |

**预览里的资产地址是短时预签名地址**（见 [asset-library.md](asset-library.md)）。因此：

- 这一页长时间开着时，预览的图片可能在地址过期后显示不出来。刷新预览即得到新地址——与头像"重新读取档案即得到新地址"同源。
- 预览态接受"地址是凭证"这一取舍，因此**未发布的资产里不得承载秘密**。这条要出现在界面上，而不是留给用户猜。

**预览不做审查、不做裁剪**：内容写什么就渲染什么。引用坏了就显示坏的——这一页的即时提示（见下）是另一个渠道，预览不因为"知道这处有问题"就替用户藏起来。**"预览看起来对"与"发布能成功"是两件事**，把它们混起来会让用户以为预览通过就等于发布通过。

### 能不能发布是一个自动产生的状态，不是一个按钮

**页面打开时，以及这一页从后台回到前台时（窗口重新获得焦点，或页面重新可见），自动调用服务端的校验入口**（见 [publication.md](publication.md)）一次，把结论作为状态呈现出来：可以发布，或者有哪几处问题、分别在哪一份文件的哪一行。**不在前端复写引用解析。**

网页端不改内容，因此不存在「正文改了还没保存、上一次结论作废」这一档。命令行可以在这一页开着的时候把新草稿 push 上来：**这一页订阅了它正在看的那个工程**（见 [../events/README.md](../events/README.md)），收到事件就重拉草稿、版本与工程状态，并重新问一次校验、重新渲染预览——状态条不会继续显示 push 之前的「可以发布」。页面在后台时（浏览器冻结标签页、流可能已被对端关掉）由**重新可见或窗口重新获得焦点**兜底重拉一次。焦点与可见性通常一起发生，接连到来的两次只问一次。

理由有两层。

第一层是"结论只有一处"：**"这份内容能不能发布"是一个判断，按 SSOT 原则只有一个实现入口。** 两端各写一份的表现有两种，都很难排查：

- 提示说没问题、发布说不行 → 用户被卡住，且没有任何提示告诉他哪一句是真的。
- 提示说不行、发布其实可以 → 用户放弃一个能用的功能。

服务端这一处的校验同时是发布的前置阶段，因此"页面提示过"与"发布时校验"用的是同一段代码、同一份规则集合，不会漂移。

第二层是"结论要主动出现"：`validate` 在命令行上是一个可以被 shell 看见的结论（见 [cli.md](cli.md)），因为脚本要能写 `validate && publish`。网页上没有这条组合，若结论要等用户点一下才产生，那么"这份草稿现在能不能发"就变成了一个需要用户先想起来去问的问题——而他打开这一页本来就是来问这件事的。因此**不设"校验"按钮**：状态放在那里，人一到就看得见。

**校验请求本身失败**（网络中断、权限不足）与"内容有问题"是两件事，不得混为一谈：前者显示为"校验未完成、可重试"，页面其余部分（预览、版本、资产）照常可用。把一次取不到结论渲染成一片失败，会让用户以为自己的工程坏了。

界面呈现校验结论的位置是**状态条**（结论就在 ① 段上，问题的逐条清单从那里展开），预览不做裁剪——内容有坏引用时预览仍照常渲染其余部分，坏的地方就显示为坏的。

**校验结论是「有问题」时，顶栏不提供对「与当前草稿清单相同的版本」的发布。** 发布读的是版本而不是草稿，但同一份清单会得到同一份拒绝；再点一次只是多一次失败的往返。清单与当前草稿不同的历史版本仍可发布——那份结论说的是草稿，不是每一个历史版本。原因就在状态条上，按钮旁不再写第二句。

## 边界与约束

- **网页端不改内容，也没有结构化编辑。** 写入只有命令行一条路（见 [cli.md](cli.md)）；"点选插入图片"那类所见即所得的问题（两套内容表示如何同步）因此根本不存在——它只在"网页端能改源码"的前提下才成立。
- **网页端不做构建，也不整组送取。** 打包与目录的上送下载都属于本地工具链与命令行（见 [cli.md](cli.md)）。
- **预览里不注入任何 aladdin 编写的脚本或样式**（跑的只有用户自己的内容与资产）。
- **预览不承诺与发布态逐像素一致。** 两者的资产地址来源不同（预签名 vs 公开地址），页的形状也不同（拼成一份 vs 一页一个地址，见上）。**内容一致是由资产不可变保证的**（见 [asset-library.md](asset-library.md)），不是由地址或形状一致保证的。
- 语法高亮属于只读源码视图的呈现细节，不在本 spec 内。

## 可验证性与长程执行

**非长程任务。** 编辑与预览都是即时的同步操作。发布才是长程的，见 [publication.md](publication.md)。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 记号可逐字替换 | 在元素属性、内联 CSS 的 `url()`、`srcset` 三处写 `asset://`，发布后三处都被替换（`internal/galaxy` 测试） |
| 记号不被浏览器解析 | 未解析的 `asset://` 在浏览器里取不到任何东西（部署后冒烟 / 端到端测试） |
| 指向不存在资产即失败 | 内容引用一个不存在的资产，发布被拒且错误信息含该标识（`internal/galaxy` 测试） |
| 指向他工程资产即失败 | 引用另一个工程的资产标识，发布被拒（`internal/galaxy` 测试） |
| 文档间坏链接即失败 | `docs` 形态下引用一个不存在的 `.md` 位置，发布被拒且指出是哪一份文件的哪一处（`internal/galaxy` 测试） |
| 预览落在不透明源 | 预览 iframe 的沙箱属性里没有 `allow-same-origin`，且内容中的脚本读不到父页面（前端测试） |
| 预览不用长效地址 | 预览的资产地址带签名与有效区间，且区间的量级是分钟（`internal/galaxy` 测试） |
| 预览不裁剪却报错 | 内容有一处坏引用时，预览仍渲染其余部分，同时服务端校验入口返回该处问题（前端测试 + `internal/galaxy` 测试） |
| 提示与发布同一入口 | 这一页的校验调用与发布的前置校验指向同一个服务端方法（代码审查 + `internal/server` 测试） |
| 校验结论自动产生 | 打开页面即调用校验入口，不需要用户先做任何操作；订阅收到事件后再次调用（前端测试） |
| 别处改动自动跟上 | 这一页订阅了它正在看的那个工程；收到事件即重拉草稿并重新渲染预览，不需要刷新页面（前端测试 + `test/e2e`） |
| 后台回来兜底重读 | 页面重新可见后重新读取草稿并重新渲染预览；页面隐藏期间不重复拉取（前端测试） |
| 有问题的同一份清单不从顶栏发布 | 草稿校验为有问题时，与草稿清单相同的版本在顶栏不可发布；清单不同的版本仍可发布（前端测试） |
| 校验失败不冒充"内容有问题" | 校验请求失败时呈现为"校验未完成"，且预览与版本、资产照常可用（前端测试） |
| 预览文档不由应用源服务 | 用户内容只经沙箱文档（`srcdoc` / `blob:`）进入 iframe；应用源上不存在一个返回用户内容的地址（前端测试 + 代码审查） |
| 预览可单独打开 | 预览有一条独立路由，单独打开时渲染的是同一份草稿，且沙箱属性与内嵌时一致（前端测试） |
| 网页端不改内容 | 源码视图是只读的；接口面上不存在从网页端写内容的调用（前端测试 + `internal/server` 测试） |

## 待定决策

| 决策 | 推荐默认 | 替换影响范围 |
|------|---------|-------------|
| 网页端编辑内容 | 暂不做，内容的写入只有命令行（**未定**） | 要放开就得引入"单条替换"这种写入形状，并配一条基线校验防两个入口互盖；只读视图要重做成编辑视图 |
| 预览的运行时错误回传（`postMessage` 通道） | 暂不做（**未定**） | 需要一条受控的预览↔宿主页面通道，且它本身是一个需要论证边界的攻击面 |
| 语法高亮 | 暂不做（**未定**） | 只读源码视图的呈现细节，不影响任何行为约定 |
| 网页端整组送取（上传一个目录） | 暂不做，交给命令行（**未定**） | 只影响界面；命令行已是主入口 |
| 内容体积上限的取值 | 定为发布校验的一部分，具体数值实现时确定（**未定**） | 只影响写入与发布校验 |
