# 全局配置与凭证 模块总览

> 本目录是 aladdin **配置来源与合并语义**的功能行为唯一信源。实现细节变更只改代码；配置的**行为**变更（新增来源、调整优先级、改变缺省语义）必须先改本目录。

## 背景与目标

aladdin 的两端进程都需要在启动时获得一份配置：服务端需要"监听在哪、日志写到哪"才能启动，CLI 需要"连哪个服务端、用谁的凭证"才能发请求。这些值有多个来源——内置默认、配置文件、本地覆盖、环境变量、命令行参数——如果两端各写一套合并逻辑，会出现同一个键在服务端和 CLI 上取到不同值，而这类偏差的表现形式是"配置明明写了却不生效"。

本模块的目标是：**配置的来源分层、合并语义与错误处理，在两端只有一套规则；凭证作为密钥，与普通配置分开存储、分开保护。**

成功的衡量标准：

1. 同一个配置键在服务端与 CLI 上的取值来源顺序完全一致，不存在"某一端少读了一层"。
2. 配置文件的定位、缺失与格式错误的处理方式在两端可预测，且"没写这个键"与"写了个空值"可区分。
3. 凭证从不出现在配置文件、日志、错误信息与 `--debug` 输出中；凭证文件的权限问题导致拒绝使用，而不是警告后继续。
4. 全仓库只有一处代码读取环境变量与配置文件，没有第二个模块自行 `os.Getenv`。

## 两端为什么各自持有一份配置

配置文件**按端拆分**，不共用一份：

| 端 | 配置文件 | 关键区分 |
|----|---------|---------|
| 服务端 | `config.yml`（默认在启动目录） | `address` 是**监听**地址 |
| CLI | `config.yml`（默认在用户配置目录） | `address` 是**目标**地址 |

拆分的直接原因是 `address` 在两端语义相反。若两端共用一份 schema，把服务端配置发给同事让他配 CLI 就会静默指向错误的地方——服务端配 `0.0.0.0:9090` 表示"监听所有网卡"，CLI 拿到同一个值则意味着"连接 0.0.0.0"，而后者在某些网络栈下**恰好也能连通本地**，于是错误不会被发现，直到部署到真实环境。

两端共享的是**命名规则与优先级规则**，不是同一份文件，也不是同一个字段集合：服务端有日志文件路径而 CLI 没有，CLI 有请求超时而服务端没有。

## 功能行为

### 来源分层与合并

配置的取值来自五层。**下层覆盖上层**，最终得到一份完整配置：

| 层 | 来源 | 说明 |
|----|------|------|
| 1 | 内置默认值 | 保证零配置即可启动 |
| 2 | 配置文件 `config.yml` | 团队共享的部分，可以提交进版本库 |
| 3 | 本地覆盖 `config.local.yml` | 个人本机改动，不提交（见 [.gitignore](../../../.gitignore)） |
| 4 | 环境变量 `ALADDIN_*` | 无人值守与容器环境的首选 |
| 5 | 命令行参数 | 单次调用，优先级最高 |

合并的关键语义：**每一层只覆盖它显式给出的键，未给出的键保持上一层的取值。** 这条规则有一个必须成立的前提——"没有写这个键"与"写了一个空值"要能被区分：

- 在配置文件中，**键出现即生效**。写出一个空值表示"显式清空这一项"，不写表示"沿用上一层"。
- 在环境变量中，**值为空串等同于没有设置**。环境变量无法表达"显式清空"，需要这一能力时应写进配置文件。

两层来源都不存在、且键也确实没被写过时，才落到内置默认值。默认值不得依赖任何外部状态（如当前用户名、网络接口、环境变量）。

### 文件与环境的宽松程度刻意不同

| 来源 | 出现无法识别的键时 |
|------|------------------|
| 配置文件 | **报错**，并指出是哪个键 |
| 环境变量 | 忽略——只读本端认识的键 |

配置文件是"为这个程序写的"，出现无法识别的键必然是笔误；环境变量是"与整个系统共用的"，无法断言某个变量就是写给本进程的。因此服务端会忽略 `ALADDIN_TIMEOUT`，CLI 会忽略 `ALADDIN_LOG_FILE`——但这两个键出现在**配置文件**里都会报错。

这条不对称带来一个必须记住的推论：环境变量无法表达"显式清空某一项"。需要清空时写进配置文件。

### 配置文件的定位与缺失语义

两端都按同一顺序确定要读的配置文件：命令行参数显式指定 > 环境变量指定 > 该端的默认位置。两端的默认位置不同：

| 端 | 默认位置 |
|----|---------|
| 服务端 | 启动时的工作目录下的 `config.yml` |
| CLI | 用户配置目录下的 `aladdin/config.yml`（与凭证文件同目录，但不同文件） |

**本地覆盖文件由主配置文件的路径推导**：同名但插入 `.local`（`config.yml` → `config.local.yml`）。由主文件推导而不是固定取 `config.local.yml`，是为了让命令行或环境变量指向任意路径时，覆盖文件仍与它成对出现、可预期。覆盖文件无论主文件是否存在都会被尝试读取，缺失不算错误。

缺失与错误的处理是有区别的，这条区别必须两端一致：

| 情形 | 行为 |
|------|------|
| 默认位置不存在配置文件 | **不是错误**，全部使用内置默认值继续运行 |
| 本地覆盖文件不存在 | **不是错误**，跳过该层 |
| 显式指定的配置文件不存在 | **是错误**，拒绝启动/拒绝执行 |
| 配置文件存在但格式非法 | **是错误**，拒绝启动/拒绝执行，并指出是哪个文件 |
| 配置文件中有无法识别的键 | **是错误**，指出具体的键 |

其中两条刻意从严：拼错的键名如果被静默忽略，用户会以为配置已生效，而实际运行的是默认值——这类问题在服务端表现为"改了半天配置没反应"。同理，显式指定一个不存在的文件是错误，因为指定动作本身表明"我认为那里有配置"，静默降级会掩盖路径拼写错误。

### 配置不得成为权限的来源

配置只描述"进程如何运行"，**不描述"谁能做什么"**。具体地：

- 主体、角色、权限码、作用域**一律不得**由配置提供。默认作用域只能来自主体的绑定关系（见 [../rbac/role-model.md](../rbac/role-model.md)）。
- 任何以配置项形式出现的"跳过鉴权""放宽权限""信任该来源"开关都不允许存在。这类开关一旦存在就一定会被用在生产环境。
- 开发用的旁路（种子数据）不属于本模块的配置体系，它有独立的环境变量命名空间且必须显式开启，见 [server-config.md](server-config.md)。

## 边界与约束

本模块**明确不处理**：

- **配置热重载**。修改配置需要重启进程。CLI 每次执行本就是一个新进程，天然满足；服务端不做文件监听，也不响应要求重载的信号。
- **远程配置中心**。配置只来自本机文件与环境变量，不从网络拉取。
- **配置内容的加密**。密钥不进配置文件，因此没有加密配置的需求；凭证的保护方式见 [credentials.md](credentials.md)。
- **配置文件格式的版本迁移**。旧格式不做兼容读取，字段变更即要求用户改配置，且因"无法识别的键是错误"而必然被发现。
- **前端的配置**。Web 前端没有配置文件，也不应该有：它运行在用户的浏览器里，任何写进前端的"配置"都是公开的。前端的运行时参数来自页面来源与 URL 查询参数（见 [../rbac/frontend-permissions.md](../rbac/frontend-permissions.md)）。

约束：

- 全仓库只有一处代码读取环境变量与配置文件。其他模块需要配置时，接收已解析完成的配置值，不得自行读取来源。
- 环境变量统一 `ALADDIN_` 前缀。变量名各自在其所属模块内集中定义——配置项在配置模块、凭证在凭证模块、开发旁路在服务端模块——调用方不得手写字符串字面量。
- 配置值与凭证值都不得出现在日志中；配置可以出现在启动日志里（用于确认实际生效值），凭证不可以。

## 可验证性与长程执行

**非长程任务，无需中途校验。** 配置是在进程启动时一次性解析完成的同步过程。需要长期保证的是分层与合并规则的稳定性：

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 单一加载入口 | 全仓库检索确认除配置模块与凭证模块外，没有第二处读取环境变量或配置文件的位置（评审时检查） |
| 优先级链固定 | 同一个键在五层的取值结果为表驱动测试所固定；新增一层而不更新测试即失败（`internal/config` 测试） |
| 覆盖只作用于显式键 | 配置文件中未出现的键不改变上一层的取值（`internal/config` 测试） |
| 空值与缺省的区分 | 空值、只写键不写值、完全没写三者产生不同结果（`internal/config` 测试） |
| 缺失语义一致 | 默认位置缺失不报错、显式指定缺失报错、格式非法报错、未知键报错（各有 `internal/config` 测试） |
| 键集合不漂移 | 示例配置的键与实现声明的键集合一致；每个声明的键都确实能改变配置（`internal/config` 测试） |
| 凭证不入日志 | 凭证值不出现在错误信息与 `--debug` 输出中（`internal/auth` 测试 + 启动冒烟） |
| 凭证文件权限 | 权限过宽时拒绝使用，而非告警继续（`internal/auth` 测试） |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 可观测性 | 配置提供日志级别与文件路径；取值集合与 [observability.md](../../observability.md) 一致 |
| YAML 解析 | 配置文件的语法由 YAML 解析库提供；本模块只消费解析结果，不自行实现语法 |
| 身份认证 | CLI 配置中的目标地址与凭证共同构成一次调用的上下文；凭证本身的来源优先级见 [../rbac/cli-permissions.md](../rbac/cli-permissions.md) |
| RBAC | 配置**不**参与权限判定；默认作用域的权威来源是主体的绑定关系 |
