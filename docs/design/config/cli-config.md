# CLI 配置

## 背景与目标

描述命令行客户端在一次调用中，除了凭证之外还需要哪些输入、从哪读、以及读不到或读错时如何失败。

CLI 的配置问题与它的鉴权问题一样，最终都表现为"命令跑不通"。两者必须能被区分：**目标地址配错**与**凭证缺失**是完全不同的故障，前者改配置、后者去登录，而它们给用户的第一印象可能都是"连不上"。本子模块的目标是让这两类输入各有清晰的来源与各自可操作的失败提示。

## 功能行为

### 配置项

| 配置键 | 含义 | 内置默认值 |
|--------|------|-----------|
| `address` | **目标**地址（服务端的 `host:port`） | `127.0.0.1:9090` |
| `timeout` | 单次调用的超时 | 30 秒 |
| `log_level` | 输出详细度；`debug` 等价于命令行 `--debug` | `info` |
| `otel_endpoint` | OTLP/HTTP 端点（`host:port`）；为空表示不上报 | 空 |
| `otel_insecure` | 是否用明文 HTTP 连接该端点 | `false` |
| `otel_sample_ratio` | 采样比例，取值 0–1 | `1` |

三端中只有 CLI 的配置含 `timeout`：服务端处理请求的超时由请求自身的上下文决定，不由进程级配置决定。

`address` 的默认值与服务端的默认监听地址**取同一个值**，因此本机开发时两端都是零配置即可互通。这个值只在配置模块中定义一处，两端引用同一常量——分成两个字面量就会在某一端调整默认端口后，让"零配置互通"这个特性静默失效。

### 配置文件的查找

按以下顺序确定要读的文件，先命中者胜出：

1. 命令行参数显式指定的路径
2. 环境变量指定的路径
3. 用户配置目录下的 `aladdin/config.yml`（即凭证文件的同目录）
4. 以上都不存在视为"无配置文件"，全部使用内置默认值

CLI 的默认位置与凭证文件同目录，但不共用文件：配置可以提交进版本库、可以贴给别人、可以写进容器镜像，凭证不行。把两者放进同一个文件，等于让"共享我的 CLI 配置"变成"泄露我的凭证"。

### 与凭证的衔接

一次 CLI 调用需要两个独立输入，它们各有自己的来源链：

| 输入 | 来源优先级 | 唯一入口 |
|------|-----------|---------|
| 目标地址与行为开关 | 命令行参数 > 环境变量 > 本地覆盖 > 配置文件 > 内置默认 | 本模块 |
| 凭证 | 命令行参数 > 环境变量 > 凭证文件 | [../rbac/cli-permissions.md](../rbac/cli-permissions.md)（优先级）与 [credentials.md](credentials.md)（落盘形态） |

两条链的形状相同（参数最高、文件最低），但**互不影响**：`--token` 只改变凭证来源，不改变目标地址；`--address` 只改变目标地址，不改变凭证来源。

一次调用中，目标地址与凭证必须来自**同一次解析结果**，不得在命令的不同位置各自解析一遍——否则会出现"地址用了覆盖文件的值、凭证用了环境变量的值"这种无法从任何一处配置推断出的组合。

**凭证缺失与配置错误必须区分提示**：

- 凭证缺失或过期 → 提示执行登录命令，而不是提示地址不可达或权限不足。
- 目标地址非法或配置文件格式错误 → 提示配置问题并指出文件与键名，而不是提示去登录。

这条区分不是措辞偏好：把配置错误报成"未认证"，会让脚本反复触发登录；把凭证缺失报成网络问题，会让用户去查一个没有故障的服务端。

### 失败类别与退出码

CLI 的退出码按 [../rbac/cli-permissions.md](../rbac/cli-permissions.md) 划定的类别区分，其中：

- **配置错误（文件不存在但被显式指定、格式非法、键名无法识别、地址非法、超时非法、日志级别非法）归入"用法错误"类别**，与参数解析失败同一个退出码。
- 配置错误**不得**归入"未认证"或"权限不足"两个类别——那两类分别触发"重新登录"与"不要重试"的脚本行为，而配置错误的正确处理是修正配置后重跑。
- 推论：**标志解析失败与多余的位置参数也必须落到"用法错误"**。否则同一个类别内部就有两个不同的退出码，脚本无法据此分支。

配置在哪些命令上被加载：只有真正要发起调用的命令才会读到配置。纯本地命令（如查看版本）不加载配置，因此它在配置损坏时依然可用——这是刻意的，否则一个写坏的配置文件会让你连版本号都查不到。

### 本地覆盖的使用方式

个人本机改动写入本地覆盖文件（不提交），典型场景是本机同时跑多个环境：

- 团队共享的 `config.yml` 写默认环境，可以提交。
- 开发者本机在本地覆盖文件中把目标地址指向自己的实例，不提交。

覆盖文件与主配置文件的读取、合并规则完全一致，见 [README.md](README.md)。它的位置由主文件推导（`config.yml` → `config.local.yml`），因此用 `--config` 指向任意路径时，覆盖文件依然与它成对出现。

## 边界与约束

- 不处理配置热重载：每次执行都是新进程，天然读取最新配置。
- 不提供任何跳过服务端鉴权的开关。
- 配置与凭证值都不得出现在 `--debug` 输出中；`--debug` 只输出**来源**（哪个文件、哪个环境变量）而非**值**。
- 不缓存配置或判定结果到磁盘。CLI 不对任何"上次的结论"做持久化复用。

## 可验证性与长程执行

**非长程任务，无需中途校验。** 配置在每次执行时解析一次。

| 核查项 | 判据（验证手段） |
|--------|----------------|
| 两条链互不影响 | 只提供凭证来源时目标地址仍取配置值，反之亦然（`internal/auth` 与 `internal/config` 测试） |
| 单次解析 | 地址与凭证分别只有一处解析入口，命令实现不各自再解析一遍 |
| 失败类别正确 | 配置错误、标志解析失败、多余位置参数同为用法错误退出码，且与"未认证""权限不足"均不同（退出码映射测试） |
| 默认值同源 | 两端的默认地址取自同一常量（`internal/config` 测试） |
| 来源而非值 | `--debug` 输出含来源标识、不含凭证原文（`internal/auth` 测试断言来源不含令牌） |
| 零配置可用 | 无配置文件、无环境变量、仅有本机凭证时可正常调用（冒烟检查） |
| 纯本地命令不受配置影响 | 查看版本在配置损坏时仍成功（冒烟检查） |

## 依赖关系

| 依赖对象 | 交互方式 |
|---------|---------|
| 配置加载（父模块） | 复用 [README.md](README.md) 的分层、合并与缺失语义 |
| 凭证 | 提供令牌与作用域；本模块只负责目标地址与行为开关，不含凭证的存储 |
| RBAC / CLI 接入 | 配置错误与鉴权失败的区分，需与 [../rbac/cli-permissions.md](../rbac/cli-permissions.md) 的退出码类别一一对应 |
| gRPC 客户端 | 接收已解析完成的目标地址、超时与凭证，不自行读取来源 |
