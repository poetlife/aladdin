# 部署信息 模块总览

> 本目录是 aladdin **"这个进程是哪一次构建、跑在哪、起来了多久"** 这一问题的功能行为唯一信源。

## 背景与目标

「运维」分组下原先只有遥测（见 [../../observability.md](../../observability.md)），它回答"Web/CLI 最近在干什么"。没有谁回答排障与发版核对时最先被问的那三个问题：

1. 线上跑的是哪个版本？
2. 前后端是不是同一次构建？
3. 这个进程起来多久了、是哪一个副本？

这三个问题原先都要 ssh 上去问。而版本号其实**已经在二进制里了**——`make build` 与 `make release-build` 一直用 ldflags 注入它，只是没有任何接口把它暴露出来；前端则根本没有记录自己是哪次构建，界面无从得知。

成功的衡量标准：

1. 有权限的管理员打开「运维 → 部署信息」，一眼看到后端版本、提交号、构建时间、启动时间与运行时长、实例标识。
2. 页面同时显示**前端自己**的版本与提交号，并在两侧提交号对不上时给出醒目提示。
3. 运行时长本地刷新，不为它轮询接口。
4. 命令行 `aladdin version` 报的版本与页面上「后端」那一栏**不可能不一致**——它们是同一个变量。
5. 无权限的主体看不到入口，直调接口被拒。
6. 本机构建显示 `dev` / `git describe` 的结果，发布构建显示 tag。

## 模块边界

| 问题 | 归属 |
|------|------|
| 哪次构建、什么平台、起来了多久 | **本模块** |
| Web/CLI 最近在干什么 | [../../observability.md](../../observability.md) |
| 这份部署是怎么配的 | [../config/README.md](../config/README.md) |
| 怎么把产物部署上去、怎么回滚 | [../../deploy.md](../../deploy.md) |

三条边界写在这里，因为它们都是"顺手多返回几个字段"最容易越过去的地方：

- **不讲配置。** 库地址、对象存储桶、登录渠道一概不在这一页。两者答的不是同一个问题（"哪次构建"对"这份部署怎么配的"），而且配置里可能含密钥——[../config/README.md](../config/README.md) 说明了为什么密钥只能来自环境变量。
- **不是第二个监控平台。** CPU、内存、磁盘、依赖连通性都不在这里。这一页连一个数字指标都不返回，返回的全是自描述字符串；那些能力交给外部监控系统。
- **不做任何操作。** 没有远程重启、没有触发发版、没有改配置。它整页只读，唯一的交互是"刷新"与"复制"。

## 版本信息只有一个来源

前后端各自由构建期注入，**取值出自同一处**：`make build` / `make release-build` 取一次 `VERSION` / `COMMIT` / `BUILD_TIME`，一路进 Go 的 LDFLAGS，另一路进 Vite 的 `define`。

这条不是洁癖，它是第 2 条成功标准成立的前提：两侧各算一份的话，页面上那道"提交号是否一致"的比较就只是在比两个不相干的字符串，而它看起来照样在工作。

两个直接后果：

- **后端侧只有一个注入目标**（`internal/buildinfo`）。命令行与服务端都从它读，因此拿到的是一个变量而不是两个长得一样的变量。
- **链接器 `-X` 会静默失效**：符号名写错时变量保持默认值，构建一路绿灯，只有版本号悄悄退化成 `dev`。这件事由 `internal/buildinfo` 的测试在构建期兜住（判据取自 Makefile 与 go.mod 本身，不另抄一份符号名）。

未注入时各项退化成诚实的缺省值（`dev`、空提交号、空构建时间），**不编一个看起来像真的取值**：空表示"没有"，且只有这一个含义——给一个零值时间的时间戳会让界面只能靠模式匹配去猜它其实表示"没有"。

## 前后端一致性怎么判

比较两侧的提交号，三种结论，**必须分开**：

| 结论 | 含义 | 页面上的处理 |
|------|------|-------------|
| 一致 | 页面与服务端出自同一次构建 | 不占地方 |
| 不一致 | 前端缓存了旧 bundle，或这个部署的前后端是分开发布的 | 醒目提示，并同时说出这两种成因 |
| 无从比较 | 至少一侧没有提交号（本机构建、未经 `make` 的构建） | 说明"只在两侧都有值时才有结论" |

「无从比较」与「不一致」**不能合成一个结论**：本机构建拿不到提交号，把它报成不一致会在每次本地开发时给出一个假告警——而一个平时总在报警的提示，在真的不一致那天也就没人看了。

## 运行时长本地算

服务端只给**进程启动时刻**，不给"已经跑了多久"。

后者是一个每问一次就变一次的数，而这一页的每一项都应当是"一次读取之下不变的事实"：给它一个随时间变化的字段，等于让页面为了它去轮询接口。界面按启动时刻自己推算、本地每分钟走一格，因此刷新按钮换的是"服务端的自述"，不是"现在几点"。

客户端与服务端时钟有偏差时，算出的时长可能是负数——那时显示「—」而不是一个负的时长："-3 秒"只会让人以为页面坏了，而它其实只是两边差了几秒。

## 权限

新增权限码 `ops.deployment.read`，**不与遥测共用 `telemetry.read`**。

两者都是"看得见但不改得动"，但它们回答的不是同一个问题：合成一码会让"给审计员看遥测"必然连带"给他看版本号"，而这两件事将来各自收紧的时机不会一样。

内置角色里授予 `system.admin`（由 `*` 覆盖）与 `auditor`。审计要能回答"当时跑的是哪一版"——某次变更发生前后服务端到底换没换、是不是同一份构建，都在这一页上，而它同样只是看。创作者默认不可见。

页面上还隐含一件事：**未认证的访客拿不到版本号**。版本号便于攻击面探测，因此不提供任何免认证的版本端点——负载均衡要的健康检查只回 `ok`，不带版本。

## 待定决策

- **多副本下的实例标识**取自主机名。容器编排里主机名通常是 Pod 名，够用；真到了需要稳定实例 ID 的场合（跨重启追踪同一个副本），要重新决定取什么。
- **没有版本变化的对比视图**（"这次发布把版本从 A 换到了 B"）。要那个能力，前提是先有一处记录每次发布的版本——那是发版流程的事，不在这一页。
