# 人读示意图约定

> 本文件是 aladdin 的 **design 文档里的人读图怎么画** 的唯一信源。

## 背景与目标

design 文档里的图不是装饰，是让人**一眼看出结构**的东西：一个工程有哪几个状态、字节存在哪一层、一次请求经过谁。这些图此前已经在用（[galaxy 的 README](galaxy/README.md) 里状态流转、存储分层、字节进出三张就是），但仓库没有任何成文约定——于是每加一张图就重新即兴决定一次：画哪种、放哪、和正文什么关系、要不要顺手导出一张 PNG 一起提交。

本文件**不发明新做法**，只是把已经在用的做法登记下来，供下一次画图时对照。

成功的衡量标准：

1. 新人能据此判断：一段内容是画在文档里的 ASCII 框图，还是该做成一份 HTML 沟通件。
2. Review 能据此检查：图是否与本次行为变更同 PR 更新。
3. 图**不成为第二套与 spec 打架的事实源**。
4. 不强制任何人安装额外工具；重器那条路是可选的、文档齐全的。

## 图的地位：说明视图，不是第二份事实来源

这和 [SSOT 原则](../../AGENTS.md) 是同一条规矩落在图上：

- **spec 的文字是唯一信源，图是它的一个视图。** 图和文字冲突时以文字为准，且这本身就是缺陷——必须在当次改动里改齐。
- **行为变更必须同时改图与文字**，不许"先改文字，图回头补"。补不上的那张图，比没有更坏：它让读者以为旧结构还在。
- **图不得暗示未实现的路径或状态。** 画一条还没写的分支，等于在 spec 里写了一个不存在的行为。

## 默认做法：同文档内的纯文本图

**默认就是它。** 绝大多数图用这个就够了。

| 项 | 约定 |
|----|------|
| 形式 | 同文档内的 ASCII / Unicode 框图 + 原生 Markdown 表格；重点用**加粗**或旁注 |
| 何时用 | 状态流转、存储分层、字节进出、请求时序——需要"看清结构"的地方 |
| 命名 | 用**正式状态名、路径、字段名**，与 spec 正文和代码同名。图里的 `② 有版本未发布` 必须能在正文里找到同一个词 |
| 粒度 | **一张图讲一件事。** 讲不清说明该拆成两张 |
| 标注 | 图旁一句点明**类型与范围**（架构 / 工作流 / 时序 / 数据流 / 生命周期），读者才知道这张图省了什么 |
| 篇幅 | 图与它解释的那段文字相邻，不集中堆到文末 |

**不提交生成后的 PNG / SVG 当 design SSOT。** 二进制进版本库就没人 review 它、也没人改它；它还会与旁边的文字各自漂移。图要能随文字一起被 diff。

合规示例（可直接对照，不要求重画）：[galaxy/README.md](galaxy/README.md) 的

- 「状态流转」——生命周期类，一张图钉死三个状态与四条边；
- 「存储分层」——架构类，用两个并排的树说清库与桶的分工；
- 「字节怎么进、怎么出」——数据流类，四行箭头把读写两条路分开。

## 可选重器：Archify（或同类）

只有**默认做法明显不够**时才上它：跨多个模块的总览、需要多视图（架构 + 时序 + 数据流）配合、要给不 clone 仓库的人演示、或大改存储/发布这类需要 **Before / Delta / After** 对照的评审。

形态是 **typed JSON IR → 交付前原子校验 → 自包含 HTML**。有价值的是中间那步校验：它让"图画得和事实不符"在交付前就失败，而不是靠人眼看。

两条不能越的边界：

- **产物是沟通件，不进 `docs/design` 正文充当 SSOT。** 正文仍是文字 + ASCII 图；HTML 是它的一个更重的呈现，可以另存、可以只在评审时贴出来。
- **不为了用它而用它。** 几行 ASCII 能画清的状态机，换成 IR + 生成管线只是把同一件事说了两遍，还说在一套没人 review 的格式里。

不强制安装。工具仅在需要的 agent 本地或 CI 里可选引入。

## 从 Archify 吸收的习惯

即便不上这套工具，这些习惯本身值得照做：

| 习惯 | 落到 aladdin |
|------|-------------|
| 图有类型（架构 / 工作流 / 时序 / 数据流 / 生命周期） | 图旁标明类型与范围 |
| Typed IR + 交付前校验 | 可选增强；只有复杂总览才走生成管线 |
| 不编造拓扑，证据可选 | 术语与 spec、代码一致；不暗示未实现路径 |
| Architecture Delta | 大改存储 / 发布等时，可选附一张 delta 供 review |
| 产物自包含、可分享 | HTML 作沟通件，不进 SSOT 正文 |

**明确不照搬**：默认把大 HTML / PNG 提交进 design；用 Archify 替掉简单状态机的 ASCII；没有校验就上自动生成的图。

## 边界与约束

本约定**不处理**：

- 文档该写什么、不该写什么——那是每个模块 spec 自己的事。
- 非人读的图（OpenAPI 渲染页、前端界面里的图形）——它们各有归属。

约束：

- **Mermaid 等渲染型图暂不作为默认路径。** 在明确接入渲染与 CI 一致性校验之前，它比 ASCII 多的那点好看，抵不过"在编辑器与 GitHub 上各显示成什么样不知道"的不确定。要用就先开一条子 issue 把渲染与 CI 定下来。
- **图随行为变更走**：属于同一模块的图与文字同 PR 改，不拆成两个 PR。

## Review 清单

改到 design 文档时，对照勾：

- [ ] 本次行为变更涉及的图，是否与文字在**同一个 PR** 里改齐
- [ ] 图里的状态名、路径、字段名是否与 spec 正文、代码一致
- [ ] 图有没有暗示一条还没实现的路径或状态
- [ ] 是否标明了图的类型与范围
- [ ] 复杂总览有没有误把生成件塞进正文、挤掉文字的位置
- [ ] 有没有把生成后的图片文件提交进版本库当 SSOT

> spec 是功能行为的唯一信源，代码是实现的唯一信源。
> 功能行为变更 → 先改 spec；实现细节变更 → 只改代码。
