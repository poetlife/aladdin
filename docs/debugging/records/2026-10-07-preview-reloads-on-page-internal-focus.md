# 在预览里点过一下之后，点外壳上任何按钮都会让预览整个重载

**日期**：2026-10-07
**收敛到的端**：Web（前端）。没有服务端调用出问题——重载是前端自己发起的，而且发的是一次**正常**的预览取址

## 症状

在工作台（`/galaxy/<工程>`）的预览 iframe 里点一张图，然后点外壳上的**任意一个按钮**（顶栏、工具条、状态条……点哪个都行），预览整块重新加载：滚动位置回到顶部、翻到的那一页丢了、正在看的图被甩掉。

关键在"**点过一下**"这个前提：没有先在预览里点过东西时，同样的按钮不引发重载。

## 收敛过程

三层，逐层把范围压到"什么时候该重拉"这一处：

1. **重载是谁发起的**：iframe 只在 `src` 变化（或 `key` 变化）时重新导航。`key` 只跟"重试"次数走，
   所以只能是 `src` 变了。而 `src` 来自 `previewUrl` 状态，唯一的写入点是 `renderPreview`
   ——重载 = **又取了一次预览地址**。
2. **谁调了 `renderPreview`**：页面只在三处调它——打开页面、点「刷新」、以及
   `refreshOpenDraft`（订阅事件与"回到前台"两条路径共用）。前两个都不是这里发生的事，
   于是落在 `useReloadWhenVisible`。
3. **为什么"点按钮"会走到那里**：`window` 的 `focus` 事件。**焦点落进本页自己的子框架、
   再回到外壳上的控件时，父窗口同样会收到 `blur` 与 `focus` 这一对**——而预览的内容住在
   发布域上，用户点内容里的任何东西都会把焦点送进那一帧。于是"在预览里点过一下"之后再点
   外壳按钮，就凑出了一次**页内的焦点换位置**，被当成了"这一页回到前台"。
   一个探针（真实 Chromium + 跨源沙箱 iframe，真点击）打出的序列：

   ```
   点击壳上的按钮            （无事）
   点击 iframe 里的内容      WINDOW-BLUR   hasFocus=true  active=IFRAME/f
   再点壳上的按钮            WINDOW-FOCUS  ← 兜底重拉在这里被触发
   切到另一个浏览器窗口      WINDOW-BLUR   hasFocus=false ← 这才是真的离开
   切回来                    WINDOW-FOCUS  ← 这一条才是兜底要认的
   ```

## 根因

**`focus` 不是一个"回到这一页"的信号**：它同时覆盖了"这一页真的离开过又回来"和"焦点在本页
内部换了个位置"两件完全不同的事。按 `focus` 一律重拉，代价恰好落在最刺眼的地方——**重取一次
预览地址就是一张新票，iframe 因此整个重新导航**。

判据（看到这个症状先查什么）：

- **先在预览（或任何一个沙箱 iframe）里点过** → 就是这个症状，不必去查预览通道是否失败。
- **没点过也一样重载** → 不是这一条，去查订阅事件是否在空转（`refreshOpenDraft` 的另一条路径）。
- **只有在别的应用/窗口/标签页之间来回切时才重载** → 那也是错的，见下面"为什么整条去掉"。

## 结论：整条兜底去掉，改成判这条连接的死活

先按"把判据收紧"修了一版（只在"本文档确实丢过焦点"之后的那次 `focus` 上重拉，实测跨源沙箱
iframe 下 `hasFocus()` 在两种情形下分别取值），但接着追问了一个更前面的问题：**这条兜底到底
在挡什么？** 查下来它的立足点比它读起来薄：

- 它声称挡的是"浏览器冻结后台标签页，流可能已被对端关掉"。可**流有 30 分钟上限寿命**
  （`watchMaxLifetime`），到点服务端主动结束，客户端一恢复就读到结束 → 重连 → 每个主题各一条
  `RESYNC` → 重拉。这一档本来就归推送自己的重连链路管。
- 真正只剩它挡的，是**连接死了而两边都不报错**（半开连接：睡眠、NAT 表项过期、换网）——这
  一档它挡得住，但**挡住的原因和它用的信号无关**：它赌的是"用户又看向这一页"与"连接已死"
  在时间上相关，而这个相关性很弱，代价是页内换一次焦点就误触发。

于是整条去掉，改成**按心跳判活**：客户端多久没从流上收到任何东西（心跳也算）就主动断开，
走既有的重连路径，重连即 `RESYNC`。判连接的死活，就去看连接。它同时覆盖了三件原来只有兜底
勉强照顾的事：僵尸连接（含用户一直没离开过的情形）、冻结标签页（定时器在恢复时立刻到点）、
以及"回到前台"这件事本身——**不再需要有人去猜"用户回来了没有"**。

代价如实写下：**没有"回到前台先重读一次"这层保险了**，重读完全由订阅驱动。若那条流以
"重试无意义的失败"结束（`isPermanentFailure`，例如权限被收回），客户端按既有策略不再重连，
这一页会停在当时的状态直到用户自己动作（刷新、切槽）——这是上一版就有的行为，不是这次引入的。
